Every uptime monitor in Site Qwality follows the same lifecycle: configure → run on schedule → emit results → trigger notifications on state change. What differs is *what* the monitor checks.

| Check type | What it checks | Use for |
|---|---|---|
| [HTTP](/uptime-monitoring/http-checks/overview/) | A URL responds with the expected status, body, and latency | Websites, APIs, webhook receivers |
| [SSL/TLS](/uptime-monitoring/ssl-tls-checks/overview/) | A certificate's expiry, chain, and validity | Anything served over HTTPS |
| [Domain expiry](/uptime-monitoring/dns-checks/overview/) | A domain's registration at the registry: expiry date, registry holds, registrar and nameserver changes | Any domain you would lose if a renewal failed |
| [Cron heartbeat](/uptime-monitoring/cron-checks/overview/) | A scheduled job *pinged* on time | Backups, ETL, batch jobs |
| [Browser](/uptime-monitoring/browser-checks/overview/) | A full Playwright script passes in a real Chromium | Login flows, checkout, multi-page journeys |

## Picking the right check

- **You have a URL that should be `200 OK`.** Use [HTTP checks](/uptime-monitoring/http-checks/overview/). You can also opt-in to a paired TLS check (cert expiry) and domain expiry check (domain registration) on the same monitor.
- **You only care about cert expiry, not whether the site is up.** Use [SSL/TLS checks](/uptime-monitoring/ssl-tls-checks/overview/). Otherwise, just enable the TLS sub-check on your HTTP monitor.
- **You want to hear before a domain registration lapses.** Enable the [domain expiry check](/uptime-monitoring/dns-checks/overview/) on an HTTP monitor for that domain. It reads the registration from the registry, so it also catches a registry hold, a registrar change, and a nameserver change.
- **You have a cron job that should run every N minutes.** Use a [cron heartbeat](/uptime-monitoring/cron-checks/overview/). Your job pings Site Qwality at the end of each successful run, and Site Qwality alerts when it doesn't.
- **You need to validate a multi-step user flow.** Use [browser checks](/uptime-monitoring/browser-checks/overview/). You write a Playwright script and Site Qwality runs it on schedule, capturing a HAR + video on failure.

## Cross-cutting concerns

### Check locations

HTTP checks run from the **check locations** you select on each monitor, on AWS, Google Cloud and Microsoft Azure. The live list is on the [locations page](https://siteqwality.com/locations/), and `GET /check-locations` returns it to API clients (see [check locations](/uptime-monitoring/http-checks/reference/#check-locations) in the HTTP reference).

- **Default.** A monitor with `check_regions` unset or empty runs from `aws-us-east-1` (Virginia, AWS).
- **Plans.** The free plan allows one location per monitor. Paid plans can select any number. Selecting more than one without a paid uptime plan returns `403` with `multi_region_requires_paid_plan`, on HTTP and browser checks.
- **Billing.** Each location a check runs from counts as one check toward your monthly check volume. A monitor checked from three locations every minute uses three checks a minute.
- **Other check types.** Browser, SSL/TLS, domain expiry and DNS record checks run from `aws-us-east-1` only. Location selection applies to HTTP checks.

Every selected location runs on each scheduled tick, and the results are evaluated together. `min_healthy_regions` sets how many of them must pass for the monitor to count as healthy. A location that cannot return a result in a run (because its provider is unreachable, for example) is left out of that run instead of counting as a failure. See [location quorum](/uptime-monitoring/http-checks/how-to/confirmation-threshold/#2-location-quorum) for the details.

Checks do not come from fixed IP addresses. To let them through a firewall or bot protection, see [allowlisting our checks](/uptime-monitoring/http-checks/allowlisting/).

### Schedules

| Check type | Minimum interval (free) | Minimum interval (paid) |
|---|---|---|
| HTTP | 60 s | 30 s |
| Cron heartbeat | n/a | n/a (driven by your job's ping cadence) |
| Browser | 5 min | 5 min |
| TLS, domain expiry (paired with HTTP) | daily, not configurable | daily, not configurable |

### Tags

Every monitor accepts a `tags: string[]` field. Use tags consistently (`service:api`, `env:prod`, `team:platform`) and you can:

- Match [maintenance windows](/incident-management/maintenance/overview/) to silence by tag.
- Filter dashboards and alerts by tag.
- Roll up uptime by service or environment.

### Services (logical grouping)

Beyond tags, you can attach a monitor to a *service* (`service_id`). Services are higher-level groupings. See **Services** in the dashboard.
