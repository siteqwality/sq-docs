If your site sits behind a firewall, a WAF or bot protection, it can block or challenge our checks, and the monitor reports an outage your users never saw.

## There are no fixed IP addresses

HTTP checks run from [check locations](/uptime-monitoring/overview/#check-locations) on AWS, Google Cloud and Microsoft Azure. Each location sends its requests from its cloud provider's shared address ranges, and those addresses change, so there is no list of IPs to allowlist. Allowlisting those shared ranges would also let in every other customer of the same cloud. Allowlist by something the request carries instead: a secret header (recommended) or our User-Agent.

If your setup cannot match on a header and you need checks from a fixed IP address, email [hello@siteqwality.com](mailto:hello@siteqwality.com).

## Option 1: a secret custom header

Add a header with a long random value to the monitor, then tell your firewall or bot protection to allow requests that carry it.

<Steps>

1. Generate a long random value, for example with `openssl rand -hex 32`.

2. Open the monitor and choose **Edit monitor**, then **Request**. Under **Custom HTTP Headers**, enter `X-Uptime-Check` as the header name and your random value as the header value. Save. Use this custom name rather than a standard metadata header such as `User-Agent`, whose value can remain visible in results.

   Through the API, read the monitor with `GET /http/job/{job_id}`, then send its complete `custom_http_headers` map, with `X-Uptime-Check` added, in `PUT /http/job/{job_id}`. The map replaces the stored headers, and masked values sent back unchanged keep their stored values.

3. In your firewall, WAF or bot protection, add a rule that allows requests whose `X-Uptime-Check` header equals the value, or lets them skip the challenge. In Cloudflare, for example, that is a WAF custom rule with the expression `any(http.request.headers["x-uptime-check"][*] eq "<your random value>")` and the **Skip** action.

4. Wait for the next check, or choose **Check now**, and confirm it passes.

</Steps>

Treat the value like a password. Site Qwality masks the `X-Uptime-Check` value when it returns a monitor or check result in the dashboard and API. If it leaks, generate a new one and update both the monitor and the rule.

## Option 2: the User-Agent

Every check sends this User-Agent:

```
site-qwality-check/1.0
```

You can match on it to skip a bot challenge or a rate limit. Anyone can send the same string, though, so it identifies our checks without proving a request came from us. Use it where a false match costs little, or together with the secret header. A monitor with Web Bot Auth turned on also carries a signature that [proves a request came from us](/bot/#verifying-a-request).

## Web Bot Auth: signed requests

Use this when the site is behind Cloudflare and you cannot change its rules, for example a client's site.

A signed request carries a digital signature next to its usual headers. Site Qwality makes the signature with a private key only we hold and publishes the matching public key at `bot.siteqwality.com`. Whoever receives the request can check the signature against that key, and if it matches, the request came from Site Qwality. Anyone can copy a User-Agent, but nobody can make a valid signature without our key.

Cloudflare [lists Site Qwality Monitor as a verified bot](https://radar.cloudflare.com/bots/directory/site-qwality-monitor). When a signed check reaches a site behind Cloudflare, Cloudflare checks the signature and recognizes the request as ours. Its bot protection usually lets verified bots through without a challenge, unless the site's own rules block them.

To turn it on, open the monitor, choose **Edit monitor**, then **Advanced**, and check **Sign requests with Web Bot Auth**. In the API, set `web_bot_auth` to `true`. It is off by default and applies to HTTP monitors only.

- Signing adds the `Signature-Agent`, `Signature-Input` and `Signature` headers. The URL, method, other headers and body stay the same.
- Site Qwality Monitor is registered with Cloudflare. Other bot-protection services may still challenge a signed check, and so can a Cloudflare rule that blocks verified bots. Use a [secret header](#option-1-a-secret-custom-header) there.
- To verify a signature yourself, see [verifying a request](/bot/#verifying-a-request).

## Blocked by bot protection

When a check fails and the response carries the signature of a known bot-protection service, the result's `failure_reason` is `bot_protection`, shown in the dashboard as **Blocked by bot protection**. The signatures recognized include Cloudflare challenges, AWS WAF CAPTCHA and challenge actions, Akamai, Imperva, DataDome and PerimeterX (HUMAN). The label is only applied to a check that already failed on its status code.

It still counts as a failure: the monitor goes down and alerts like any other failed check, because from the outside we cannot tell whether your users are being refused too.

What to do about it:

- **Turn on Web Bot Auth** when the site is behind Cloudflare and you cannot change its rules. Each check is then signed as Site Qwality Monitor, which Cloudflare lists as a verified bot. See [Web Bot Auth: signed requests](#web-bot-auth-signed-requests).
- **Allowlist our checks** with a [secret header](#option-1-a-secret-custom-header). This is the fix that lasts.
- **Add a location on another provider.** Bot protection often scores cloud networks differently, so checking from another network can help. More than one location per monitor needs a paid uptime plan; see [check locations](/uptime-monitoring/http-checks/reference/#check-locations).
- **Try HTTP/1.1.** Some bot-management edges treat HTTP/2 and HTTP/1.1 clients differently. Set `http_version` to `http1_1`; see [HTTP versions](/uptime-monitoring/http-checks/reference/#http-versions).
- **Monitor an endpoint that is not challenged**, such as a health check path your protection lets through, if the page itself is always behind a challenge.

<Aside type="tip">
`confirmation_threshold` can stop an occasional challenge from paging you, but it does not stop the failures being recorded. See [requiring N failed checks](/uptime-monitoring/http-checks/how-to/confirmation-threshold/).
</Aside>
