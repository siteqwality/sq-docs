The full request/response schema is in the auto-generated [API Reference](/api-reference/). This page is the human-readable cheat sheet for `POST /http/job` and `PUT /http/job/{job_id}`.

## Request settings

| Field | Type | Default | Description |
|---|---|---|---|
| `friendly_name` | string | none | Display name shown in the dashboard. 1 to 99 characters. |
| `service_id` | uuid \| null | none | Create only: assign the monitor to a service in your account. Unknown or foreign service IDs return `404`. Change an existing assignment from Services. |
| `uri` | string | required | Target URL. Must parse as an absolute URI with a host. `https` is required unless `monitor_tls` is explicitly `false`. |
| `method` | string | required | Any valid HTTP method token (`GET`, `POST`, `HEAD`, ...). |
| `run_interval_seconds` | int | required | Seconds between checks. Must be at least `60` and a multiple of `60`. |
| `run_interval_thirty_seconds` | bool | `false` | Run every 30 seconds instead. Only valid together with `run_interval_seconds: 60`. |
| `timeout_ms` | int | required | Per-request timeout in milliseconds. Maximum `60000`. |
| `check_regions` | string[] | see [default locations](#default-locations) | Location ids the check runs from. Omitted or empty on create uses the [default locations](#default-locations). More than one requires a paid uptime plan. See [check locations](#check-locations). |
| `min_healthy_regions` | int | `1` | Minimum locations that must pass for the check to count as healthy. At least `1`, at most the number of `check_regions`. In a run where some locations return no result, it is capped at the number that did. |
| `confirmation_threshold` | int | `1` | Consecutive failed checks required before the monitor transitions to `failed` and alerts. `1` to `10`. See [requiring N failed checks](/uptime-monitoring/http-checks/how-to/confirmation-threshold/). |
| `recovery_period_runs` | int | `2` | Consecutive healthy checks before the all clear is sent and the incident resolves. `1` to `10`; `1` is immediate. Monitors created before this field existed have `1`. See [recovery and flapping](/uptime-monitoring/http-checks/how-to/recovery-and-flapping/). |
| `flap_hold` | bool | `true` | Hold short outages while the monitor flaps and send one notice instead. Monitors created before this field existed have `false`. See [recovery and flapping](/uptime-monitoring/http-checks/how-to/recovery-and-flapping/). |
| `follow_redirects` | bool | `true` | Follow HTTP redirects before evaluating the response. |
| `request_body` | string | none | Body sent with the request. |
| `content_type` | enum | none | `Content-Type` of the request body. See [content types](#content-types). |
| `auth_type` | enum | none | `basic`, `digest`, or `bearer`. |
| `auth_username` | string | none | Username for `basic` / `digest` auth. |
| `auth_password` | string | none | Password for `basic` / `digest` auth. |
| `auth_bearer_token` | string | none | Token for `bearer` auth. |
| `success_http_codes` | int[] | none | Status codes that force a success. Each must be a valid HTTP status code. |
| `failure_http_codes` | int[] | none | Status codes that force a failure. Each must be a valid HTTP status code. |
| `custom_http_headers` | map | none | Extra request headers as `{name: value}`. A secret header here is how you [allowlist our checks](/uptime-monitoring/http-checks/allowlisting/). |
| `keyword_search` | string | none | Text to search for in the response body. Maximum 1000 characters; an empty string is treated as unset. |
| `keyword_search_inverted` | bool | `false` | Invert the assertion: fail when the keyword IS found. |
| `keyword_search_case_sensitive` | bool | `false` | Match case-sensitively. |
| `keyword_search_regex` | bool | `false` | Interpret `keyword_search` as a regular expression. |
| `group_notification_ids` | uuid[] | default group | Notification groups to fire on state change. Maximum 10, no duplicates, must belong to your account. On create, omitting it (or sending `null`) attaches your account's [default group](/incident-management/notifications/default-routing/#the-default-notification-group); `[]` notifies no one. |
| `monitor_tls` | bool | `true` | Provision a paired [TLS check](/uptime-monitoring/ssl-tls-checks/overview/) for the URL's hostname. |
| `tls_port` | int | `443` | Port the TLS check connects to, 1 to 65535. Needs `monitor_tls`. See [TLS port](/uptime-monitoring/ssl-tls-checks/reference/#port). |
| `monitor_dns` | bool | `true` | Provision a paired [domain expiry check](/uptime-monitoring/dns-checks/overview/) for the URL's registrable domain. Silently skipped at create time, and rejected with `400` on update, when the host is on a shared platform suffix such as `*.vercel.app`. |
| `monitor_page_speed` | bool | `false` | Provision a paired page-speed (Lighthouse) check on a slower schedule. |
| `tags` | string[] | none | Free-form tags. Used for grouping and [maintenance-window](/incident-management/maintenance/overview/) matching. |
| `http_version` | enum | `auto` | Preferred HTTP version for the check transport. See [HTTP versions](#http-versions). |
| `state` | enum | `active` | Update only. `active` or `paused`. Paused checks stop running and alerting. |
| `final_uri` | string | none | Expected final URL after redirects. A mismatch fails the check. |

`PUT /http/job/{job_id}` takes the same fields, all optional; a request with no fields is rejected. Sending `check_regions: []` on update leaves regions unchanged. Include the current `auth_type`, `content_type`, and complete `custom_http_headers` map when changing other fields: omitting these fields clears them.

## Read-only fields

| Field | Type | Description |
|---|---|---|
| `id` | uuid | Check ID. |
| `account_id` | uuid | Owning account. |
| `current_status` | enum | See [status enum](#status-enum). |
| `last_run_at` | rfc3339 \| null | Most recent check execution. |
| `last_status_change_at` | rfc3339 \| null | When `current_status` last transitioned. |
| `created_at` | rfc3339 | When the check was created. |
| `tls_job_id` | uuid \| null | Paired TLS check, if `monitor_tls` is on. |
| `dns_job_id` | uuid \| null | Paired domain expiry check, if `monitor_dns` is on and the domain is registrable. |
| `page_speed_job_id` | uuid \| null | Paired page-speed check, if `monitor_page_speed` is on. |
| `group_notifications` | object[] \| null | Full notification-group objects resolved from `group_notification_ids`. |
| `tls_port` | int | Fetch one check only, when TLS monitoring is on. The port the TLS check uses. |
| `partial_failure` | object \| absent | Present while runs pass the quorum but some locations fail: `failed_locations` (location ids), `total_locations` and `since` (rfc3339). Never paged. |
| `not_checked_reason` | string \| null | Set only while an active check is not being run. `quota`: the account's uptime quota for this period is used up. See [not checked](#not-checked). |

The response also returns `service_id` as a UUID or `null`.

## Status enum

| Status | Meaning |
|---|---|
| `success` | The monitor is not in a confirmed failure. A monitor whose recent checks have failed but not yet met its `confirmation_threshold` stays `success`. |
| `failed` | Confirmed failure. Notifications fire and an incident opens. |
| `pending_failure` | Legacy value. Nothing sets it today; debouncing is handled by [`confirmation_threshold`](/uptime-monitoring/http-checks/how-to/confirmation-threshold/). Treat it as `success` if you encounter it on an old record. |

## Not checked

When an account uses up its uptime quota for the period and the plan stops checks at the limit, active checks are skipped until the quota resets or the plan is upgraded. While that lasts, `GET /http/job/{job_id}` and `GET /monitors` return `not_checked_reason: "quota"` for each active check, and the dashboard shows **Not checked: quota** instead of the last status. `current_status` keeps its last value, so do not read it as up. A paused check shows as paused, never as not checked. The first skipped run of each period records a `quota_not_checked` [monitor event](#monitor-events).

## Monitor events

`GET /monitors/{monitor_id}/events?kind=http|cron|browser&limit=25` lists things that happened to a monitor besides going down and recovering, newest first. `kind` defaults to `http`; `limit` is 1 to 100 (default 25).

| `kind` | Recorded when |
|---|---|
| `quota_not_checked` | The first run of a usage period was skipped because the quota is used up. `data` has `product` and `period`. |
| `schedule_missing` | A daily sweep found the monitor's schedule (or its TLS or domain check's schedule) missing or switched off. `data.repaired` says whether it was switched back on. The account owners are emailed. |
| `tls_unknown` | The TLS check could not connect for more than a day. The account owners are emailed. |
| `inconclusive_run` | One location of several answered, and it failed. The status did not change. `data` has `selected`, `reported` and `failed_locations`. |
| `degraded_quorum` | A second inconclusive run in a row took the monitor down on fewer locations. `data` has `transition_id` and `locations`. |
| `partial_failure` | A run passed while some locations failed, the first in a row. `data` has `failed_locations` and `total_locations`. |
| `recovery_pending` | The monitor recovered and the all clear waits for the recovery period. `data.runs_needed` is the period. |
| `recovery_reset` | A check failed during the recovery period, so the count restarted. |
| `recovery_confirmed` | The recovery period passed and the all clear went out. |
| `flap_started` | The monitor started flapping. `data` has `transitions` and `window_minutes`. |
| `flap_break_through` | A held outage lasted long enough to be sent. `data.break_through_minutes` is the limit. |
| `flap_ended` | The monitor was stable long enough to stop flapping. `data.held` counts the outages held. |

Returns `404` when the monitor is not in your account and `400` for an unknown `kind`. New event kinds may be added; ignore ones you do not know.

## Check locations

Location ids follow `<provider>-<region>`, for example `aws-us-east-1` or `gcp-asia-southeast1`. The live list, with each location's city, country and provider, is on the [locations page](https://siteqwality.com/locations/). From the API, call `GET /check-locations` (the location below is an example of the shape):

```json
{
  "default_location_id": "aws-us-east-1",
  "locations": [
    {
      "id": "gcp-asia-southeast1", "provider": "gcp", "provider_name": "Google Cloud",
      "provider_region": "asia-southeast1", "city": "Singapore", "country_code": "SG",
      "continent": "asia", "label": "Singapore · Google Cloud", "status": "live",
      "is_default": false, "capabilities": ["http"]
    }
  ]
}
```

The current fleet offers 24 HTTP locations. Discover ids through this endpoint rather than hardcoding a city list, and select only the locations you want each monitor to use.

Only locations with `status: "live"` and `"http"` in `capabilities` can be selected for an HTTP check. The list also carries `draining` and `retired` locations so older results keep a readable label: a `draining` location keeps serving monitors that already use it but cannot be newly selected, and a `retired` one no longer runs.

How `check_regions` is validated on create and update:

| You send | Result |
|---|---|
| A live location id | Accepted. |
| A retired id: `aws-us-east-2` or `aws-us-west-1` | Accepted and replaced with `aws-us-east-1`, its replacement. |
| An id that does not exist | `400` with `Invalid check_regions <value>`. |
| A location that cannot run this check type | `400`. |
| More than one location without a paid uptime plan | `403` with `multi_region_requires_paid_plan`. |

On every scheduled run, each selected location makes the request and returns its own result, recorded with that location's id in `check_region`. Each result counts as one check toward your monthly check volume. A location that cannot return a result in a run (its provider is unreachable, for example) is left out of that run: nothing is recorded for it, it is not billed, and the quorum is evaluated over the locations that did report. If a monitor has exactly one location and it cannot report, the executor attempts the default location when it is different and enough execution time remains. A returned result is recorded under the default's id. If no location returns a result, the monitor's status stays unchanged. With two or more locations, a run where only one answered and it failed is [inconclusive](/uptime-monitoring/http-checks/how-to/confirmation-threshold/#2-location-quorum): the status changes only if the next run is inconclusive too.

### Default locations

A create that leaves out `check_regions` (or sends `[]`) runs from `aws-us-east-1`. On a paid uptime plan it runs from two locations instead: `aws-us-east-1` plus a healthy location on another cloud provider in the same country (the same city first), with `min_healthy_regions: 1`, so you are alerted only when both fail. Nothing is stored as a preference: each create picks again, and an existing monitor never changes. A retention add-on on its own is not an uptime plan.

The pair is the default only while it fits: the account's projected monthly checks, the new monitor included, must stay within half of its monthly uptime check quota (the free allowance plus the uptime plan). Otherwise the default is one location. Choosing locations yourself is never refused by this rule.

`GET /check-locations/default` returns what a create would get, and the projection behind it. Pass the new monitor's `run_interval_seconds` (60 to 86400), and optionally `run_interval_thirty_seconds`, `monitor_tls` and `monitor_dns` (both default to `true`). An invalid interval returns `400`. API keys need `read:monitors`.

```json
{
  "check_regions": ["aws-us-east-1", "gcp-us-east4"],
  "min_healthy_regions": 1,
  "single_location_reason": null,
  "projection": {
    "checks_per_location_per_month": 43200,
    "paired_checks_per_month": 60,
    "monitor_checks_per_month": 86460,
    "account_checks_per_month": 120000,
    "quota": 600000,
    "pair_quota_percent": 50
  }
}
```

`single_location_reason` is `null` for the pair, or says why the default is one location: `plan` (no paid uptime plan), `quota` (the pair would pass half the quota) or `no_healthy_pair` (no healthy location on another provider in the default's country right now). The projection counts a 30-day month: one check per location per run, a 30-second monitor runs twice a minute, and the TLS and domain expiry checks paired with an HTTP monitor run daily (30 a month each). `account_checks_per_month` covers the account's active HTTP monitors on the locations each one runs from.

Outages list each failing location: `GET /http/job/{job_id}/events` returns `failed_locations`, `total_locations` and `degraded_quorum` on each outage, and `held_reason: "flap"` with `held_released_at` when its alert was held for flapping.

Checks do not come from fixed IP addresses. See [allowlisting our checks](/uptime-monitoring/http-checks/allowlisting/).

## HTTP versions

| Value | Behavior |
|---|---|
| `auto` | Prefer HTTP/2 via ALPN, fall back to HTTP/1.1 (default). |
| `http1_1` | Force HTTP/1.1 only. Best for some CDN / bot-management edges. |
| `http2` | Require HTTP/2; the check fails if it cannot be negotiated. |
| `http2_with_fallback` | Explicit prefer-h2-with-fallback. Same transport behavior as `auto` today. |

The negotiated version actually observed on each run is recorded on the check result.

## Response bodies

Every check records its outcome, status code and per-phase timings. The
**response body is kept only when a check fails**, which is when you need it to
tell a 500 from a blank page from a hijacked domain. A passing check's body is
not stored.

When a check fails, the result carries:

- `response_body`: the first 8 KB of the response, for display.
- `body_bytes`: the true size of the captured body. If it is larger than
  `response_body`, the inline copy is the head of a bigger document.
- `body_truncated`, `body_available`, `body_expired`: whether the snippet is
  partial, whether the stored body can be downloaded now, and whether one was
  captured but has aged out of your plan's window.

Call `GET /http/job/result/{job_result_id}/body` for a pre-signed URL to the
stored body, valid for one hour. The stored download contains at most the first 3 MiB of a failed response; it may be shorter than `body_bytes`, and `body_truncated` indicates truncation. It answers `404` when no body was captured
(a passing check) and `410` when one was captured but falls outside your
retention window.

A keyword assertion is evaluated against the live response while the check
runs, never against the stored copy, so a keyword failure always carries the
body that failed it even though the status code was `200`.

Keyword and JSON path assertions look at the first 10 MB of the response. A
keyword found there passes. When the response is larger and the first 10 MB
cannot decide the assertion (the keyword is not there, the keyword is inverted,
or any JSON path), the check fails with `failure_reason` `body_too_large`
instead of guessing. The rest of the response is still read, so a connection
that drops late still fails the check. The downloadable copy holds at most the
first 3 MB, while `body_bytes` reports the true size.

### How long a captured body stays readable

| Plan | Failure bodies readable for |
|---|---|
| Free | 5 days |
| Any paid uptime plan | 30 days |
| On request | Up to 365 days |

These are **read windows, not deletion schedules.** The window is evaluated at
the moment you ask for a body: past it, `GET /http/job/result/{id}/body`
answers `410` and the dashboard shows the body as expired. Upgrading therefore
makes older captured bodies readable again straight away, rather than only
affecting new checks, and downgrading closes off older ones without deleting
anything.

Do not read the table as a statement about when the stored object is destroyed.
Object deletion is handled separately by the storage lifecycle on a longer
schedule, and it is not the same number.
