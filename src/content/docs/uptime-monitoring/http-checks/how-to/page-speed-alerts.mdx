Turning on `monitor_page_speed` provisions a paired page-speed check that runs Google PageSpeed Insights against your URL every 6 hours. Beyond charting the scores, it alerts when the **Lighthouse performance score drops below a threshold**, and again when it recovers.

## Turn it on

Set `monitor_page_speed` on the HTTP check, either through **Monitor Page Speed** in the **Optional checks** section of the monitor form, or through the API, with an [API key](/getting-started/account-and-team/#generate-api-keys) exported as `SITEQWALITY_API_KEY` and `$JOB_ID` set to the check's `id`:

```bash
curl -X PUT https://api.siteqwality.com/http/job/$JOB_ID \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "monitor_page_speed": true }'
```

A **Page Speed Insights** tab appears on the monitor once the first result lands. Read the latest result with `GET /http/job/{job_id}/page_speed` and the series with `GET /http/job/{job_id}/page_speed/history`.

## What triggers an alert

Each monitor is either healthy or degraded, and only a change between the two alerts:

| State | Current score | Result |
|---|---|---|
| healthy | below the threshold | **Degraded** alert fires |
| degraded | at least 10 points above the threshold | **Recovered** alert fires |
| degraded | anywhere below that | nothing |
| healthy | at or above the threshold | nothing |

- A score sitting **exactly at** the threshold counts as healthy. The comparison is strictly "below".
- Recovery needs 10 points of headroom, capped at 100. Lighthouse scores move a few points between runs with nothing changed, so a page scoring around the threshold alerts once instead of on every run.
- A monitor that stays degraded does **not** re-alert every 6 hours. You get one alert on the way down and one on the way back up.

A new page-speed check starts healthy, so its first run alerts if the score is already below the threshold.

## The threshold

The threshold defaults to **50 out of 100**. Change it under **Alert below score** in the **Optional checks** section of the monitor form, or with `page_speed_alert_threshold` (a whole number from 1 to 100) on the HTTP check:

```bash
curl -X PUT https://api.siteqwality.com/http/job/$JOB_ID \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "page_speed_alert_threshold": 40 }'
```

With a threshold of 40, the monitor degrades below 40 and recovers at 50. The new threshold applies from the next run.

`GET /http/job/{job_id}/page_speed` returns it as `performanceThreshold` on Lighthouse's native `0.0` to `1.0` scale, so 40 reads `0.4`.

Only the **performance** category is compared. SEO, accessibility, and best-practices scores are collected and charted, but nothing alerts on them.

## Turn alerts off

To keep the scores and charts without the emails, clear **Alert on page speed** in the monitor form, or send `alert_on_page_speed: false`:

```bash
curl -X PUT https://api.siteqwality.com/http/job/$JOB_ID \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "alert_on_page_speed": false }'
```

The check keeps running every 6 hours. Turning alerts off on a degraded monitor marks it healthy, which resolves any page-speed incident it opened. Turned back on, it starts healthy, and the next run below the threshold alerts.

## Where the alert goes

Page-speed alerts fan out through the **parent HTTP monitor's notification groups**, over **email, SMS, Slack, webhook, Telegram, Discord, and Microsoft Teams** only.

PagerDuty, Jira Service Management (Opsgenie), Google Chat, Mattermost, Pushover, and Pushbullet channels are skipped (see [which alerts reach which channels](/integrations/coverage/)). If a monitor's group contains only those types, its page-speed alerts go nowhere: add an email or Slack channel to the group if you want page-speed coverage.

## What it does not do

A page-speed alert opens an incident only when the HTTP check belongs to a [service](/incident-management/services/overview/). It does **not**:

- record a state transition, so it never affects uptime percentage or SLA reports;
- appear on a status page;
- change the HTTP monitor's own status.

## Maintenance windows

Page-speed alerts are covered by the same [maintenance windows](/incident-management/maintenance/overview/) as the parent monitor, matched on the HTTP check's tags.

Inside a window, a degraded alert is **held** until the window ends and then released. If the score recovers before the window ends, the held alert is dropped and no recovery alert is sent either.

## Practical notes

- The 6 hour schedule is not configurable, so a regression can be up to 6 hours old before you hear about it.
- Rate limits and transient 5xx responses from Google's PageSpeed Insights API are retried on the next scheduled run rather than surfacing as a failure.
- Google gets **2 minutes** per run. If PageSpeed Insights has not returned a result by then, or Lighthouse cannot load the page, the run is skipped: the last scores stay in place, nothing alerts, and the next run tries again.
- There is no mobile or desktop toggle: Site Qwality sends no `strategy` parameter, so the analysis runs with Google's own default.
