A site that comes back for one check and fails again sends you an all clear and then a second outage alert a minute later. A site that bounces up and down every few minutes sends a pair of alerts every time. Two HTTP check settings deal with this:

- `recovery_period_runs` waits for several healthy checks before the all clear.
- Flap hold holds short outages while a monitor flaps and sends one notice instead. It is an account setting that each monitor can override.

New monitors get a recovery period of `2`. Monitors created before it shipped keep `recovery_period_runs: 1`, so nothing changes until you opt in. The monitor form offers the new default on those monitors. Flap hold is different: it follows the account's [notification settings](/incident-management/notifications/settings/), which have it on, so every monitor holds flaps unless it is set to never hold.

| Field | Type | Default for new monitors | Range |
|---|---|---|---|
| `recovery_period_runs` | int | `2` | `1` to `10`. `1` sends the all clear on the first healthy check. |
| `flap_hold_override` | bool \| null | `null` | `null` follows the account setting, `true` always holds, `false` never holds. |

`flap_hold` on a response is the value in effect, a read-only bool. See [turn flap hold on or off](#turn-flap-hold-on-or-off).

```bash
curl -X PUT https://api.siteqwality.com/http/job/$JOB_ID \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "recovery_period_runs": 2, "flap_hold_override": null }'
```

Out-of-range values are rejected with `400` and the message `recovery_period_runs must be between 1 and 10`. There is no plan gate.

## Recovery period

The monitor goes back to `success` on the first healthy check, as before. Uptime, SLA reports and the outage's recorded duration all use that first healthy check. What waits for the recovery period:

- the all clear notification on every channel;
- automatic resolution of the incident the outage opened.

A failed check inside the period resets the count. If the monitor goes back down before the all clear was due, nobody is told twice: the open incident stays open, and the outage alert that already went out still stands. When the all clear does go out, it gives the time of the last recovery.

A 60 second monitor with `recovery_period_runs: 2` sends the all clear one minute after the first healthy check.

## Flap hold

A monitor is flapping after **4 status changes within 30 minutes**. While it flaps:

- One **Flapping** notice goes out to the monitor's email, Slack, Microsoft Teams, Discord, Google Chat, Mattermost, Telegram and Pushbullet channels.
- Each new outage is held. If the monitor recovers within **5 minutes**, the held outage and its recovery are dropped together. If it is still down after 5 minutes, the held outage is sent to every channel, paging ones included, and the incident opens.
- Once the monitor has had no status change for **15 minutes**, a **Stable** summary says how many outages were held.

SMS, PagerDuty, Opsgenie and Pushover never get the Flapping or Stable notices, only outages that broke through. Webhooks get no flap notices today.

Held outages show on the monitor page with **Alert held while flapping**, and **then sent** once one broke through. The activity feed records when flapping started, each break-through and when it ended.

### Turn flap hold on or off

Flap hold applies to HTTP monitors for now. Whether a monitor holds depends on two things:

- The account setting `flap_hold`, under **Notifications**, **Settings**. It is on by default.
- The monitor's own `flap_hold_override`. In the monitor form, **Hold alerts while flapping** lets you follow the Notifications setting, always hold or never hold. `null` follows the account, `true` always holds and `false` never holds.

An override wins over the account setting. A monitor's `flap_hold` is the result: the override if it has one, otherwise the account setting, otherwise on. `PUT /http/job/{job_id}` takes `flap_hold_override` (leave it out to keep it, send `null` to follow the account), and a request that still sends `flap_hold` sets the override.

<Aside type="caution" title="Older monitors now hold flaps">
Monitors created before flap hold shipped used to have it off. They now follow the account setting, so they start holding flaps unless you set them to never hold. A monitor where flap hold was explicitly turned off after it shipped stays on never hold.
</Aside>
