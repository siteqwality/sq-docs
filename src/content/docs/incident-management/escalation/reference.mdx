The full request schemas live in the auto-generated [API Reference](/api-reference/). This page is the human-readable cheat sheet.

## Escalation policy

| Field | Type | Default | Description |
|---|---|---|---|
| `name` | string | required | Human label, shown in dashboards and per-incident views. |
| `repeat_count` | int | `3` | How many more times to run through the levels after the first pass, from `0` to `20`. See [repeat cycles](/incident-management/escalation/overview/#repeat-cycles). |

Deleting a policy needs an admin or an API key; other roles get `403`.

## Escalation level

| Field | Type | Default | Description |
|---|---|---|---|
| `level_number` | int | last | Position within the policy, from `1`. Lower runs first. Omit it to add the level last. A position inside the list inserts the level there and moves the levels at and below it down one. A position past the end (more than `N + 1` for `N` levels) or below `1` is a `400`. |
| `timeout_minutes` | int | required | How long to wait for any responder ack at this level before advancing, counted from when the level starts. The level advances within a few seconds of it. Whole minutes, from `1` to `1440` (one day). |
| `target_user_ids` | uuid[] | `[]` | Page these specific users. Each user's notification rules + contact methods determine the actual delivery. |
| `target_schedule_ids` | uuid[] | `[]` | Page whoever is on-call in these on-call schedules at firing time. |

A level with no resolvable targets pages nobody, but it still waits out its timeout and still advances.

## Levels are positions

A policy's levels are always numbered `1` to `N` with no gaps and no duplicates. Every change keeps it that way:

- **Adding** a level puts it at its `level_number` (last by default) and moves the levels at and below it down one.
- **Deleting** a level moves every level below it up one.
- **Reordering** rewrites every number in one go. See the [reorder endpoint](#reorder-endpoint).

An open incident follows its level, not the number. After a reorder it keeps waiting on the same level and moves on from that level's place in the new order.

Deleting the level an open incident is waiting on pages nobody straight away. When that level's timeout ends, the escalation continues at the level that took its place, and the incident records an `escalation_level_removed` event. If the deleted level was the last one, its timeout ends the pass: the next repeat starts at level 1, or the escalation is `exhausted` when no repeats remain.

## Step types: practical recipes

### Page the on-call rotation

```json
{ "timeout_minutes": 5, "target_schedule_ids": ["<primary>"] }
```

The most common first level. Resolves at firing time, so handoffs work transparently.

### Page a specific person

```json
{ "timeout_minutes": 10, "target_user_ids": ["<eng-manager>"] }
```

Use for fixed targets like "the engineering manager always gets paged at level 2."

### Page on-call + a backup person

```json
{
  "timeout_minutes": 5,
  "target_schedule_ids": ["<primary>"],
  "target_user_ids": ["<sre-lead>"]
}
```

Both fire in parallel. First ack from anyone wins.

### Page on-call + secondary on-call

```json
{
  "timeout_minutes": 10,
  "target_schedule_ids": ["<primary>", "<secondary>"]
}
```

Both schedules' current responders get paged. Useful when you want a second pair of eyes from level 1.

### Final-level "page everyone"

```json
{ "timeout_minutes": 30, "target_user_ids": ["<eng-mgr>", "<vp-eng>", "<cto>"] }
```

Reserve for `critical` incidents that have already burned through 30+ minutes without an ack. If you hit this regularly, fix the on-call rotation, not the escalation.

## Reorder endpoint

`PUT /escalation_policy/{policy_id}/level/reorder` accepts a `level_ids` array in the order you want and rewrites every level's `level_number` to match, in one transaction.

```json
{ "level_ids": ["<id-1>", "<id-2>", "<id-3>"] }
```

The array must name every level of the policy exactly once. A missing level, an extra or unknown id, or a repeated id is a `400` and changes nothing, so a list built before someone else added or deleted a level is refused rather than applied. Fetch the levels again and resend. A policy in another account is a `404`.

## How targets are paged

A level's targets are resolved and de-duplicated, then each user is paged through **their own** notification rules for the incident's urgency.

| Incident severity | Urgency used |
|---|---|
| `critical` | high |
| `major` | high |
| `minor` | low |

This mapping is fixed and cannot be overridden per policy. Every user starts with a high and a low rule on their sign-in email.

Contact methods are email, SMS and Slack DM; there are no phone calls. A rule is skipped when its method cannot page: an SMS number that is not verified, an email address that bounced permanently or reported spam, or SMS when the account has none left. Each skip is recorded on the incident as a `page_skipped` event with its reason. A user no rule can reach is paged at their sign-in email, recorded as `escalation_fallback_email`. See [readiness](/incident-management/escalation/readiness/) for the full definition.

## Readiness endpoint

`GET /escalation_policy/{policy_id}/readiness` reports, for each level and each urgency, whether the level reaches someone before it times out. `POST /escalation_policy/readiness` does the same for levels that are not saved yet. Both only read. See [check that a policy reaches someone](/incident-management/escalation/readiness/).

## Escalation state values

| Value | Meaning |
|---|---|
| `active` | Cycling through levels. |
| `acknowledged` | Acked or resolved. Paging stopped and pending schedules deleted. |
| `exhausted` | Repeat cycles are used up. Level cycling stopped, but a per-user delayed page that was already scheduled can still fire. |
