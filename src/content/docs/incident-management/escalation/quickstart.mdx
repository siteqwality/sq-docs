By the end of this guide you'll have an escalation policy that:

1. Pages the on-call rotation first; waits 5 minutes for ack.
2. If no ack: pages a secondary user; waits 10 minutes.
3. If still no ack: pages the engineering manager; waits 15 minutes.
4. Repeats once if no one ever acks.

You need the `Primary on-call` schedule from the [on-call quickstart](/incident-management/on-call/quickstart/), plus a secondary engineer and an engineering manager in the account.

Paging more than one person needs a responder pack, and the people in this guide take more seats than the free plan includes. See [plans and limits](/getting-started/plan-limits/#on-call-responders).

## 1. Create the policy

<Tabs syncKey="interface">
<TabItem label="Dashboard">

<Steps>

1. Go to **Respond → Escalation Policies** and click **New policy**.

2. Name: `Primary escalation`. **Times to repeat:** `1`. Leave **When nobody acknowledges** on **Email the account owners and admins**. Click **Create Policy**.

</Steps>

</TabItem>
<TabItem label="API">

With an [API key](/getting-started/account-and-team/#generate-api-keys) exported as `SITEQWALITY_API_KEY`:

```bash
curl -X POST https://api.siteqwality.com/escalation_policy \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "name": "Primary escalation", "repeat_count": 1 }'
```

Save the returned `id` as `POLICY_ID`.

</TabItem>
</Tabs>

## 2. Add the levels

<Tabs syncKey="interface">
<TabItem label="Dashboard">

<Steps>

1. Open the policy and click **Add level**.

2. Level 1: **Timeout (minutes)** `5`. Under **Target Schedules**, pick the `Primary on-call` schedule. Click **Add Level**.

3. **Add level** again. Level 2: **Timeout (minutes)** `10`. Under **Target Users**, pick the secondary engineer. Click **Add Level**.

4. **Add level** again. Level 3: **Timeout (minutes)** `15`. Under **Target Users**, pick the engineering manager. Click **Add Level**.

</Steps>

</TabItem>
<TabItem label="API">

`target_user_ids` takes user IDs, which `GET /account/info` lists. `SCHEDULE_ID` is the `id` of `Primary on-call` from `GET /on_call_schedule`.

```bash
# Level 1: page the on-call schedule
curl -X POST https://api.siteqwality.com/escalation_policy/$POLICY_ID/level \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "timeout_minutes": 5,
    "target_schedule_ids": ["'$SCHEDULE_ID'"]
  }'

# Level 2: page secondary user
curl -X POST https://api.siteqwality.com/escalation_policy/$POLICY_ID/level \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "timeout_minutes": 10,
    "target_user_ids": ["44444444-aaaa-4bbb-9ccc-bbbbbbbbbbbb"]
  }'

# Level 3: page eng manager
curl -X POST https://api.siteqwality.com/escalation_policy/$POLICY_ID/level \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "timeout_minutes": 15,
    "target_user_ids": ["55555555-aaaa-4bbb-9ccc-cccccccccccc"]
  }'
```

`level_number` is auto-assigned in creation order.

</TabItem>
</Tabs>

## 3. Check readiness

Readiness says whether every level reaches someone before it times out, for critical and major incidents and for minor ones. Fix anything it lists, such as a user whose only rule is an unverified SMS number. See [check readiness](/incident-management/escalation/readiness/).

<Tabs syncKey="interface">
<TabItem label="Dashboard">

Open the policy. The **Readiness** panel at the top gives the verdict and lists every problem.

</TabItem>
<TabItem label="API">

```bash
curl https://api.siteqwality.com/escalation_policy/$POLICY_ID/readiness \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY"
```

`"ready": true` means every level reaches someone at both urgencies.

</TabItem>
</Tabs>

## 4. Test it

Attach the policy to a [service](/incident-management/services/overview/), [open a manual incident](/incident-management/incidents/how-to/manual-incidents/) on that service, and don't ack it. The on-call is paged first, then each later level as the one before it times out (after 5 minutes, then 10 more).

To test faster, use a temporary policy with 1-minute timeouts.
