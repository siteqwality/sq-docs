## Service fields

| Field | Type | Default | Notes |
|---|---|---|---|
| `id` | UUID | | Read-only. |
| `name` | string | | Required. |
| `description` | string | none | `null` on update clears it. |
| `escalation_policy_id` | UUID | none | Who the service's incidents page. Without one, nobody is paged. Must be a policy in your account (`404` otherwise). `null` on update clears it. |
| `incident_creation_mode` | `manual`, `auto` | `manual` | `auto_with_confirmation` is still accepted on input and treated as `auto`, but is never returned. |
| `reopen_window_minutes` | integer | `30` for new services | `0` to `1440`. A monitor that fails again within this many minutes of the last alert of a resolved auto-created incident reopens it instead of opening a new one. `0` never reopens. See [reopen window](/incident-management/services/overview/#reopen-window). |
| `auto_resolve` | `always`, `unless_acknowledged`, `never` | `unless_acknowledged` | Whether an auto-created incident resolves itself when all its monitors recover. `unless_acknowledged` leaves an acknowledged incident for a person to resolve. See [auto-resolve](/incident-management/services/overview/#auto-resolve). |
| `incident_merge_window_minutes` | integer | none | Deprecated and ignored. While an auto-created incident is open, every failing monitor of the service joins it. |
| `default_incident_severity` | `minor`, `major`, `critical` | `minor` | Severity of incidents the service opens automatically, and of manual incidents opened on it without a `severity`. |
| `auto_publish_to_status_page_id` | UUID | none | Puts automatic incidents on this status page and emails its subscribers. `null` on update clears it. |
| `public_incident_template` | object | none | `{ "title", "message", "resolved_message" }`, each optional: the public title, first public update and resolved update for this service's incidents on a status page. Values are trimmed and blank ones dropped. The title is at most 512 characters and each message 5,000 (`400` otherwise). Leaving it out keeps it; `null` clears it. Omitted from responses when empty. |
| `owner_team` | string | none | The owning team, at most 256 characters. Trimmed; blank stores none. `null` on update clears it. |
| `tags` | string array | `[]` | Up to 20 labels of 256 characters; blanks and repeats are dropped. An update replaces the list; `[]` clears it. |
| `on_call_schedule_id` | UUID | none | The [on-call schedule](/incident-management/on-call/overview/) shown as on call for this service. Without one, the first level of the escalation policy is. Must be a schedule in your account (`404` otherwise). `null` on update clears it. |
| `disabled` | boolean | | Write-only, on update. `true` switches the service off: its monitors open no automatic incidents, and incidents you open by hand still work. `false` switches it back on. |
| `disabled_at` | RFC 3339 | none | Read-only. When the service was switched off; omitted while it is on. |
| `monitor_count` | integer | | Read-only. Linked monitors of every type. |
| `health` | object | | Read-only, on `GET /service` and `GET /service/{id}`. See [health](#health). |
| `created_at` | RFC 3339 | | Read-only. |

## Endpoints

| Method | Path | What it does |
|---|---|---|
| `GET` | `/service` | List services with their health. See [listing services](#listing-services). |
| `POST` | `/service` | Create a service. `409` with code `service_limit_reached` at 100 services. |
| `GET` | `/service/{id}` | Fetch one service. |
| `GET` | `/service/{id}/metrics` | Incidents, MTTA, MTTR and uptime. See [metrics](#metrics). |
| `PUT` | `/service/{id}` | Update the fields you send. |
| `DELETE` | `/service/{id}` | Delete the service and its broadcast targets, and unlink its monitors. Needs an admin, or an API key with `write:services`: other roles get `403`. |
| `GET` | `/service/{id}/monitors` | List linked monitors of every type as `{ id, name, monitor_type, status, healthy, paused }`. |
| `POST` | `/service/{id}/monitors` | Link monitors. See [linking monitors](#linking-monitors). |
| `DELETE` | `/service/{id}/monitors/{monitor_type}/{monitor_id}` | Unlink one monitor. `204`; `404` when it is not on this service. |
| `PUT` | `/service/{id}/monitors` | Deprecated. Replaces the HTTP and heartbeat links with `{ "http_job_ids": [...], "cron_job_ids": [...] }`; other types are untouched. |
| `GET` | `/service/{id}/notification_target` | List broadcast targets. |
| `POST` | `/service/{id}/notification_target` | Add a broadcast target. |
| `PUT` | `/service/{id}/notification_target/{target_id}` | Change a target's `min_severity` and `events`, or a Slack target's `channel`. `null` resets a filter; omitted fields keep their value. `400` for an unknown or empty event list, `404` when the target is not on the service. |
| `DELETE` | `/service/{id}/notification_target/{target_id}` | Remove a broadcast target. |

<Aside type="note" title="Scopes">
Scoped API keys, M2M API clients and AI assistants need `read:services` for the `GET` routes and `write:services` for the rest.
</Aside>

## Listing services

`GET /service` answers `{ "data": [...], "total": N, "next_cursor": "..." }`. `data` is the page of services, `total` counts every service matching the filters, and `next_cursor` is `null` on the last page.

| Parameter | Notes |
|---|---|
| `limit` | 1 to 100, default 50. Larger values are clamped. |
| `cursor` | `next_cursor` from the previous page. Send the same filters and `sort` with it. |
| `q` | Text in the name, description or team, case-insensitive. |
| `team` | Only services of this team, case-insensitive. |
| `tag` | Only services with this tag, case-insensitive. |
| `status` | Comma-separated health: `operational`, `degraded`, `partial_outage`, `major_outage`. |
| `sort` | `-created_at` (default, newest first), `created_at`, `name`, `-name`, `status` (worst health first, then name) or `-last_incident_at` (latest incident first, services without one last). |
| `offset` | Deprecated. Rows to skip; cannot be combined with `cursor`. |

An unknown `sort` or `status`, a cursor this endpoint did not return for that sort, or `cursor` with `offset` returns `400`.

```bash
curl "https://api.siteqwality.com/service?status=major_outage,partial_outage&sort=status&limit=20" \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY"
```

### Health

| Field | Notes |
|---|---|
| `status` | `major_outage` (an open critical incident, or every active monitor failing), `partial_outage` (an open major incident, or some monitors failing), `degraded` (an open minor incident) or `operational`. Paused monitors and merged incidents do not count. |
| `in_maintenance` | `true` while a maintenance window naming the service in its `service_ids` runs and its end is in the future. It never changes `status`. |
| `open_incident_count` | Open incidents on the service, merged ones left out. |
| `failing_monitor_count` | Linked monitors failing now, paused ones left out. |
| `last_incident_at` | When the newest incident on the service opened, or `null`. |
| `on_call_now` | Who is on call: from `on_call_schedule_id` when set, otherwise every user and schedule on the first level of the escalation policy. Each entry has `user_id`, `user_name`, and for a schedule `schedule_id`, `schedule_name` and `until` (the next handoff). A schedule with nobody on call adds no entry. |

## Metrics

`GET /service/{id}/metrics` takes optional `from` and `to` (RFC 3339; default the 30 days up to now, at most 366 days) and answers:

| Field | Notes |
|---|---|
| `total_incidents`, `open_incidents`, `resolved_incidents`, `acknowledged_incidents` | Incidents opened on the service in the window, merged ones left out. |
| `mtta`, `mttr` | `{ samples, mean_seconds, p50_seconds, p90_seconds }`, the same measures as [`GET /incident/metrics`](/incident-management/incidents/reference/). Empty samples are `null`. |
| `uptime` | `{ percentage, incident_seconds, measured_seconds }`: the share of the window with no open incident on the service. Only time after the service was created and before now is measured; `percentage` is `null` when none is. |

`400` for a bad range, `404` when the service is not in your account.

```bash
curl "https://api.siteqwality.com/service/$SERVICE_ID/metrics" \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY"
```

## Linking monitors

`POST /service/{id}/monitors` adds monitors and leaves the service's other monitors alone. Linking a monitor that is already on the service does nothing.

```bash
curl -X POST https://api.siteqwality.com/service/$SERVICE_ID/monitors \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "monitors": [
        { "monitor_type": "http", "monitor_id": "<http-monitor-id>" },
        { "monitor_type": "tls", "monitor_id": "<tls-check-id>" }
      ] }'
```

| Field | Notes |
|---|---|
| `monitors` | One or more `{ "monitor_type", "monitor_id" }`. `monitor_type` is `http`, `cron`, `browser`, `tls`, `dns`, `dns_record` or `page_speed`. |
| `move` | `true` moves monitors that belong to another service. Default `false`. |

It answers with the service's monitors, like `GET`. Nothing is linked when any monitor fails:

| Status | When |
|---|---|
| `400` | `monitors` is empty, or a type is unknown or `alert_rule` (alert rules link in their own settings). |
| `404` | The service, or a monitor of that type, is not in your account. |
| `409` | A monitor belongs to another service and `move` is not `true`. Code `monitor_in_other_service`; `data.conflicts` lists each `{ monitor_type, monitor_id, service_id }`. |

`DELETE /service/{id}/monitors/{monitor_type}/{monitor_id}` unlinks one monitor and returns `204`, `400` for an unknown type, and `404` when the service is not yours or the monitor is not on it.

Monitors also take a `service_id` when you create or update them: `POST /http/job`, `PUT /http/job/{id}`, `POST /cron/job`, `PUT /cron/job/{id}`, `POST /browser_check`, `PUT /browser_check/{id}`, `POST /dns/record-monitor` and `PUT /dns/record-monitor/{id}`. On an update, `null` unlinks and leaving it out keeps it. A service ID that is not in your account returns `404` before anything changes.

## Broadcast targets

Create one with `type` and `details`:

| `type` | `details` | Notes |
|---|---|---|
| `email` | `{ "email": "oncall@example.com" }` | Any address. One outside your members' email domains returns `409` with code `email_target_confirmation_required` and the address in `data.email`, until you send `"confirm_external_recipients": true` beside `type` and `details`. |
| `slack_channel` | `{ "channel": "C0123456" }` with `integration_id` | Sends with a connected [Slack integration](/integrations/slack/). Nothing secret is stored on the target. |
| `slack_channel` | `{ "slack_token": "xoxb-...", "channel": "#incidents" }` | A Slack bot token you supply. The token is write-only: it reads back as `"has_token": true`. |
| `webhook` | `{}` with `integration_id` | Sends with a connected [webhook integration](/integrations/webhooks/): signed with its secret, with its settings, and listed in its delivery log. |
| `webhook` | `{ "url": "https://hooks.example.com/incidents" }` | Must be a public URL. It reads back as its scheme and host only, such as `https://hooks.example.com/****`. Uses the [webhook envelope](/integrations/webhooks/#incident-webhooks) and retry schedule, and is signed with a secret of its own that the create response returns once as `signing_secret`. |

Every target also takes these optional fields:

| Field | Notes |
|---|---|
| `integration_id` | A Slack integration for `slack_channel`, a webhook integration for `webhook`. `404` when it is not in your account; `400` for another kind of integration, for a token or URL sent beside it, or for a Slack target without a `channel`. If the integration is deleted later, the target sends nothing, and an integration that is switched off records each skipped delivery. |
| `min_severity` | `minor`, `major` or `critical`. Incidents below it are not sent. It is compared with the highest severity the incident has reached. Omitted means every severity. |
| `events` | Any of `incident_opened`, `incident_acknowledged`, `incident_updated`, `incident_resolved`, `incident_reopened`, `incident_merged`, `incident_service_changed`. Omitted means every event; an empty list or an unknown name is a `400`. |

A filtered-out event leaves no trace on the target: nothing is sent and nothing is recorded.

A service can have up to 20 targets; the 21st returns `409` with code `service_target_limit_reached`.

```bash
curl -X POST https://api.siteqwality.com/service/$SERVICE_ID/notification_target \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "type": "webhook", "details": { "url": "https://hooks.example.com/incidents" } }'
```

### When targets are told

Every lifecycle event below is sent to the service's broadcast targets. The last column is what the Slack, email and webhook targets deliver today:

| Event | Happens when | Delivered today |
|---|---|---|
| Opened | An incident opens on the service, automatically or by hand. | Yes |
| Resolved | An incident on the service resolves. | Yes |
| Acknowledged | A responder acknowledges it. | Recorded |
| Updated | An update is posted, or the severity or title changes. | Recorded |
| Reopened | A resolved incident reopens. | Recorded |
| Merged | An incident is merged into another. | Recorded |
| Service changed | An incident moves to another service. | Recorded |

A recorded event starts delivering as each channel's message for it ships. A monitor recovering while the incident stays open sends nothing, and an incident merged into another sends no resolved message. An update posted as an internal note is marked internal on its event. Status page subscribers only ever get public updates.

## Automatic incidents

| Behavior | Value |
|---|---|
| Sources | Linked monitors of every type. See [what fails and recovers](/incident-management/services/overview/#auto-created-incidents) for each. |
| Title | `<monitor name> is down` |
| Severity | `default_incident_severity` |
| Skipped when | The service is `manual` or switched off (`disabled_at` set). |
| Waits when | A maintenance window covers the monitor by tag or by service. It opens when the window ends if the monitor is still failing, and never opens if it recovers first. |
| One open incident | The service has at most one open auto-created incident. Every failing monitor joins it, recorded as a `monitor_joined` timeline event. |
| Reopened when | A monitor fails again within `reopen_window_minutes` of the last alert of the resolved incident. |
| Resolved when | Every monitor on the incident is healthy again (`healthy` in the monitor list), and `auto_resolve` allows it. |
| Paged | Right after the incident is recorded. If that is interrupted, a sweep pages it within about a minute. |
