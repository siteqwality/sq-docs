An incident's `monitors` list says which monitors it is about. A monitor joins on its own when it fails on an auto-created incident, or you add it by hand. Each entry also carries an **impact**, which is how a [status page](/status-pages/overview/) describes that part of your service during the incident. Every field is in the [incident reference](/incident-management/incidents/reference/#incident-monitor).

## Auto and manual

On an [auto-created incident](/incident-management/services/overview/#auto-created-incidents), every failing monitor of the service joins the open incident with `source: "auto"`, and the incident's timeline records a `monitor_joined` event. Each entry's `joined_at` and `recovered_at` show how an outage spread and healed monitor by monitor.

You add monitors by hand with `source: "manual"`, which is how a manual incident names what it affects.

## Impact and status pages

A status page marks the components behind an incident's monitors. Set a monitor's `impact` to choose what its component shows:

| `impact` | What it means |
|---|---|
| `degraded` | Working, but worse than normal. |
| `partial_outage` | Partly down. |
| `major_outage` | Down. |
| `null` | Not set. Derived from the incident's severity. |

## Add, change and remove monitors

In the dashboard, open the incident and use its **Monitors** section:

- **Add:** click **Add monitor**, pick an HTTP check, heartbeat or browser check and its impact, then click **Add**.
- **Change the impact:** pick a new value in the monitor's **Impact** column. **From severity** goes back to deriving it from the incident's severity.
- **Remove:** open the monitor's row actions and choose **Remove**.

Through the API, add a monitor with an optional impact. Adding one that is already linked changes nothing:

```bash
curl -X POST https://api.siteqwality.com/incident/$INCIDENT_ID/monitors \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "monitor_id": "<monitor-id>", "monitor_type": "http", "impact": "partial_outage" }'
```

Change the impact (send `null` to go back to deriving it from severity), or remove the monitor:

```bash
curl -X PUT https://api.siteqwality.com/incident/$INCIDENT_ID/monitors/http/$MONITOR_ID \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "impact": "major_outage" }'

curl -X DELETE https://api.siteqwality.com/incident/$INCIDENT_ID/monitors/http/$MONITOR_ID \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY"
```

You can also name monitors when you create the incident, with `monitors` on `POST /incident`:

```json
{
  "monitors": [
    { "monitor_id": "<monitor-id>", "monitor_type": "http", "impact": "degraded" },
    { "monitor_id": "<heartbeat-id>", "monitor_type": "cron" }
  ]
}
```

`affected_http_job_ids`, the older list of HTTP monitors, is deprecated: use `monitors`.
