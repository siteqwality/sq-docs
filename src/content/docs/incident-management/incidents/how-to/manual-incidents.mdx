Most incidents are auto-created by monitors. Sometimes they aren't, and you want one anyway. This page covers the patterns where manual creation is the right move, and the cleanest way to do it.

<Aside type="tip" title="Manual incidents page exactly like automatic ones">
Choose a **Service** when you report the incident (`service_id` in the API) and it runs the service's escalation policy: same levels, same timeouts, same repeat cycles, same one-click acknowledgement. See [making it page someone](#making-it-page-someone).
</Aside>

## When to create one manually

- **A third-party dependency broke something user-visible.** Stripe is degraded, AWS is throttling, your CDN is intermittently 502-ing. Your monitors might be showing a partial signal, but you have first-hand evidence.
- **A bug surfaced in production that no monitor catches.** UI broken for a specific browser, auth flow broken only for SSO users.
- **Coordinating a multi-team outage.** One canonical incident beats five Slack threads.
- **Pre-announced maintenance went sideways.** A deploy you'd protected with a [maintenance window](/incident-management/maintenance/overview/) actually broke something. The maintenance window suppressed the auto-incident, so create one manually.

## When *not* to

- Don't manually create an incident for an outage a monitor will catch in 60 seconds anyway. The auto-incident will be cleaner, since it has fewer race conditions with `responder_status` and the monitor list.
- Don't create an incident as a stand-in for a Slack message. If you don't intend to publish it on a status page or trigger paging, just message the team directly.

## Two flavors of manual incident

### Standalone incident (no status page)

Use this for internal-only tracking. Useful if you want the timeline + paging behavior without publishing.

In the dashboard, go to **Respond → Incidents** and click **Report incident**. Give it a **Title**, a **Severity** and an **Initial Message**, then click **Report Incident**.

Through the API:

```bash
curl -X POST https://api.siteqwality.com/incident \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Stripe webhooks intermittently failing",
    "severity": "major",
    "message": "Seeing ~5% failure rate on inbound Stripe webhooks. Investigating."
  }'
```

### Status-page incident (published)

Use this when the outage affects customers and they should know.

In the dashboard, go to **Manage → Status Page** and open the page. On its **Incidents** tab, click **Report Incident**, fill in the **Title**, **Severity** and **Initial Update**, optionally pick the **Affected Monitors**, and click **Report Incident**.

Through the API:

```bash
curl -X POST https://api.siteqwality.com/status_page/$STATUS_PAGE_ID/incident \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "status_page_id": "<status-page-id>",
    "title": "Some webhook deliveries delayed",
    "severity": "minor",
    "message": "We are seeing increased latency on outbound webhooks. Investigating with our delivery provider.",
    "affected_http_job_ids": []
  }'
```

The incident appears immediately on the public page.

## Publish later, and keep notes internal

An incident you started without a page can go on one later. In the dashboard, open it and click **Publish to status page**: pick the page, check the public title and the first public update customers will read, and choose whether to email the page's subscribers. The same panel lists the pages it is on, each with **Unpublish**. Through the API:

```bash
curl -X POST https://api.siteqwality.com/incident/$INCIDENT_ID/publish \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "status_page_id": "<status-page-id>",
    "title": "Webhook deliveries delayed",
    "message": "Some webhooks are arriving late. We are working with our delivery provider."
  }'
```

`DELETE /incident/$INCIDENT_ID/publish/<status-page-id>` takes it off the page again.

The page shows the public title and public updates only. On an incident's own page in the dashboard, updates are **internal notes** unless you switch the composer to **Public update**, so "failing over db-7" stays with your team. An update posted through the API is public unless you send `"visibility": "internal"`. See [public and internal updates](/incident-management/incidents/reference/#public-and-internal-updates).

## Linking to affected monitors

Even on manual incidents, name the monitors if monitors *do* exist for the broken thing. This makes the incident appear as a banner on the matching status-page components, and groups it correctly in dashboards.

In the dashboard, open the incident and click **Add monitor** under **Monitors**. Pick the monitor and its impact (**From severity**, **Degraded**, **Partial outage** or **Major outage**), then click **Add**.

Through the API, send `monitors` on the create request. Each entry takes an optional `impact` (`degraded`, `partial_outage` or `major_outage`):

```json
{
  "monitors": [
    { "monitor_id": "a3c1f5e0-1234-4abc-9def-aaaaaaaaaaaa", "monitor_type": "http", "impact": "major_outage" },
    { "monitor_id": "b7d2e601-5678-4def-9abc-bbbbbbbbbbbb", "monitor_type": "http" }
  ]
}
```

The older `affected_http_job_ids` list is deprecated but still accepted. You can add, re-grade and remove monitors after creation too: see [affected monitors and impact](/incident-management/incidents/how-to/affected-monitors/).

## Making it page someone

A manual incident only pages when it has a service, and that [service](/getting-started/concepts/) has an escalation policy attached. In the dashboard, pick the **Service** in the **Report incident** form. Through the API, send `service_id` at creation:

```bash
curl -X POST https://api.siteqwality.com/incident \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Stripe webhooks intermittently failing",
    "severity": "major",
    "message": "Seeing ~5% failure rate on inbound Stripe webhooks. Investigating.",
    "service_id": "<service-id>"
  }'
```

From there it behaves exactly like a monitor-opened incident: level 1 of the service's policy fires immediately, the timeout is scheduled, and acknowledging (from the dashboard, the API, or a paged responder's [email or SMS link](/incident-management/incidents/how-to/one-click-actions/)) cancels the escalation.

The service's broadcast targets, if it has any, are also notified.

<Aside type="caution" title="Silent no-paging is the common mistake">
Two situations produce an incident that pages nobody:

- **No service** (no `service_id`). The incident is created and nothing else happens.
- **The service has no escalation policy.** Broadcast targets still fire, but nobody is paged.

A service ID from another account is refused with `404`.

If a manual incident did not page, check the service first.
</Aside>

## Move an incident to another service

Filed it under the wrong service? Open the incident, click **Edit**, pick the right **Service** (or **None**) and click **Save Changes**.

Through the API, send `service_id` on `PUT /incident/{incident_id}`: a service id moves the incident there (`404` if it is not in your account), `null` detaches it from any service, and leaving it out keeps it as it is.

```bash
curl -X PUT https://api.siteqwality.com/incident/$INCIDENT_ID \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "service_id": "<new-service-id>" }'
```

Moving an open incident cancels the old service's escalation and starts the new service's [escalation policy](/incident-management/escalation/overview/) at level one. The new policy only starts while the incident is still `triggered`: an acknowledged incident does not start paging again. The move is recorded as a service-changed [broadcast event](/incident-management/services/overview/#broadcast-targets).

An auto-created incident cannot move onto a service that already has an open auto-created incident: the request returns `409` with `data.conflict` set to `open_auto_incident_exists`. Merge the two incidents instead, see [merge incidents](/incident-management/incidents/how-to/merge-incidents/).

## Severity guidance for manual incidents

| Use case | Severity |
|---|---|
| Documentation site down | `minor` |
| Login broken for a subset of users | `major` |
| Full outage, billing affected, security event | `critical` |

Severity drives display order, color, and filters. It also picks the **urgency** used when paging: `critical` and `major` page at high urgency, `minor` at low. Each targeted responder's own [notification rules](/incident-management/notifications/overview/#notification-rules) for that urgency decide which of their contact methods fire, so a `minor` incident can legitimately reach a different set of devices than a `critical` one. Raising a `minor` incident to `major` or `critical` pages the current escalation level again.

## Following up

After resolving, especially for `major` and `critical` incidents, open the incident's **Post-incident** tab:

- Start a postmortem. It is drafted from the incident's timeline, so you only write the analysis.
- Add action items with an owner and a due date. Owners get one email if an item is still open after its due date, and every open item shows on the **Follow-ups** tab of the Incidents page.

See [write a postmortem and track follow-ups](/incident-management/incidents/how-to/postmortems/).

<Aside type="tip">
The full update history is preserved on the incident object. `GET /incident/{id}` returns it sorted chronologically.
</Aside>
