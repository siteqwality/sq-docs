## Public and internal updates

A **public** update shows on every status page the incident is published on and can move its `status`. An **internal** note stays in the app: it never reaches a status page or its subscribers, and it never changes `status`. Status pages show the `public_title` (or `title` when it is empty) and public updates only.

Account members with incident write access can edit or delete an internal note from its timeline entry, including after resolution. Public updates stay in the timeline; post a correction instead. Notes on merged source incidents are read-only.

`PUT /incident/{incident_id}/update/{update_id}` accepts only `{ "message": "Updated note" }` and returns the note. It preserves the original author and posting time. Empty messages return `400`. `DELETE` at the same path returns `204` with no body. Either route returns `404` for a missing, foreign or public update, `403` without incident write access, and `409` for a merged incident. These actions do not change incident status or notify subscribers. The timeline event records who edited or deleted the note.

Resolving a published incident always posts a public `resolved` update, so its page never shows an incident as open after you resolved it. The text is the one you give, else the service's [public template](/incident-management/services/overview/#publish-incidents-to-a-status-page), else "This incident has been resolved."

## Status enum

| Value | Meaning |
|---|---|
| `investigating` | Cause not yet known. |
| `identified` | Cause known, fix in progress. |
| `monitoring` | Fix rolled out, watching. |
| `resolved` | Done. The only non-active status. |

## Responder status enum

| Value | Meaning |
|---|---|
| `triggered` | No one has claimed the incident. Escalation keeps paging. |
| `acknowledged` | A responder owns it. Escalation stops. |
| `resolved` | Responder work is done. |

## Request bodies

### Create (`POST /incident` or `POST /status_page/{id}/incident`)

| Field | Type | Required | Description |
|---|---|---|---|
| `title` | string | yes | Incident title. |
| `severity` | enum | yes | `minor` / `major` / `critical`. |
| `message` | string | yes | Text of the first incident update. |
| `status_page_id` | uuid | no | Publish to a status page at creation. |
| `monitors` | object[] | no | Affected monitors: `{ "monitor_id", "monitor_type", "impact" }`, with `impact` optional. |
| `affected_http_job_ids` | uuid[] | no | Deprecated: affected HTTP monitors. Use `monitors`. Sending both is fine, and duplicates are accepted. |
| `service_id` | uuid | no | Service tag. |

### Update (`PUT /incident/{incident_id}`)

Every field is optional. Send only what changes:

| Field | Type | Description |
|---|---|---|
| `title` | string | New title. |
| `severity` | enum | New severity. Raising it from `minor` to `major` or `critical` pages the current escalation level again, and an acknowledged incident goes back to `triggered`. |
| `service_id` | uuid \| null | Move the incident to this service (`404` if it is not in your account). `null` detaches it. Leaving it out keeps the current service. Moving an open incident cancels the old service's escalation and starts the new service's policy at level one, only while the incident is `triggered`. |
| `status` | enum | Deprecated: post an update, or resolve. `resolved` resolves the incident with a public update; another value sets the status. |
| `resolved_at` | rfc3339 | Deprecated and ignored: resolving records the time. |
| `public_title` | string \| null | The title status pages show, up to 512 characters (`400` if longer). `null` or blank clears it. |

### Post an update (`POST /incident/{incident_id}/update`)

| Field | Type | Description |
|---|---|---|
| `message` | string | Update text. |
| `visibility` | enum | `public` (default) or `internal`. |
| `status` | enum | Optional, public updates only. The new status; leaving it out keeps the current one. `resolved` resolves the incident, and a status earlier than the current one returns `409` unless `force` is `true`. On an internal note it is ignored, and `resolved` returns `400`. |
| `force` | bool | Allow a public update to move the status backward. |
| `notify_subscribers` | bool | Email the subscribers of every status page the incident is on about a public update. Default `false` here, and `true` on `POST /status_page/{status_page_id}/incident/{incident_id}/update`, which emails only that page. |

### Acknowledge (`POST /incident/{incident_id}/acknowledge`)

| Field | Type | Description |
|---|---|---|
| `acknowledged_by` | uuid | Optional when authenticated as a user (defaults to you). Required when calling with an API key. |

### Resolve (`POST /incident/{incident_id}/resolve`)

Every field is optional:

| Field | Type | Description |
|---|---|---|
| `message` | string | Text of the public `resolved` update. |
| `post_public_update` | bool | Post that update even when the incident is on no status page. A published incident always gets one. |
| `notify_subscribers` | bool | Email the subscribers of every page the incident is on. Default `true`. |

### Merge (`POST /incident/{incident_id}/merge`)

`{incident_id}` is the target. See [merge incidents](/incident-management/incidents/how-to/merge-incidents/).

| Field | Type | Required | Description |
|---|---|---|---|
| `source_ids` | uuid[] | yes | The incidents to merge into the target, 1 to 20. |

Returns the target incident. `400` for an empty list or more than 20 ids, and `404` when the target or any source is not in your account. A merge is all or nothing: a `409` changes nothing, and its `data.incident_id` names the incident it refused.

### Participants

| Method | Path | Body | Returns |
|---|---|---|---|
| `GET` | `/incident/{incident_id}/participants` | none | The participant list. |
| `POST` | `/incident/{incident_id}/participants` | Exactly one of `user_id`, `schedule_id` or `escalation_policy_id`, plus optional `role` (default `responder`) and `page` (default `true`). | The full participant list. |
| `PUT` | `/incident/{incident_id}/participants/{user_id}` | `{ "role": "lead" \| "responder" \| "comms" }` | The full list. Making someone `lead` demotes the previous lead to `responder`. |
| `DELETE` | `/incident/{incident_id}/participants/{user_id}` | none | `204`. |

A schedule adds whoever is on call now. A policy adds the users and on-call people at its first level. With `page` true, each added user is paged through their own notification rules. Paging an incident without a service returns `400`, and paging a resolved one returns `409` (`resolved`); send `"page": false` there. A `lead` must be sent as `user_id`. The first user to acknowledge becomes `lead` when there is none.

### Monitors

| Method | Path | Body | Returns |
|---|---|---|---|
| `POST` | `/incident/{incident_id}/monitors` | `{ "monitor_id", "monitor_type", "impact" }`, with `impact` optional. | The full monitor list. Adding one that is already linked changes nothing and returns `200`. |
| `PUT` | `/incident/{incident_id}/monitors/{monitor_type}/{monitor_id}` | `{ "impact": null \| "degraded" \| "partial_outage" \| "major_outage" }` | The full list. |
| `DELETE` | `/incident/{incident_id}/monitors/{monitor_type}/{monitor_id}` | none | `204`. |

### Postmortem

| Method | Path | Body | Returns |
|---|---|---|---|
| `GET` | `/incident/{incident_id}/postmortem` | none | The postmortem, or `404` when there is none. |
| `POST` | `/incident/{incident_id}/postmortem` | Optional `body` and `owner_user_id`. Without `body` it is drafted from the timeline. | `201` and the new `draft`. |
| `PUT` | `/incident/{incident_id}/postmortem` | Any of `body`, `status`, `owner_user_id` (`null` clears it). | The postmortem. |
| `DELETE` | `/incident/{incident_id}/postmortem` | none | `204`. The action items stay. |

### Action items

| Method | Path | Body | Returns |
|---|---|---|---|
| `GET` | `/incident/{incident_id}/action_items` | none | The incident's action items, oldest first. |
| `POST` | `/incident/{incident_id}/action_items` | `title`, plus optional `owner_user_id`, `due_date` and `external_url`. | `201` and the item. |
| `PUT` | `/incident/{incident_id}/action_items/{action_item_id}` | Any of `title`, `status`, `owner_user_id`, `due_date`, `external_url`; `null` clears the last three. | The item. |
| `DELETE` | `/incident/{incident_id}/action_items/{action_item_id}` | none | `204`. |
| `GET` | `/incident/action_items` | Query: `status` (`open` default, `done`, `wont_do`, `all`), `owner_user_id`, `overdue`, `limit`, `offset`. | Every incident's items in `data`, soonest due first, plus `total`. |

A new due date or owner re-arms the one overdue email. See [the reminder](/incident-management/incidents/how-to/postmortems/#overdue-items-and-the-reminder-email).

### Publish (`POST /incident/{incident_id}/publish`)

| Field | Type | Description |
|---|---|---|
| `status_page_id` | uuid | The status page to publish this incident to. A page that is not in your account returns `404`. |
| `title` | string | Optional. Sets `public_title`. Otherwise the page keeps the current public title, then uses the service template's title. An incident a monitor opened shows "Service disruption" rather than its monitor's name. |
| `message` | string | Optional. A public update to post with it. When the incident has no public update yet, one is always posted: this text, else the service template's message, else "We are investigating this issue." |
| `notify_subscribers` | bool | Email the page's subscribers that the incident opened. Default `true`. Never sent for a resolved incident, and at most once per page. |

Publishing to a page the incident is already on changes nothing unless you send a `title` or `message`.

### Unpublish (`DELETE /incident/{incident_id}/publish/{status_page_id}`)

Takes the incident off that page. The incident and its updates are kept, and nobody is emailed. Returns the incident, or `404` when it is not on that page.

## Incident metrics

`GET /incident/metrics` returns counts and acknowledgement/resolution durations for incidents **created** in a time window. It requires `read:incidents`. The MCP tool is `incident_metrics`.

| Query | Meaning |
|---|---|
| `from` | Inclusive creation time, RFC 3339. Defaults to 30 days before `to`. |
| `to` | Exclusive creation time, RFC 3339. Defaults to now. The maximum window is 366 days. |
| `service_id` | Only incidents currently associated with this account-owned service. A missing or foreign service returns `404`. |
| `severity` | Current severity: `minor`, `major` or `critical`. |

The response contains `total_incidents`, `open_incidents`, `resolved_incidents` and `acknowledged_incidents`, plus `mtta` and `mttr`. Each duration summary has `samples`, `mean_seconds`, `p50_seconds` and `p90_seconds`. Percentiles use continuous interpolation. With no samples the durations are null, not zero.

MTTA runs from creation to the first acknowledgement event. MTTR runs from creation to the latest resolution event for incidents currently resolved. Earlier incidents without those events use their stored acknowledgement and resolution times. Unresolved incidents contribute no MTTR sample. Negative durations are excluded. Merged source incidents contribute to neither counts nor durations.

The time window selects creation times; lifecycle state and duration values are current when queried. A resolution after `to` can therefore contribute, and later service or severity edits can change filtered results. `acknowledged_incidents` counts incidents with an acknowledgement time, including resolved incidents and incidents triggered again after reopening.

Full incident detail and lifecycle responses can also include `first_paged_at`, the first responder page accepted by its provider, and `mitigated_at`, the first public status transition to `monitoring`. Email and carrier delivery updates are tracked separately. These fields are omitted when no matching event exists and on list responses. Earlier pages are not backfilled, and resolution alone does not set a mitigation time.

## Conflicts (`409`)

A `409` from these routes carries a code in `data.conflict`:

| Route | `data.conflict` | Meaning |
|---|---|---|
| `POST /incident/{id}/merge` | `same_incident` | A source is the target. |
| `POST /incident/{id}/merge` | `source_merged` | A source was already merged into another incident. |
| `POST /incident/{id}/merge` | `source_resolved` | A source is already resolved. |
| `POST /incident/{id}/merge` | `target_resolved` | The target is resolved. |
| `POST /incident/{id}/merge` | `target_merged` | The target was merged into another incident. |
| `POST /incident/{id}/participants` | `merged` | The incident was merged into another. |
| `POST /incident/{id}/participants` | `resolved` | `page` is `true` on a resolved incident. |
| `POST /incident/{id}/participants` | `nobody_on_call` | The schedule or policy resolved to no one. |
| `POST /incident/{id}/monitors` | `merged` | The incident was merged into another. |
| `POST /incident/{id}/postmortem` | `exists` | The incident already has a postmortem; `data.postmortem` holds it. |
| `POST /incident/{id}/postmortem` | `merged` | The incident was merged into another. |
| `PUT /incident/{id}/postmortem` | `incident_open` | Publishing before the incident is resolved. |
| `POST /incident/{id}/action_items` | `merged` | The incident was merged into another. |
| `PUT /incident/{id}` | `open_auto_incident_exists` | You moved an auto-created incident onto a service that already has an open auto-created incident. |
| `POST /incident/{id}/reopen` | `open_auto_incident_exists` | Another open auto-created incident already covers that service. |
| `POST /incident/{id}/reopen` | `merged` | A merged incident cannot reopen. |
