A channel (also called a *notification* in the API) is a single delivery destination. Channels live inside a [notification group](/incident-management/notifications/overview/#notification-groups), which is what you attach to monitors.

Every channel has:

```json
{
  "notification_group_id": "<group-uuid>",
  "type": "email|sms|slack|webhook|telegram|discord|microsoft_teams|pagerduty|opsgenie|google_chat|mattermost|pushover|pushbullet",
  "details": { ... }    // type-specific fields
}
```

This page documents `details` for each type.

<Aside type="caution" title="Channel support varies by alert source">
Not every alert source reaches every channel type. A channel of a type the source does not support is **skipped**: no alert arrives on it, and a `skipped` receipt records why (see [Skipped deliveries](#skipped-deliveries)). Saving the monitor still succeeds, with a warning. Check [which alerts reach which channels](#which-alerts-reach-which-channels) before you rely on a channel, and keep an email or SMS channel in every group that has to page someone.
</Aside>

## Which alerts reach which channels

| Alert source | Reaches | Skipped |
|---|---|---|
| HTTP monitors, browser checks, domain expiry, log/metric/trace alert rules, RUM issues | All 13 channel types | None |
| Heartbeat (cron) monitors | Email, SMS, Slack, webhook, Telegram, PagerDuty | Discord, Microsoft Teams, Google Chat, Mattermost, Opsgenie, Pushover, Pushbullet |
| TLS expiry and page speed | Email, SMS, Slack, webhook, Telegram, Discord, Microsoft Teams | Google Chat, Mattermost, PagerDuty, Opsgenie, Pushover, Pushbullet |
| DNS record changes | Email, webhook, PagerDuty | Every other type |

Incidents do not use notification channels. Escalation steps reach responders through their [contact methods](/incident-management/notifications/overview/) (email, SMS, or a Slack DM with a bot token you paste in), and a service broadcasts to its own targets (email, a Slack channel with a pasted bot token, or a webhook URL). Maintenance windows send no notifications, and status page updates go only to the page's email subscribers.

## Skipped deliveries

When an alert is deliberately not sent to a channel, Site Qwality records a receipt with the status `skipped` and a reason slug.

| Reason | Meaning | Marks the channel degraded |
|---|---|---|
| `heartbeat_channel_unsupported` | Heartbeat alerts cannot be sent to this channel type yet. | No |
| `tls_channel_unsupported` | TLS certificate alerts cannot be sent to this channel type yet. | No |
| `page_speed_channel_unsupported` | Page speed alerts cannot be sent to this channel type yet. | No |
| `dns_record_channel_unsupported` | DNS record change alerts cannot be sent to this channel type yet. | No |
| `sms_quota` | The account is over its SMS quota and has no SMS credits left. | Yes |
| `sms_platform_limit` | Site Qwality's own monthly SMS sending limit was reached. The problem is on our side, not in your channel. | Yes |

Other slugs are reserved and not recorded yet. Treat a reason you do not recognise as a plain skip.

Skipped receipts appear in a channel's recent deliveries (`health.recent` on `GET /notification/{id}` and on each channel in `GET /notification_group`) and in a monitor's alert history (`GET /monitors/{id}/alert_history`, with the slug in `detail`). A skip by design, such as `heartbeat_channel_unsupported`, is listed but does not change the channel's `health.state`. An `sms_quota` or `sms_platform_limit` skip sets it to `degraded`, because the next alert will likely not arrive either.

### Warnings when you save a monitor

Creating or updating an HTTP, heartbeat or DNS record monitor still succeeds when one of its notification groups holds a channel its alerts cannot reach. The response carries a `warnings` array beside `data`, one entry per channel and alert source:

```json
"warnings": [
  {
    "code": "channel_not_supported_for_source",
    "message": "Heartbeat alerts cannot be sent to Discord yet, so \"On-call\" will skip that channel for them.",
    "notification_group_id": "<group-uuid>",
    "notification_id": "<channel-uuid>",
    "channel": "discord",
    "source": "heartbeat",
    "reason": "heartbeat_channel_unsupported"
  }
]
```

`source` is `heartbeat`, `tls_expiry`, `page_speed` or `dns_record`, and `reason` is the slug the skipped receipts will carry. An HTTP monitor is also checked for the alerts of its paired TLS and page speed checks. The field is left out when there is nothing to warn about.

## Email

```json
{
  "type": "email",
  "details": { "email_address": "alerts@example.com" }
}
```

- Validated against a basic email regex.
- No verification step, so anything that parses as an email is accepted.
- Sender is `Site Qwality <no-reply@notifications.siteqwality.com>`. Allow it to avoid spam folders.
- The subject names the monitor type, the state and the monitor (for example `[HTTP down] prod-api`); the body links to the monitor in the dashboard.

## SMS

```json
{
  "type": "sms",
  "details": {
    "country_code": 1,
    "phone_number": "5551234567"
  }
}
```

- `country_code` is the country dialing prefix as an integer (1 for US, 44 for UK, 49 for DE, etc).
- `phone_number` is the local number with no formatting characters.
- Validation requires a parseable phone number.
- Each message uses your account's SMS credits. When the account is over its SMS quota and has no credits left, the message is not sent and is recorded as skipped with `sms_quota`.

<Aside type="caution">
SMS delivery is best-effort and is tried once. For critical pages, pair SMS with a second channel such as email or a push app.
</Aside>

## Slack

```json
{
  "type": "slack",
  "details": {
    "integration_id": "<slack-integration-uuid>",
    "channel": "#ops"
  }
}
```

- Requires a Slack integration first. See [Integrations → Slack](/integrations/slack/).
- `channel` accepts `#name` or a Slack channel ID. The app must be added to private channels.
- Monitor alerts render as a message attachment with a status color, the monitor name and URL. They have no buttons.
- Incident messages link to the incident in Site Qwality and have no buttons. Acknowledge and resolve from the incident page.

## Webhook

```json
{
  "type": "webhook",
  "details": { "integration_id": "<webhook-integration-uuid>" }
}
```

- The URL lives on the integration object (`/integration/webhook`), not the channel, so multiple channels can share one URL with different downstream meaning.
- Payload is a signed JSON POST with an event envelope. See [Integrations → Webhooks](/integrations/webhooks/) for events, headers and signature checks.

Sample webhook body (`data` truncated):

```json
{
  "id": "<delivery-uuid>",
  "event": "monitor.down",
  "severity": "critical",
  "created_at": "2026-03-14T09:26:53Z",
  "account_id": "<account-uuid>",
  "data": {
    "http_job_id": "<monitor-uuid>",
    "request_uri": "https://api.example.com",
    "response_http_code": 503,
    "status": "failed"
  }
}
```

## Telegram

```json
{
  "type": "telegram",
  "details": { "telegram_integration_id": "<telegram-integration-uuid>" }
}
```

- Setup is two-step: start a setup code, send it to the bot, then finalize. See [Integrations → Telegram](/integrations/telegram/).
- Messages render as HTML-formatted text with the monitor name, URL and state. They have no link back to Site Qwality.

## Discord

```json
{
  "type": "discord",
  "details": { "discord_integration_id": "<discord-integration-uuid>" }
}
```

- Discord integration uses an incoming webhook URL (created in your Discord server settings).
- Messages render as embeds with a status color and the monitor details. They have no link back to Site Qwality.

## Microsoft Teams

```json
{
  "type": "microsoft_teams",
  "details": { "teams_integration_id": "<teams-integration-uuid>" }
}
```

- Teams integration uses a Workflows webhook URL for a Teams channel. Office 365 connector URLs no longer work. See [Integrations → Microsoft Teams](/integrations/microsoft-teams/).
- Messages render as Adaptive Cards with a status color.

## PagerDuty

```json
{
  "type": "pagerduty",
  "details": {
    "pagerduty_integration_id": "<pagerduty-integration-uuid>",
    "pagerduty_severity": "critical"
  }
}
```

- `pagerduty_severity` is optional and defaults to `critical`. Values: `critical`, `error`, `warning`, `info`.
- Outages trigger a PagerDuty incident; recoveries resolve the same one via a shared dedup key.
- Domain expiry warnings always send at `warning` regardless of this setting, and never auto-resolve.
- See [Integrations → PagerDuty](/integrations/pagerduty/).

## Jira Service Management (Opsgenie)

```json
{
  "type": "opsgenie",
  "details": { "opsgenie_integration_id": "<opsgenie-integration-uuid>" }
}
```

- No per-channel priority field. Outages are `P1`, domain expiry warnings are `P3`.
- Recoveries close the alert by alias. Domain expiry alerts never close on their own.
- The channel type is still `opsgenie`. See [Integrations → Jira Service Management (Opsgenie)](/integrations/opsgenie/).

## Google Chat

```json
{
  "type": "google_chat",
  "details": { "google_chat_integration_id": "<google-chat-integration-uuid>" }
}
```

- The integration holds a space incoming webhook URL, which is readable back through `GET /integration`.
- Messages render as Google Chat cards.
- Sends that fail 3 times are recorded and dropped rather than retried further. See [Integrations → Google Chat](/integrations/google-chat/).

## Mattermost

```json
{
  "type": "mattermost",
  "details": { "mattermost_integration_id": "<mattermost-integration-uuid>" }
}
```

- The integration holds an incoming webhook URL, readable back through `GET /integration`.
- Messages render as Slack-style attachments with a status color.
- Same 3-attempts-then-drop behavior as Google Chat. See [Integrations → Mattermost](/integrations/mattermost/).

## Pushover

```json
{
  "type": "pushover",
  "details": { "pushover_integration_id": "<pushover-integration-uuid>" }
}
```

- The integration holds both a user (or group) key and an application API token.
- Outages send at priority `1` (bypasses quiet hours); recoveries and expiry warnings at `0`.
- See [Integrations → Pushover](/integrations/pushover/).

## Pushbullet

```json
{
  "type": "pushbullet",
  "details": { "pushbullet_integration_id": "<pushbullet-integration-uuid>" }
}
```

- The integration holds an account access token.
- Messages arrive as note pushes on every signed-in device.
- See [Integrations → Pushbullet](/integrations/pushbullet/).

## Delivery guarantees by channel

Not all channels behave the same when a send fails. This matters when you are choosing which channel to trust for a critical page.

| Channels | On failure |
|---|---|
| Webhooks | Up to 6 attempts over 30 minutes. Every attempt is in the endpoint's [delivery log](/integrations/webhooks/#delivery-log-and-replay). While retries are pending the alert's receipt reads `delayed`; when they end it becomes `delivered`, `failed` or `rejected`. |
| PagerDuty, Opsgenie | 3 attempts. A `4xx` other than `408` or `429` is recorded as rejected. Other failures run the send again up to twice; after that the alert is **dropped with no record**. |
| Pushover, Pushbullet | 1 attempt. A `4xx` is recorded as rejected. Other failures run the send again up to twice; after that the alert is dropped with no record. |
| Email, SMS, Slack, Telegram | 1 attempt. A failure runs the send again up to twice; after that the alert is dropped with no record. |
| Discord, Microsoft Teams, Google Chat, Mattermost | 3 attempts in quick succession, then the failure is recorded and the message is dropped. If the attempts run past the send's time limit, the alert is lost with no record. |

For a page that must arrive, use more than one channel type.

## Common pitfalls

- **Channel created but no notifications arrive.** First check whether the channel is attached to a *group* and the group is attached to the *monitor*. Channels alone don't deliver.
- **Channel save refused with a `422`.** A channel must name an integration of its own type in your account, so a mistyped ID or an ID of another integration type is refused. Copy the ID from `GET /integration`.
- **Alerts show as skipped.** The alert source cannot use that channel type, or SMS ran out of quota. See [Skipped deliveries](#skipped-deliveries).
- **SMS not arriving.** Verify the country code is the integer prefix (`1`, not `"+1"`); confirm the number is plain digits.
