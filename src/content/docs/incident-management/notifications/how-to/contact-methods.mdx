A contact method is one way to reach you personally. Incident pages use contact methods, through your [notification rules](/incident-management/notifications/how-to/notification-rules/). Monitor alerts do not: they go to [notification groups](/incident-management/notifications/default-routing/).

## What you start with

A new user (sign-up, accepted invite or SCIM) starts with one contact method: their sign-in email, already verified, with a `high` and a `low` notification rule on it, both with no delay. So a new teammate added to an escalation policy is paged by email until they set up something else.

## Types

| Type | `details` | Verification |
|---|---|---|
| `email` | `{ "email": "alice@example.com" }` | Optional. Your sign-in email is verified when you add it. |
| `sms` | A phone number and its country (see below) | Required before a rule can use it. |
| `slack_dm` | `{ "slack_token": "xoxb-...", "channel": "U0123ABCD" }` | Optional. |

A `slack_dm` method does not use the account's Slack integration. Its token never reads back in full: it shows as `****` followed by its last four characters.

Phone calls are not delivered, so a `phone_call` method is refused.

Each user can have up to 20 contact methods. You manage your own, and admins can manage anyone's.

## Add one in the dashboard

<Steps>

1. Open the menu under your name (bottom left), choose **Notifications**, then go to **Contact methods**.

2. Click **Add method** (**Add contact method** if you have none yet) and pick **Email**, **SMS** or **Slack DM**. For SMS, choose the country, then type the number the way you would dial it locally, for example `07911 123456` for the UK.

3. Click **Add contact method**, then [verify the method](#verify-a-contact-method). An SMS number cannot be used in a rule until you do.

</Steps>

An email address that bounces permanently, or reports a page as spam, stops receiving pages: the rule is skipped and the incident records why. The [readiness check](/incident-management/escalation/readiness/) on each escalation policy shows any method like this.

## Add one with the API

Contact methods live under `/user/{user_id}/contact_method`. In the examples, `USER_ID` is your user ID from `GET /account/info`.

```bash
curl -X POST https://api.siteqwality.com/user/$USER_ID/contact_method \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "type": "sms",
    "details": { "phone_number": "07911 123456", "country": "GB" }
  }'
```

```json
{
  "data": {
    "id": "6d0c2f4e-8a7b-4b1e-9c3d-2e5f7a9b1c0d",
    "user_id": "1a2b3c4d-5e6f-4a7b-8c9d-0e1f2a3b4c5d",
    "type": "sms",
    "details": {
      "phone_number": "7911123456",
      "country_code": "44",
      "e164": "+447911123456",
      "country": "GB"
    },
    "verified": false,
    "created_at": "2026-10-14T09:30:00Z"
  }
}
```

### SMS numbers

SMS works for numbers in any country. Give the country one of these ways:

| Form | Example `details` |
|---|---|
| Number and country (ISO 3166-1 alpha-2), what the dashboard sends | `{ "phone_number": "07911 123456", "country": "GB" }` |
| Number and calling code, as a string or a number | `{ "phone_number": "7911123456", "country_code": "44" }` or `"country_code": 44` |
| E.164 number | `{ "e164": "+447911123456" }`, `{ "phone_number": "+447911123456" }` or a bare `"+447911123456"` |

A US number works the same way: `{ "phone_number": "202 555 0123", "country": "US" }`, `"country_code": "1"`, or `"+12025550123"`.

A number with no country (no leading `+`, no `country`, no `country_code`) is rejected, and so is a number that is not valid for its country.

Older SMS methods may show only `phone_number` and `country_code` in `details`.

### Email and Slack DM

```bash
curl -X POST https://api.siteqwality.com/user/$USER_ID/contact_method \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "type": "email", "details": { "email": "alice@example.com" } }'

curl -X POST https://api.siteqwality.com/user/$USER_ID/contact_method \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "type": "slack_dm", "details": { "slack_token": "xoxb-your-bot-token", "channel": "U0123ABCD" } }'
```

### Rules created for you

When you add a method that a rule can use (any email or Slack DM method, or a verified SMS number), and you have no rule yet for `high` or `low` urgency, Site Qwality creates the missing rule on the new method with no delay. Verifying an SMS number does the same. Rules you already have are never changed.

## Verify a contact method

An email that matches your sign-in email is verified when you add it. Every other method starts unverified. An SMS number must be verified before a notification rule can use it; for email and Slack DM, verifying confirms the destination works.

In the dashboard, click **Verify** next to the method, then **Send code**. Enter the 6-digit code you receive and click **Confirm**. The method then shows **Verified**.

Through the API:

<Steps>

1. Send a code to the method, with its `id` from the create response as `METHOD_ID`. Site Qwality sends a 6-digit code by email, SMS or Slack DM, depending on the method.

   ```bash
   curl -X POST https://api.siteqwality.com/user/$USER_ID/contact_method/$METHOD_ID/verification \
     -H "Authorization: Bearer $SITEQWALITY_API_KEY"
   ```

   ```json
   { "data": { "expires_in_seconds": 600, "resend_after_seconds": 60, "code_length": 6 } }
   ```

2. Confirm it. A correct code returns the method with `"verified": true`.

   ```bash
   curl -X POST https://api.siteqwality.com/user/$USER_ID/contact_method/$METHOD_ID/verification/confirm \
     -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
     -H "Content-Type: application/json" \
     -d '{ "code": "123456" }'
   ```

</Steps>

| Limit | Value |
|---|---|
| Code length | 6 digits |
| Code expiry | 10 minutes |
| Resend | After 60 seconds |
| Wrong codes | 5, then the code is locked |
| Sends per method | 5 a day |
| Sends per account | 20 a day |

## Edit a contact method

Change the address or number in place instead of deleting and re-adding the method, so your rules keep pointing at it. In the dashboard, click the pencil icon next to the method, change the details and click **Save changes**. Through the API:

```bash
curl -X PATCH https://api.siteqwality.com/user/$USER_ID/contact_method/$METHOD_ID \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "details": { "phone_number": "06 12 34 56 78", "country": "FR" } }'
```

- `details` takes the same shapes as create. For a Slack DM, send the full bot token again.
- The type cannot change. To switch from email to SMS, add a new method.
- Changing the email address or phone number marks the method unverified, unless the new email is your sign-in email. Verify it again; an unverified SMS number cannot be added to a rule.

## Delete a contact method

In the dashboard, click the trash icon next to the method and confirm with **Remove**. The confirmation says how many paging rules go with it. Through the API:

```bash
curl -X DELETE https://api.siteqwality.com/user/$USER_ID/contact_method/$METHOD_ID \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY"
```

<Aside type="caution">
If you delete the method your rules use, those rules go with it. A user with no rule for an incident's urgency is paged only at their sign-in email, so check your [notification rules](/incident-management/notifications/how-to/notification-rules/) afterwards.
</Aside>
