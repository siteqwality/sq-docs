A **maintenance window** is a time range during which monitors with matching tags, or the monitors of chosen services, don't page. Checks still run and failures are still recorded; they just don't reach humans while the window is active.

Use maintenance windows for:

- **Scheduled deploys**: the four-second blip during your zero-downtime rollout shouldn't page anyone.
- **Database migrations**: the ten-second connection-pool restart isn't an outage.
- **Vendor maintenance**: your CDN's scheduled maintenance shouldn't page you.
- **Long-running batch jobs**: the queue spike during nightly ETL is expected.

## Two types

### One-time

A single `starts_at` / `ends_at` pair. Fire-and-forget for one specific deploy or operation.

```json
{
  "name": "Friday API deploy",
  "tags": ["service:api"],
  "schedule_type": "one_time",
  "starts_at": "2026-05-10T14:00:00Z",
  "ends_at": "2026-05-10T14:30:00Z"
}
```

### Recurring

A recurrence rule. Two flavors:

**Daily**, the same window every day:

```json
{
  "name": "Nightly batch ETL",
  "tags": ["service:etl"],
  "schedule_type": "recurring",
  "timezone": "America/Los_Angeles",
  "recurrence": {
    "type": "daily",
    "start_time": "02:00",
    "end_time": "03:00"
  }
}
```

**Weekly**, the same window on chosen days each week:

```json
{
  "name": "Sunday maintenance window",
  "tags": ["env:prod"],
  "schedule_type": "recurring",
  "timezone": "UTC",
  "recurrence": {
    "type": "weekly",
    "days": ["sunday"],
    "start_time": "02:00",
    "end_time": "04:00"
  }
}
```

`start_time` and `end_time` are 24-hour `HH:MM` in the window's `timezone` (defaults to `UTC`). Days accept full English names (`monday` .. `sunday`) or three-letter abbreviations (`mon` .. `sun`), case-insensitively; anything else is rejected at creation.

## Windows by service

A window can name services in `service_ids` instead of, or as well as, tags. Every monitor and alert rule linked to those services is covered, whatever its tags, including monitors you add to the service later:

```json
{
  "name": "Checkout deploy",
  "service_ids": ["<service-id>"],
  "schedule_type": "one_time",
  "starts_at": "2026-05-10T14:00:00Z",
  "ends_at": "2026-05-10T14:30:00Z"
}
```

A window needs tags, services or both. A telemetry alert rule is also covered when the window lists it in `alert_rule_ids`, which includes RUM issue alerts.

## How tags match

Each maintenance window has a list of `tags`. Monitors also have tags. A monitor is silenced when its tags **overlap** with an active window's tags, meaning at least one tag appears in both lists. That's the whole rule:

- There is **no wildcard tag**. To silence everything, give every monitor a shared tag (for example `env:prod`) and put that tag on the window.
- A window needs at least one tag or one service (the API rejects a window with neither).
- A monitor with **no tags** never matches by tag; put its service on the window instead.

Patterns we recommend:

- `service:<name>` to silence everything in a service.
- `env:<name>` to silence everything in an environment.
- `type:cron` to silence all cron checks.

## What "silenced" means precisely

Suppression applies to monitor notifications that carry monitor context (HTTP monitors, heartbeats, browser checks and alert rules, including RUM issue alerts). While a matching window is active:

- **Checks still run on schedule.** Results are recorded.
- **Failure notifications are held, not dropped.** They are stored and re-evaluated when the window's current occurrence ends, so a monitor that is still down after the window pages then.
- **Recovery notifications are suppressed** and clear the held failure for that monitor, so a blip fully inside the window pages no one.
- **Auto-created incidents wait.** A monitor that fails inside the window opens its service's incident when the window ends, if it is still failing then; a blip that recovers inside the window never opens one. An incident that was already open keeps its escalation paused until the window ends.
- **Ending a window early releases what it held.** Deleting a window, moving its end earlier or removing tags or services sends the alerts it no longer covers within a minute, unless another active window still covers them.
- **The window shows what it holds.** `GET /maintenance_windows/{window_id}/coverage` lists the monitors the window matches and how many alerts are held for each right now; the dashboard's window form shows the same list.
- **Status pages keep showing live status** unless you also publish a [status page maintenance](/status-pages/how-to/publish-maintenance/) entry.

`is_currently_active` on the response tells you whether the window is in effect right now (computed against the server clock).

## Maintenance windows vs status page maintenance

Easy to confuse:

| | Maintenance window | Status page maintenance |
|---|---|---|
| **Purpose** | Suppress paging | Tell customers "scheduled maintenance" |
| **Effect** | Internal | External |
| **Routes through** | Notification fanout (held/suppressed) | Status page rendering |
| **Endpoint** | `/maintenance_windows` | `/status_page/{id}/maintenance` |

You typically want both for a planned outage: the maintenance window so on-call doesn't get woken; the status page maintenance so customers see "Scheduled maintenance: 02:00-04:00 UTC" on the public page.
