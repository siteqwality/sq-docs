The audit log answers "who changed this, and when". Every mutating request made against your account is recorded with the actor, the action, the request path and status, the source IP, and the user agent.

Find it under **Settings → Audit log**. Only **super admins, admins, and auditors** can read it, because it exposes other members' actions and IP addresses.

Click any row to open its full details: who acted and with which credential, the request, the source IP and browser, and shortcuts to everything else that actor or target was involved in.

## What is and is not recorded

**Recorded:** every authenticated `POST`, `PUT`, `PATCH` and `DELETE` against your account, whoever made it and whichever credential they used.

**Not recorded:**

- **Reads.** `GET` requests are not logged, so the log tells you who changed something, not who *looked* at it. The one exception is session replay: every view is recorded as `rum.replay.viewed` (see [who watched](/observability/replay/reference/#who-watched)). A handful of read endpoints that use `POST` purely to carry a request body (the dashboard's batch monitor lookup, the log-parser test preview, the consent page loading what an AI assistant is asking for) are treated as reads and excluded too.
- **Unauthenticated requests**, including ones whose credentials were rejected. Successful, verified incident actions are an exception: responder action links and accepted Slack actions identify the member and incident, so they are recorded.
- **Site Qwality staff actions**, which live in a separate internal audit log. Staff acting *as* one of your users through impersonation do appear here, marked as such.

A request that identifies its caller and is then denied **is** recorded, with the resulting status. That covers validation failures and permission denials alike: a viewer-role user attempting a delete, an API key used outside its scopes, or a write attempted while the account is suspended all appear with their `403`. A rejected attempt is worth seeing.

## Actor types

| Actor type | Meaning |
|---|---|
| `session` | A team member using a session or a verified incident action. `actor_user_id` identifies them. |
| `m2m` | An [M2M API client](/enterprise/api-clients/). `actor_m2m_client_id` identifies it. |
| `api_key` | A static API key. `actor_api_key_id` identifies which one, and `actor_api_key_name` carries its display name. Entries from before 2026-08-06 predate the column and have neither. |
| `impersonated_staff` | A Site Qwality staff member acting as one of your users. `impersonated_by` records which staff member. |
| `connected_app` | An [AI assistant](/integrations/mcp/) (or other OAuth app) acting as the member who approved it. `actor_user_id` and `actor_user_email` identify the member; `connected_app` names the app. |
| `partner` | A user of your [partner account](/partners/context-switching/) acting on this account. |
| `system` | Written by Site Qwality itself rather than by a request. Today that is the `account.created` entry recorded when the account is set up. |

## Reading the log

Each entry carries:

| Field | Description |
|---|---|
| `occurred_at` | When, in UTC. |
| `actor_type`, `actor_user_id`, `actor_user_email`, `actor_api_key_id`, `actor_api_key_name`, `actor_m2m_client_id`, `impersonated_by` | Who. `actor_user_email` is the person behind a session, an AI assistant or a partner action. |
| `connected_app` | `{ client_id, name }` of the AI assistant involved: the one that acted, or the one connected or disconnected. `name` is what the app registered itself as. |
| `via`, `mcp_tool` | `via` is `mcp` for the [MCP server](/integrations/mcp/), `action_link` for a responder action link, or `slack` for an accepted Slack incident action. `mcp_tool` names the MCP tool when applicable. |
| `consent_granted`, `scopes` | On an `oauth.authorize` entry: whether the member allowed the assistant, and the scopes they granted. |
| `action` | The path with UUIDs (and free-form segments like RUM release versions) removed, dot-joined. |
| `target_kind`, `target_id` | The resource type and, when the path had one, its ID. |
| `http_method`, `http_path`, `http_status` | The raw request and its outcome. |
| `request_ip`, `user_agent` | Where from. The IP is the connection our API gateway actually saw, not a client-supplied header, so it cannot be spoofed by the caller. |
| `configuration_change` | Optional observed `before` and `after` snapshots for successful policy, on-call schedule and service changes. |

`action` is derived from the path, so it groups related calls without the verb. Some real examples:

| Request | `action` |
|---|---|
| `POST /http/job` | `http.job` |
| `DELETE /http/job/{id}` | `http.job` |
| `POST /incident/{id}/acknowledge` | `incident.acknowledge` |
| `POST /account/m2m_client` | `account.m2m_client` |
| `POST /oauth/authorize` (a member allowing or refusing an AI assistant) | `oauth.authorize` |
| `DELETE /account/connected_apps/{id}` (a member disconnecting an AI assistant) | `account.connected_apps` |
| `GET /rum/{app_id}/sessions/{session_id}/replay` (watching a replay, at most once per viewer per 30 minutes) | `rum.replay.viewed` |

The verb lives in `http_method`, so filter on both when you want "who deleted a monitor" rather than "who touched monitors".

## Configuration comparisons

Open a successful escalation policy, on-call schedule or service change to see **Observed configuration**. The comparison shows settings that differ between snapshots taken before and after the request. It covers child changes too, including policy levels and their order, schedule layers and overrides, and service monitor and notification-target links.

The API exposes these snapshots as `configuration_change.before` and `configuration_change.after`. Each snapshot has a `kind` (`escalation_policy`, `on_call_schedule` or `service`) and `settings`. A creation has a null `before`; a deletion has a null `after`. The dashboard CSV export includes both snapshots.

Policy targets and schedule participants retain their order and repeated entries. Service links include the resource IDs and types. Monitor URLs, notification destinations and credentials are excluded from the snapshots.

These are observed snapshots, read separately from the change. Concurrent edits can affect the comparison. Snapshot capture is best-effort: an unavailable snapshot leaves the ordinary audit entry without a comparison. Earlier entries and rejected requests do not gain snapshots retroactively.

## Incident actions

A successful responder link writes `incident.acknowledge` or `incident.resolve` with `via: "action_link"`, the member and the incident. Its recorded path is `/incident/action/[redacted]`; the action token is never stored in the audit entry. Opening the confirmation page does not write a successful action, and replaying a used link does not add another one.

An accepted, verified Slack action uses `via: "slack"`. Both action sources use `actor_type: "session"` to identify the member, even when no browser session was needed. Their `request_ip` and `user_agent` are absent.

## Query it

```bash
curl -G https://api.siteqwality.com/account/audit_log \
  -H "Authorization: Bearer $SESSION_JWT" \
  --data-urlencode "action=http.job" \
  --data-urlencode "actor_type=m2m" \
  --data-urlencode "since=2026-07-15T00:00:00Z" \
  --data-urlencode "limit=200"
```

<Aside type="caution" title="Super admin, admin, or auditor session required">
The endpoint is gated on the super admin, admin, or auditor role, which only a logged-in user session carries. API keys and M2M clients get a `403`: a leaked automation credential must not be able to read every member's actions and IP addresses. There is no programmatic export for SIEM ingestion today.
</Aside>

| Param | Default | Notes |
|---|---|---|
| `actor_user_id` | none | Exact UUID. |
| `actor_api_key_id` | none | Exact UUID; narrows to one API key's actions. |
| `actor_type` | none | One of the actor types above. |
| `action` | none | Exact match **or dot-prefix**: `http.job` also matches `http.job.regions`, never `http.jobs`. |
| `target_kind` | none | Exact match. |
| `target_id` | none | Exact UUID. |
| `since`, `until` | last 90 days | RFC 3339. |
| `limit` | 100 | Clamped to 1..1000. |

Entries come back newest first.

<Aside type="caution" title="There is no cursor pagination">
The only way to reach older entries is to move the `since` and `until` window. If a query returns exactly `limit` rows, assume there are more and narrow the range.
</Aside>

## AI assistants

Everything an assistant changes goes through the same API as the dashboard, so it is logged like any other change, and the entry answers three questions:

- **Who:** the member who approved the assistant (`actor_user_email`). An assistant never acts as anyone else, and never with more than that member's role allows.
- **Through which assistant:** `connected_app.name`, for example `Claude`.
- **How:** `via: "mcp"` and the tool it used, for example `pause_monitor`. An API key used through MCP keeps `actor_type: api_key` and gets the same `via` and `mcp_tool`.

Connecting an assistant is logged too: an `oauth.authorize` entry records who allowed or refused which app, with the scopes granted, and an `account.connected_apps` `DELETE` records who disconnected it. To see everything assistants did, filter on `actor_type=connected_app`.

## The 90-day read window

Reads are clamped to the **last 90 days**. A `since` older than that is silently pulled forward, and omitting `since` gives you exactly 90 days.

Worth being precise about what that does and does not mean: **rows older than 90 days are not deleted**. Nothing purges the audit log today. The window is a read limit, not a retention policy, and a longer-term retention story is still an open product decision. If you have a compliance requirement to keep this data beyond 90 days, export what you need on a schedule rather than assuming either that it is gone or that it will stay forever.

## Reliability

Audit writes are best-effort. If a write fails, the underlying request still succeeds and the failure is logged internally rather than surfaced to you. Replay views are the exception: a replay is not served unless its view was recorded.

That means the log is an excellent record and not a guaranteed-complete ledger. It is designed so that auditing can never take your account down.
