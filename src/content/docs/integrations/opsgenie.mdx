The Jira Service Management (Opsgenie) integration creates an alert through the Alerts API of Jira Service Management, or of Opsgenie, when a monitor goes down and closes that same alert when the monitor recovers. Pairing is done through the alert **alias**, which Site Qwality derives from the monitor and the outage. In the API and in channel details the type is still called `opsgenie`.

## What you need

An **API key** from an API integration.

<Steps>

1. In Jira Service Management, go to **Operations → Integrations**. Still on Opsgenie: **Settings → Integrations**.

2. Add an **API** integration.

3. Copy its **API key**.

</Steps>

## Endpoint

The same alerts live on three hosts, and a key only works on its own:

| `endpoint` | In the dashboard | Sends to |
|---|---|---|
| `jsm` | Jira Service Management | `api.atlassian.com/jsm/ops/integration/v2/alerts` |
| `opsgenie_us` | Opsgenie (US) | `api.opsgenie.com/v2/alerts` |
| `opsgenie_eu` | Opsgenie (EU) | `api.eu.opsgenie.com/v2/alerts` |

The dashboard picks Jira Service Management unless you choose otherwise. Atlassian stops Opsgenie on 5 April 2027, and the Opsgenie choices go away then. A key sent to the wrong host is refused and recorded as rejected.

The endpoint is set when you add the integration. To change it, add the integration again with the other endpoint and move your channels to it. Integrations added before the endpoint choice existed have `external_ref: null` and send to Opsgenie US, as they always have.

## Connect it

In the dashboard, go to **Manage → Integrations** and click the **Jira Service Management (Opsgenie)** card. Name it, choose the **Endpoint**, paste the key into **API Key**, and click **Add**.

Or through the API, with [`POST /integration/opsgenie`](/api-reference/operations/add_opsgenie_integration/):

```bash
curl -X POST https://api.siteqwality.com/integration/opsgenie \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "friendly_name": "Acme JSM",
    "api_key": "<api-integration-key>",
    "endpoint": "jsm"
  }'
```

| Field | Required | Description |
|---|---|---|
| `friendly_name` | yes | Up to 256 characters. |
| `api_key` | yes | The API integration's key. |
| `endpoint` | no | `jsm`, `opsgenie_us` or `opsgenie_eu`. Omitted means `opsgenie_us`, so Jira Service Management customers must send `"jsm"`. Any other value is a 422. |

The name and key must be non-empty. The key is not verified at save time.

The API key is a secret. `GET /integration` never returns it: `opsgenie_api_key` shows it as `****` followed by its last four characters (just `****` when it is shorter than 16 characters). The endpoint is not a secret: it comes back as `external_ref.endpoint`.

## Add it to a notification group

Integrations deliver nothing on their own. Alerts reach one once it is a channel in a notification group that your monitors use.

<Steps>

1. Go to **Respond → Notifications**. Click a group's name to open it, or click **Add group** to make a new one.

2. Under **Notifications**, click **Add Notification Method**. Set **Notification Type** to **OpsGenie** and choose this integration under **Integration**.

3. Click **Done editing**, then **Update Group** (**Create Group** for a new group).

</Steps>

Through the API, create the channel with [`POST /notification`](/api-reference/operations/create_notification/):

```bash
curl -X POST https://api.siteqwality.com/notification \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "notification_group_id": "<your-group-id>",
    "type": "opsgenie",
    "details": { "opsgenie_integration_id": "<opsgenie-integration-id>" }
  }'
```

`opsgenie_integration_id` is the only field. There is no per-channel priority setting; see [priority](#priority) below.

## Create and close

Down and up events share one alias built from the monitor ID and the ID of the state transition that opened:

```
sq-http-<monitor-id>-<state-transition-id>
sq-browser-<browser-check-id>-<state-transition-id>
```

- **Monitor goes down** → `POST .../v2/alerts` on the integration's endpoint, with `message: "Monitor DOWN: <name>"`, a description carrying the URL and failure reason, and that alias.
- **Monitor recovers** → `POST .../v2/alerts/<alias>/close?identifierType=alias`, with the recovery message attached as the close note.

Open alerts are deduplicated by alias, so repeated failures within one outage update a single alert rather than stacking. A separate outage later produces a different state transition, and therefore a new alert.

Alert messages longer than 130 characters are truncated to fit the Alerts API limit.

### Priority

Priority is fixed and not configurable per channel:

| Event | Priority |
|---|---|
| Monitor or browser check down | `P1` |
| Recovery (close) | none sent |
| Domain expiry warning | `P3` |

<Aside type="caution" title="Domain expiry alerts do not auto-close">
Domain and DNS expiry warnings are **create-only**: no recovery event exists for them. They key on the DNS job plus the expiry date (`sq-dns-expiry-<job-id>-YYYY-MM-DD`), so repeated warnings for the same date collapse into one alert, but nothing ever closes it.

Close those alerts yourself. Renewing the domain does not close them, and since renewal moves the expiry date, the next warning creates a **new** alert while the old one stays open.
</Aside>

## Delivery behavior

Each attempt waits up to 10 seconds for an answer, and a redirect is never followed. A failed send is tried up to 3 times in quick succession, which is safe because the alias makes the call idempotent; no attempt starts so close to the run's time limit that it could not finish. A 4xx answer other than 408 or 429 means the service refused the event: it is recorded as rejected and not retried. Any other failure fails the event, and it is run up to two more times. If those fail too, the alert is dropped with no record in alert history, so pair this channel with a second one for anything you cannot afford to miss.

## Limitations

- These channels fire for **HTTP monitors, browser checks, domain expiry warnings, log, metric and trace alert rules, and RUM issues**. Heartbeat (cron) monitors, TLS expiry warnings, page speed alerts and DNS record changes do not reach these channels today: a channel on a group used by those sources is skipped. See the [coverage table](/integrations/coverage/#opsgenie).
- Incidents and escalation policies do not page through Jira Service Management or Opsgenie.
