Site Qwality runs a [Model Context Protocol](https://modelcontextprotocol.io) (MCP) server, so Claude, ChatGPT, Cursor, VS Code and other AI assistants can work with your account. Ask which monitors are down, what happened in last night's incident, or what the logs said around a failed check, and let the assistant take everyday actions: pause a monitor, acknowledge an incident, post a status page update.

The server URL is:

```text
https://mcp.siteqwality.com/mcp
```

It is available on every plan, including Free. Plan limits and usage quotas apply exactly as they do in the dashboard.

## How signing in works

<Steps>

1. Add the server URL to your assistant (steps for each one are below).

2. The assistant opens a Site Qwality consent page in your browser. Sign in if you are not already.

3. Choose **read-only** or **read and write**, then approve.

</Steps>

The assistant then acts as you, limited to what you approved. Your role still applies: a Viewer cannot make changes even after granting write access.

To cut an assistant off, revoke it under **AI assistants** in your personal settings (open the menu under your name, bottom left). It can no longer sign in, and the access it already has stops working within a minute.

## Add Site Qwality to your assistant

<Tabs syncKey="mcp-client">
<TabItem label="Claude">

Works in Claude on the web and in Claude Desktop, on every Claude plan.

<Steps>

1. Open **[Customize → Connectors](https://claude.ai/customize/connectors)**, click **+**, then **Add custom connector**.

2. Name it `Site Qwality`, paste `https://mcp.siteqwality.com/mcp` as the URL, and click **Add**. Leave **Advanced settings** empty.

3. Click **Connect** and approve access on the Site Qwality consent page.

4. In a chat, turn the connector on from the **+** menu under **Connectors**.

</Steps>

On Team and Enterprise plans an Owner adds the connector once under **Organization settings → Connectors**, and each member then clicks **Connect** under **Customize → Connectors**. Free Claude plans allow one custom connector.

</TabItem>
<TabItem label="Claude Code">

```bash
claude mcp add --transport http siteqwality https://mcp.siteqwality.com/mcp
```

Then run `/mcp` inside Claude Code, pick `siteqwality` and sign in. Add `--scope user` to the command to make Site Qwality available in every project, not only the current one.

</TabItem>
<TabItem label="Cursor">

Add this to `~/.cursor/mcp.json` (every project) or `.cursor/mcp.json` (one project):

```json
{
  "mcpServers": {
    "siteqwality": {
      "url": "https://mcp.siteqwality.com/mcp"
    }
  }
}
```

Cursor opens your browser to sign in when it first connects. If it does not, open Cursor's MCP settings and click **Connect** next to `siteqwality`.

</TabItem>
<TabItem label="VS Code">

Run **MCP: Add Server** from the Command Palette, choose **HTTP**, paste the URL and name it `siteqwality`. Or add it to `.vscode/mcp.json` yourself:

```json
{
  "servers": {
    "siteqwality": {
      "type": "http",
      "url": "https://mcp.siteqwality.com/mcp"
    }
  }
}
```

VS Code opens your browser to sign in the first time the server starts. The tools appear in Copilot Chat under **Configure Tools**.

</TabItem>
<TabItem label="ChatGPT">

Available on the web for ChatGPT Plus, Pro, Business, Enterprise and Edu.

<Steps>

1. Open **Settings → Security and login** and turn on **Developer mode**.

2. Go to [ChatGPT Plugins](https://chatgpt.com/plugins), click **+** and create an app named `Site Qwality` with `https://mcp.siteqwality.com/mcp` as the server URL and **OAuth** as the authentication.

3. Approve access on the Site Qwality consent page.

4. In a chat, pick **Developer mode** from the **+** menu and select Site Qwality.

</Steps>

By default ChatGPT asks you to confirm each write action before it runs.

## Headless agents and CI

Agents that run without a person at a browser (CI jobs, scheduled scripts, background agents) sign in with an [API key](/getting-started/account-and-team/#generate-api-keys) instead of the consent page. Send it as a header:

```text
Authorization: Bearer <your API key>
```

Create it under **Settings → API keys → New key**, choose **Full access** (ingest keys cannot call the API), and tick only the scopes the agent needs. A key with no scopes ticked can do everything your account can.

## Permissions

Access is granted per area, as `read:<area>` and `write:<area>`. On the consent page, read-only grants every `read:` scope and read and write grants both. On an API key you tick them one by one, and write does not include read, so tick both if the agent needs both.

| Area | Scopes | Covers |
|---|---|---|
| Monitors | `read:monitors`, `write:monitors` | HTTP, SSL/TLS, domain expiry, cron and browser checks |
| Incidents | `read:incidents`, `write:incidents` | Incidents (including those on status pages), escalation policies, on-call schedules, maintenance windows |
| Notifications | `read:notifications`, `write:notifications` | Notification channels and groups, and reading integrations |
| Status Pages | `read:status_pages`, `write:status_pages` | Status pages with their monitors, layout, maintenance, subscribers, branding and custom domain |
| Logs | `read:logs`, `write:logs` | Log search, parsers, saved views |
| Metrics | `read:metrics`, `write:metrics` | Metric queries and saved views |
| Traces | `read:traces`, `write:traces` | Trace search and detail |
| RUM | `read:rum`, `write:rum` | RUM applications and analytics |
| Dashboards | `read:dashboards`, `write:dashboards` | Dashboards, templates, version history and widget queries. Public share links are never available to assistants. |
| Services | `read:services`, `write:services` | Services and the escalation policy each one routes to |
| User notification settings | `read:users`, `write:users` | Each user's contact methods and notification rules |

Services and user notification settings are available to assistants that connect with an API key. The consent page does not offer them yet, so an assistant that signs in with OAuth cannot reach them.

Adding, changing or removing an integration needs the separate `integrations:manage` permission. You can tick it on an API key; the consent page never offers it.

Session replay content is never available to an assistant, whatever it is granted: it stays with the people allowed to [watch replays](/observability/replay/reference/#who-can-watch-a-replay).

## What you can ask for

Assistants pick the right tool themselves; you just ask. **Write** tools need the matching `write:` scope.

| Tool | What it does | Access |
|---|---|---|
| `list_attention_items` | Shows what needs attention now: monitors that are down, open incidents, most urgent first. | Read |
| `list_monitors` | Lists your monitors and their current status. | Read |
| `get_monitor` | Shows one monitor's settings and state. | Read |
| `get_recent_checks` | Shows a monitor's latest check results, including the failing step of a browser check. | Read |
| `get_alert_history` | Shows a monitor's recent outages, the alerts each one sent and who acknowledged it. | Read |
| `acknowledge_monitor_outage` | Acknowledges a monitor's outage, recording who is on it and, by default, stopping its repeat alerts. Takes `monitor_id` and an optional `transition_id`; without one it acknowledges the open outage. The first acknowledgement stands, and an outage that has ended is refused. See [acknowledge a monitor outage](/incident-management/notifications/how-to/acknowledge-outages/). | Write |
| `list_check_locations` | Lists the locations a check can run from, with the ids to use when creating or updating a monitor. | Read |
| `create_http_monitor` | Creates an HTTP monitor that alerts your account's default notification group. | Write |
| `update_http_monitor` | Changes an HTTP monitor's settings. | Write |
| `pause_monitor`, `resume_monitor` | Pauses or resumes a monitor. | Write |
| `delete_monitor` | Deletes a monitor. | Write, asks first |
| `run_browser_check` | Runs a browser check now. | Write |
| `list_incidents`, `get_incident` | Lists incidents, or shows one with its timeline. | Read |
| `incident_metrics` | Counts incidents created in a time window and returns mean, p50 and p90 acknowledgement/resolution durations in seconds. Supports service and severity filters; merged incidents are excluded. | Read |
| `acknowledge_incident`, `resolve_incident` | Acknowledges or resolves an incident. API-key and M2M acknowledgement needs `acknowledged_by`; sessions act as their own member. Resolve accepts a message and `notify_subscribers`. | Write |
| `create_incident` | Opens an incident, optionally linked to a service and published on a status page. A service's configured policy pages responders. | Write |
| `update_incident` | Changes title, severity or service. Omitted fields stay unchanged; `service_id: null` detaches the service. Moving service or increasing severity can start paging. | Write |
| `reopen_incident` | Reopens a resolved incident, restarting its escalation and posting a public reopening on linked pages. Open and merged incidents return `409`. | Write |
| `post_incident_update` | Adds an update to an incident. A public update (the default) shows on its status pages and can change its status: `resolved` resolves it. It emails subscribers when posted through a named page the incident is on, or with `notify_subscribers`. An internal note stays in the app. Moving public status backwards needs `force: true`. | Write |
| `publish_incident` | Puts an incident on a status page with a public title and first update, and emails the page's subscribers unless told not to. | Write |
| `unpublish_incident` | Takes an incident off a status page. Nothing is emailed and the incident is kept. | Write, asks first |
| `list_status_pages` | Lists your status pages, each with its public address (`page_url`). | Read |
| `list_status_page_components` | Lists a status page's components in page order (monitors, heartbeats and manual components), with any status set by hand. | Read |
| `set_status_page_component_status` | Sets what a status page shows for one component, with an optional note and end time. | Write |
| `clear_status_page_component_status` | Clears that status, so the page follows the monitor again. | Write |
| `search_logs` | Searches your logs. | Read |
| `list_metric_names`, `query_metrics` | Lists your metrics, or queries one. | Read |
| `search_traces`, `get_trace` | Searches your traces, or shows one trace's spans. | Read |

### Status pages

These tools manage status pages end to end. They use the Status Pages scopes, except the four incident tools (`list_status_page_incidents`, `publish_incident`, `update_status_page_incident` and `delete_status_page_incident`), which use the Incidents scopes.

| Tool | What it does | Access |
|---|---|---|
| `get_status_page` | Shows one page and its public address (`page_url`). | Read |
| `create_status_page`, `rename_status_page` | Creates or renames a page. | Write |
| `delete_status_page` | Deletes a page. | Write, asks first |
| `update_status_page_layout` | Replaces the whole layout: groups, their order and the components in each. | Write, asks first |
| `create_status_page_component`, `update_status_page_component` | Adds a manual component (one with no monitor, whose status you set), or renames it, changes its description or sets its status. | Write |
| `delete_status_page_component` | Deletes a manual component. | Write, asks first |
| `list_status_page_monitors`, `get_status_page_monitor` | Lists the HTTP monitors, browser checks and heartbeats (cron jobs) on a page, or shows one with its page name and SLA target. | Read |
| `add_status_page_monitor`, `update_status_page_monitor` | Adds a monitor or heartbeat to a page, or changes its page name or SLA target. | Write |
| `remove_status_page_monitor` | Takes a monitor or heartbeat off a page. It keeps running. | Write, asks first |
| `list_status_page_incidents` | Lists the incidents shown on a page. | Read |
| `publish_incident` | Shows an existing incident on a page. | Write |
| `update_status_page_incident` | Changes a page incident's title or severity. Its status changes through `post_incident_update` or `resolve_incident`. | Write |
| `delete_status_page_incident` | Deletes an incident shown on a page. | Write, asks first |
| `list_status_page_maintenances`, `get_status_page_maintenance` | Lists a page's maintenance windows, or shows one. | Read |
| `schedule_status_page_maintenance`, `update_status_page_maintenance` | Schedules or changes a maintenance window. Each call names what it covers: `whole_page: true`, or the monitors in `affected_http_job_ids`, never both. Confirmed subscribers hear about new and rescheduled windows. | Write |
| `delete_status_page_maintenance` | Deletes a maintenance window. | Write, asks first |
| `list_status_page_subscribers`, `export_status_page_subscribers` | Lists a page's email subscribers, or exports them all as CSV. | Read |
| `add_status_page_subscriber` | Sends an address a confirmation link, optionally for only some components or only incidents or maintenance. | Write |
| `import_status_page_subscribers` | Imports addresses from CSV. Each gets a confirmation link; past the hourly limit they are queued. | Write |
| `remove_status_page_subscriber` | Removes a subscriber. | Write, asks first |
| `get_status_page_branding` | Shows a page's branding. | Read |
| `update_status_page_branding`, `get_status_page_branding_upload_url` | Changes branding, or gets an upload link for a logo, dark-theme logo, favicon or social image. | Write |
| `delete_status_page_branding_asset` | Removes a logo, dark-theme logo, favicon or social image. | Write, asks first |
| `get_status_page_custom_domain` | Shows a page's custom domain and the DNS records it needs. | Read |
| `set_status_page_custom_domain` | Serves a page on your own domain. | Write |
| `remove_status_page_custom_domain` | Stops serving a page on its custom domain. | Write, asks first |

### Everything else

Two more tools reach everything else the [Site Qwality API](/api-reference/) can do:

| Tool | What it does | Access |
|---|---|---|
| `find_api_operations` | Searches the API for the operation that does what you asked. | Read |
| `call_api` | Calls any operation `find_api_operations` found. | Scope of the operation, asks first |

## Safety

- **Risky actions are marked.** `delete_monitor`, `call_api` and the status page tools that delete, remove or replace something (marked "asks first" above) are flagged as destructive, so assistants that honor the flag ask you before running them. Read tools are flagged read-only.
- **Your data is data.** Results include text you and your services control, such as monitor names and log lines. The tools tell the assistant to treat that text as data, never as instructions.
- **Changes are audited.** Every change an assistant makes goes through the same API as the dashboard and shows up in your [audit log](/enterprise/audit-log/#ai-assistants) as the member who approved it, with the assistant's name, "via MCP" and the tool it used. Connecting and disconnecting an assistant are logged too.
- **Grant the least you need.** Choose read-only when you only want answers. You can reconnect with write access later.

## Partner and agency accounts

If you manage [client accounts](/partners/client-accounts/), an assistant can work in one of them when your client lets you set custom headers (Claude Code, Cursor, VS Code and Codex CLI do). Add this header next to the server URL:

```text
X-SQ-Account: <client account id>
```

It works when you signed in through the consent page. API keys cannot switch accounts. See [Working in a client account](/partners/context-switching/) for what the header changes and why a wrong id returns `404`.

## Troubleshooting

| Problem | Fix |
|---|---|
| The assistant stopped working after you revoked it, or says it is not authorized (`401`) | Connect again: **Connect** in Claude, `/mcp` in Claude Code, `codex mcp login siteqwality` in Codex, or remove and re-add the server elsewhere. |
| `403` on an action | The access you approved does not cover it. Revoke it under **AI assistants** in your personal settings and reconnect with read and write, or add the scope to your API key. A `403` can also mean your role does not allow the action, or a plan limit was reached; the message says which. |
| `404` with `X-SQ-Account` set | The client id is wrong, or you are using an API key. See [Working in a client account](/partners/context-switching/). |
| The assistant cannot find a tool for what you asked | Ask it to use `find_api_operations`. |
