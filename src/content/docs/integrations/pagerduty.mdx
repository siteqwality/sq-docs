The PagerDuty integration posts to the **Events API v2**. A monitor going down triggers a PagerDuty incident; the same monitor recovering resolves it automatically, because both events carry the same dedup key.

## What you need

An **Integration Key** (also called a routing key) from a PagerDuty service.

<Steps>

1. In PagerDuty, open the **service** you want Site Qwality to page.

2. **Integrations → add an "Events API V2" integration.**

3. Copy its **Integration Key**.

</Steps>

## Connect it

In the dashboard, go to **Manage → Integrations** and click the **PagerDuty** card. Give it a name, paste the key into **Integration Key (Events API v2)**, choose the **Region** of your PagerDuty account, and click **Add**.

Or through the API, with [`POST /integration/pagerduty`](/api-reference/operations/add_pagerduty_integration/):

```bash
curl -X POST https://api.siteqwality.com/integration/pagerduty \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "friendly_name": "Acme PagerDuty",
    "routing_key": "<events-api-v2-integration-key>",
    "region": "eu"
  }'
```

| Field | Required | Description |
|---|---|---|
| `friendly_name` | yes | Up to 256 characters. |
| `routing_key` | yes | The Events API v2 integration key. |
| `region` | no | `us` (default) or `eu`. Any other value is a 422. |

The name and key must be non-empty. The key is not validated against PagerDuty at save time, so a typo surfaces as a failed notification later, not as an error here.

The routing key is a secret: `GET /integration` never returns it. `pagerduty_routing_key` shows it as `****` followed by its last four characters (just `****` when it is shorter than 16 characters). The region is not a secret: it comes back as `external_ref.region`.

## Region

PagerDuty keeps US and EU accounts apart, and a key only works in its own region. Choose the region of your PagerDuty account: EU accounts sign in at `*.eu.pagerduty.com`. US events go to `events.pagerduty.com`, EU events to `events.eu.pagerduty.com`. A key sent to the wrong region is refused by PagerDuty and recorded as rejected.

The region is set when you add the integration. To change it, add the integration again with the other region and move your channels to it. Integrations added before the region choice existed have `external_ref: null` and send to US, as they always have.

## Add it to a notification group

Integrations deliver nothing on their own. Alerts reach one once it is a channel in a notification group that your monitors use.

<Steps>

1. Go to **Respond → Notifications**. Click a group's name to open it, or click **Add group** to make a new one.

2. Under **Notifications**, click **Add Notification Method**. Set **Notification Type** to **PagerDuty** and choose this integration under **Integration**.

3. Choose a **Severity** for the events this channel sends: **Critical** (the default), **Error**, **Warning** or **Info**.

4. Click **Done editing**, then **Update Group** (**Create Group** for a new group).

</Steps>

Through the API, create the channel with [`POST /notification`](/api-reference/operations/create_notification/):

```bash
curl -X POST https://api.siteqwality.com/notification \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "notification_group_id": "<your-group-id>",
    "type": "pagerduty",
    "details": {
      "pagerduty_integration_id": "<pagerduty-integration-id>",
      "pagerduty_severity": "critical"
    }
  }'
```

| Field | Required | Description |
|---|---|---|
| `pagerduty_integration_id` | yes | The integration UUID. |
| `pagerduty_severity` | no | `critical` (default), `error`, `warning`, or `info`. |

## Trigger and resolve

Every down/up pair shares one dedup key built from the monitor ID and the ID of the state transition that opened:

```
sq-http-<monitor-id>-<state-transition-id>
sq-browser-<browser-check-id>-<state-transition-id>
```

- **Monitor goes down** → `event_action: "trigger"`, summary `Monitor DOWN: <name>`, source set to the monitor URL, plus `custom_details` carrying the monitor, URL, and failure reason.
- **Monitor recovers** → `event_action: "resolve"` with the same dedup key and nothing else. PagerDuty closes the incident it opened.

Because the key includes the state transition, a *second* outage of the same monitor opens a *new* PagerDuty incident rather than reopening the old one. Repeated triggers within one outage collapse onto the same incident.

Summaries longer than 1024 characters are truncated to fit the Events API limit.

<Aside type="caution" title="Domain expiry alerts do not auto-close">
DNS and domain-expiry warnings are **trigger-only**: there is no recovery event for them, so they key on the DNS job plus the expiry date (`sq-dns-expiry-<job-id>-YYYY-MM-DD`). Repeated warnings about the same expiry date collapse into one PagerDuty incident, but nothing ever resolves it.

You have to close those incidents in PagerDuty yourself. Renewing the domain does not close them, and because renewal changes the expiry date, the next warning opens a **new** incident while the old one stays open.

Expiry warnings always send at severity `warning`, ignoring the channel's configured severity.
</Aside>

## Delivery behavior

Each attempt waits up to 10 seconds for PagerDuty to answer, and a redirect is never followed. A failed send is tried up to 3 times in quick succession, which is safe because the dedup key makes the call idempotent; no attempt starts so close to the run's time limit that it could not finish. A 4xx answer other than 408 or 429 means PagerDuty refused the event: it is recorded as rejected and not retried. Any other failure fails the event, and it is run up to two more times. If those fail too, the alert is dropped with no record in alert history, so pair PagerDuty with a second channel for anything you cannot afford to miss.

## Limitations

- PagerDuty channels fire for **HTTP monitors, browser checks, heartbeat (cron) monitors, domain expiry warnings, DNS record changes, log, metric and trace alert rules, and RUM issues**. TLS expiry warnings and page speed alerts do not reach PagerDuty today: a PagerDuty channel attached to a group used by those sources is skipped. See the [coverage table](/integrations/coverage/#pagerduty).
- Incidents and escalation policies do not page through PagerDuty. The integration sends monitor and alert-rule events only.
