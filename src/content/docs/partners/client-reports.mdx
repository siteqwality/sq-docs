The report comes from the API; the dashboard has no button for it. With an [M2M client](/enterprise/api-clients/) token that has `read:monitors`, exported as `ACCESS_TOKEN`:

```bash
curl "https://api.siteqwality.com/monitors/report?month=2026-07" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "X-SQ-Account: $CLIENT_ACCOUNT_ID" \
  -o acme-july.html
```

The response is **HTML, not JSON**, styled for paper. Open it in a browser and print it to PDF (the page has a print button); that PDF is what you send.

The `X-SQ-Account` header, set to the client's `account_id`, makes it a client's report. API keys cannot use that header, so a client's report needs an M2M token. Without the header you get your own account's report, which a full-access [API key](/getting-started/account-and-team/#generate-api-keys) can also pull (it needs `read:monitors` if you limited its scopes).

## Choosing the month

| `month` | Result |
|---|---|
| omitted | The last **complete** month, which is what a monthly report normally covers |
| `2026-07` | That UTC calendar month |
| the current month | Allowed. The report says on its face that the month is not finished |
| a future month | Refused |
| more than 13 months ago | Refused |

## What the report contains

- Per-monitor uptime for the month, against the account's monitors.
- An outage log: when each outage started, when it ended, how long it lasted.
- The month's totals.

The document also states its own boundaries:

<Steps>

1. **HTTP monitors only.** Heartbeat monitors and browser checks are named and counted as excluded.

2. **Uptime is a daily rollup rebuilt at 03:00 UTC.** A report for the month in progress is month-to-date. A report for a finished month pulled before 03:00 UTC on the 1st may be missing the last day, and says so.

3. **The outage log is current to the minute**, so it can disagree slightly with the uptime figures at a month edge.

</Steps>

## Branding

The report takes its logo, brand color and display name from status page branding (each status page's **Branding** tab, under **Manage → Status Pages**), resolved in this order:

<Steps>

1. **The client's own status page branding**, if the client has a status page.
2. **Your branding**, if they do not. This is the usual case for a managed client.
3. **Neither**, in which case the report is plain and unbranded.

</Steps>

Site Qwality branding is never used as a fallback.

## A monitor paused during an outage

If a monitor was failing when it was paused, its outage is measured to its **last actual check**, not to now, so a monitor paused mid-outage stops accruing downtime. Monitors on accounts nobody signs into are paused automatically after long enough dormancy, and those are the clients whose reports you send rather than read.

## Automating it

The same M2M token can pull every client's report on a schedule. Copy each client's account ID from **Manage → Clients** into `clients.txt`, one per line:

```bash
# One report per client, for last month. $ACCESS_TOKEN is an M2M token with read:monitors.
while read -r id; do
  curl -s "https://api.siteqwality.com/monitors/report" \
    -H "Authorization: Bearer $ACCESS_TOKEN" \
    -H "X-SQ-Account: $id" \
    -o "report-$id.html"
  sleep 1
done < clients.txt
```

`GET /partner/accounts` refuses M2M tokens and API keys, so the script cannot list clients itself. See [roles and access](/partners/overview/#roles-and-access).
