To build a client's monitoring, use the ordinary API with one extra header, set to the client's `account_id`. With an [M2M client](/enterprise/api-clients/) token exported as `ACCESS_TOKEN` (this call needs `read:monitors`):

```bash
curl https://api.siteqwality.com/http/jobs \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "X-SQ-Account: $CLIENT_ACCOUNT_ID"
```

That request lists the **client's** monitors. Every endpoint behaves as though you were signed in as that client, except the few that [refuse the header](#endpoints-that-refuse-the-header).

In the dashboard the same thing happens when you open a client from the **Clients** page. A banner shows which client you are in, and leaving it puts you back on your own account.

## What the header changes, and what it does not

| Changes | Stays yours |
|---|---|
| Which account the request reads and writes | Who you are, and your role |
| Quotas, entitlements and feature gates | The audit trail's record of who acted |

Every change you make inside a client is recorded in **that client's** [audit log](/enterprise/audit-log/), attributed to you as a partner rather than to one of the client's own users, so your client can see what you did on their behalf.

## Which credentials may switch

| Credential | May send `X-SQ-Account` |
|---|---|
| Dashboard session | yes |
| [M2M client](/enterprise/api-clients/) | yes |
| [API key](/getting-started/account-and-team/#generate-api-keys) | **no** |

API keys are excluded because a key with no scope list is unrestricted, so the header would hand it every client account. Use a session, or an M2M client with the scopes it needs.

The header does not widen what a credential may do: an M2M client scoped to `read:monitors` can read a client's monitors but not write them, as on your own account.

## Endpoints that refuse the header

These prefixes return `404` in client context:

| Prefix | Why |
|---|---|
| `/account` | Team, roles, invitations and SSO act on **your** organization, so honoring the header would edit your own team while appearing to edit the client's. |
| `/auth` | Same reason. |
| `/billing` | A client has no payment method; its entitlements come from the [bundle you set](/partners/client-accounts/#set-a-clients-bundle). |
| `/partner` | Client accounts cannot have client accounts. |
| `/admin` | Internal staff surface. |
| `/v1/api-keys`, `/v1/audit-events` | A client's API keys and audit log, which sit under `/account` on the older paths. |

To invite a client's own user to their account, ask us and we will do it for you.

## Every rejection is a 404

A wrong `X-SQ-Account` value never returns `401` or `403`. An unknown account id, an account that is not yours, a client you removed and a malformed uuid all get the same `404` with no detail, so account ids cannot be probed.

If a request that works on your own account returns `404` with the header set, check the client id first, then whether the path is one of the refused prefixes above.

## Suspended and removed clients

| Client state | Reads | Writes |
|---|---|---|
| Live | yes | yes |
| Suspended | yes | no |
| Removed | no | no |

A suspended client stays readable so you can see what you have and export it. If **your** partner account is suspended, your clients are suspended too, and the same rule applies to every one of them.
