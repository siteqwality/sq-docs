Field-by-field reference for the **`@siteqwality/rum`** browser SDK. For install and first-run, see the [SDK overview](/sdk/overview/) and the [RUM quickstart](/observability/rum/quickstart/).

## Init options (`RumConfig`)

```javascript
import { SiteQwalityRUM } from '@siteqwality/rum';

await SiteQwalityRUM.init({ applicationId: '...', clientToken: '...' });
```

| Option | Type | Default | Description |
|---|---|---|---|
| `applicationId` | string | required | The [RUM application](/observability/rum/reference/) ID. |
| `clientToken` | string | required | The application's public client token. Sent as the bearer token on every payload. |
| `service` | string | none | Logical service name, stored in the SDK's context. |
| `version` | string | none | App version. Attached to every error event and used for [source-map](/observability/rum/how-to/source-maps/) matching. |
| `env` | string | none | Environment label (`prod`, `staging`, ...), stored in the SDK's context. |
| `apiBase` | string | none | Deprecated and unused. Remote config is fetched from `ingestBase`; the option is kept for backwards compatibility. |
| `ingestBase` | string | `https://rum.siteqwality.com` | Override for the RUM ingest host (event delivery and config fetch). |
| `replayBase` | string | `https://replay.siteqwality.com` | Override for the replay segment endpoint. |

`init` is idempotent: a second call while an instance exists is a no-op. On init the SDK fetches its server-side config (session filters, privacy settings and excluded resources) from `GET {ingestBase}/v1/config`, authenticated by the client token, and refreshes it every 5 minutes. The fetch has a 5 second timeout and never throws: on any failure (network error, non-2xx, unexpected response shape) the SDK falls back to safe defaults, meaning no session filters, no excluded resources, `mask_inputs: true` / `mask_text: false` and `hide_action_text: false`. A failed refresh keeps the last known config.

## Public methods

### `SiteQwalityRUM.init(options)`

Starts the SDK: creates or restores the session, fetches config, starts all collectors, and begins sampling evaluation. Returns a promise; `await` it if you call other methods immediately after.

### `SiteQwalityRUM.setUser(user)`

| Field | Type | Description |
|---|---|---|
| `id` | string | Your internal user ID. Used by `custom` session filters (`has_user`). |
| `email` | string | User email. |
| `name` | string | Display name. |

All fields optional. `id` and `email` attach to every event recorded after the call; `name` stays in the browser. Call after `init()`; calls made before it are ignored.

From 1.0.6 that includes page views and vitals, so every session shows its user in **RUM → Sessions** and the session search finds it. Earlier versions attached the user to error and detail events only, so a session without detail capture showed no user.

Each call replaces the previous user. Call `setUser({})` on logout.

### `SiteQwalityRUM.setGlobalAttribute(key, value)`

Adds a string attribute to every error and detail event recorded after the call, in `custom_attributes`. Page views and vitals do not carry it. Setting an existing key replaces its value, and per-call `context` wins over a global attribute with the same key.

```javascript
SiteQwalityRUM.setGlobalAttribute('plan', 'pro');
```

| Limit | Value |
|---|---|
| Attributes | 50 |
| Key length | 128 characters |
| Value length | 1,024 characters |

A longer value is cut to 1,024 characters. A blank or overlong key, a non-string, or a new key past the 50th is ignored without an error. Global attributes are stored like `context`; see the warning below. Call after `init()`; calls made before it are ignored. Added in 1.0.6.

### `SiteQwalityRUM.removeGlobalAttribute(key)`

Stops attaching `key` to events recorded after the call. Removing a key that is not set does nothing. Added in 1.0.6.

### `SiteQwalityRUM.addError(error, context?)`

Records a custom error alongside auto-captured ones (recorded with `error_source: "custom"`, message, and stack). Custom errors count toward `error` session filters. The `context` parameter **is stored**: it is merged into the event's `custom_attributes` and retained for 30 days. See the warning under `addAction` below.

### `SiteQwalityRUM.addAction(name, context?)`

Records a custom action with `action_type: "custom"` and `action_target: name`. Actions always increment the session's action count (used by `custom` filters with `min_actions`); the individual action event is only shipped when detail capture is active for the session. The `context` parameter **is stored**: it is merged into the event's `custom_attributes` and retained for 30 days.

If the application [hides element text in click names](/observability/rum/how-to/remote-config/#hiding-element-text-in-click-names), a `name` ending in bracketed text is stored without it, so `checkout[step 2]` becomes `checkout`. Leave square brackets out of action names.

<Aside type="danger" title="Do not put personal data in context">
The `context` argument of `addError` and `addAction` **is stored**. The SDK merges it into the event's `custom_attributes`, a `Map(String, String)` column on the `rum_events` table, and it is retained for **30 days** on every plan, free and paid alike. Buying a larger RUM Analyze pack raises the number of sessions you can record, not how long their events are kept, so there is no way to make that window longer.

An earlier version of this page said `context` was "accepted for forward compatibility and is not attached to the event today". That was wrong. If you have been passing user objects, email addresses, order contents or anything else that identifies a person, that data is in `rum_events` now and stays there until its 30-day window expires.

One timing difference is worth knowing. `addError` always ships, so its `context` is always stored. An `addAction` event is only shipped when detail capture is active for the session, so its `context` is stored only for filter-matched sessions. The action *count* is always incremented either way.

No dashboard screen or API response renders `custom_attributes` today. Do not treat that as a safeguard. The data is stored, it is readable by anyone with database access, and a future release may surface it in the product.

Global attributes set with `setGlobalAttribute` are stored the same way, on every error and detail event.

Pass low-cardinality, non-personal labels only, such as `{ feature: 'checkout', step: '3' }`.
</Aside>

## Click names

With detail capture active, every click is recorded as an action whose `action_target` names the clicked element:

| Element | Name |
|---|---|
| Has `data-sq-action-name`, or sits inside an element that has it | That value, trimmed, up to 100 characters, with square brackets turned into parentheses |
| Has an `id` | `#id` |
| Anything else | Tag, up to two classes, then up to 30 characters of its text (or else its full `aria-label`) in brackets, such as `button.btn.primary[Send message]` |

The bracketed text can contain what your users typed or see, such as names or message previews. Two ways to keep it out:

- Set `data-sq-action-name` on the element to give it a fixed name: `<button data-sq-action-name="Send message">`. Needs SDK 1.0.6.
- Turn on [hiding element text in click names](/observability/rum/how-to/remote-config/#hiding-element-text-in-click-names) for the application. Clicks are then named without the brackets, such as `button.btn.primary`. Ingest applies it for every SDK version, and from 1.0.6 the browser stops sending the text too.

## What is collected when

| Signal | Always-on | Detail (filter-activated) |
|---|---|---|
| Page views, load / DOM-ready timing | yes | |
| Web Vitals: `lcp_ms`, `fcp_ms`, `cls`, `inp_ms`, `ttfb_ms` | yes | |
| Error events (message, stack, fingerprinting) | yes | |
| Action count | yes | |
| Individual click / action events | | yes |
| Resource timings (url, duration, transfer size) | | yes |
| Long tasks (browser `longtask` entries, with duration) | | yes |
| Session replay (rrweb) | | with `capture_replay: true` |

Detail capture activates when any enabled [session filter](/observability/rum/how-to/session-filters/) matches; replay additionally requires `capture_replay: true` on the matching filter.

From 1.0.5 the SDK skips resource timings matching the application's [excluded resources](/observability/rum/how-to/remote-config/#excluded-resources). Ingest drops them for every SDK version.

## Sampling evaluation

Filters are evaluated in the browser every 5 seconds against the running session state (error count, LCP, CLS, page count, action count, user presence). Activation is one-way: once detail or replay capture turns on for a session, it stays on for that session.

| `filter_type` | Condition keys | Matches when |
|---|---|---|
| `error` | `has_error` | The session has thrown at least one error. |
| `slow_performance` | `lcp_gt_ms`, `cls_gt` | LCP or CLS exceeds the threshold. |
| `custom` | `has_user`, `min_actions` | User is identified and/or action count reached. |

## Sessions

| Behavior | Value |
|---|---|
| Storage | `sessionStorage` key `sq_rum_session`. |
| Session ID | `crypto.randomUUID()`. |
| Expiry | After 15 minutes of inactivity, or 4 hours total, a new session starts. |

## Batching and delivery

The SDK sends three event streams to `ingestBase`, each independently batched:

| Stream | Endpoint | Contents |
|---|---|---|
| Measures | `POST /v1/measure` | Views and vitals. |
| Detail events | `POST /v1/events` | Resources, actions, long tasks. |
| Errors | `POST /v1/errors` | Error events. |

A batch flushes every 10 seconds, immediately at 50 queued events, and on tab hide or page unload. Every batch is a `fetch` with `keepalive`, so the last one outlives the page, authenticated by the `Authorization` header and sent without cookies (`credentials: 'omit'`). A batch over 60 KB goes without `keepalive`, since browsers refuse larger keepalive requests. Delivery is fire-and-forget; failed sends are not retried. Before SDK 1.0.2 the last batch used `navigator.sendBeacon` and never arrived, so upgrade if you pin an older version.

## Replay recording

- rrweb is lazy-loaded only when a replay-enabled filter activates, keeping the base bundle small.
- Segments flush at 100 rrweb events and at least every 30 seconds, to `POST {replayBase}/v1/segments`.
- Input masking (`mask_inputs`) and text masking (`mask_text`) come from the application's [privacy settings](/observability/replay/reference/#privacy-settings), not from anything you pass to `init()`. A new application is created with input masking on and text masking off, but the value actually stored on your application is what the SDK obeys, and an application created earlier may store `mask_inputs: false`. Check it.
