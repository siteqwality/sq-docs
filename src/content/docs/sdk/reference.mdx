Field-by-field reference for the **`@siteqwality/rum`** browser SDK. For install and first-run, see the [SDK overview](/sdk/overview/) and the [RUM quickstart](/observability/rum/quickstart/).

## Init options (`RumConfig`)

```javascript
import { SiteQwalityRUM } from '@siteqwality/rum';

SiteQwalityRUM.init({ applicationId: '...', clientToken: '...' });
```

| Option | Type | Default | Description |
|---|---|---|---|
| `applicationId` | string | required | The [RUM application](/observability/rum/reference/) ID. |
| `clientToken` | string | required | The application's public client token. Sent as the bearer token on every payload. |
| `service` | string | none | Logical service name, kept in the SDK's context. Not sent with any event today. |
| `version` | string | none | App version. Attached to every error event and used for [source-map](/observability/rum/how-to/source-maps/) matching. |
| `env` | string | none | Environment label (`prod`, `staging`, ...), kept in the SDK's context. Not sent with any event today. |
| `apiBase` | string | none | Deprecated and unused. Remote config is fetched from `ingestBase`; the option is kept for backwards compatibility. |
| `ingestBase` | string | `https://rum.siteqwality.com` | Override for the RUM ingest host (event delivery and config fetch). |
| `replayBase` | string | `https://replay.siteqwality.com` | Override for the replay segment endpoint. |
| `recorderUrl` | string | `recorder-<version>.min.js` next to the loaded `sdk.min.js` | CDN bundle only: where to load the replay recorder from. Set it when you self-host the SDK files or your Content Security Policy restricts script sources. The npm package bundles the recorder through your bundler and ignores this option. Added in 1.1.0. |
| `ignoreErrors` | `Array<string \| RegExp>` | `[]` | Errors to drop in the browser. A string drops errors whose message contains it (case-sensitive); a RegExp is tested against the message. See [error filtering](#error-filtering). Added in 1.1.0. |
| `beforeSend` | function | none | `(event, kind) => event \| false \| null \| void`. Inspect, change or drop each error before it is sent. See [error filtering](#error-filtering). Added in 1.1.0. |

`init` is idempotent: a second call while an instance exists is a no-op. Collection starts synchronously inside the call: the session, transports and collectors are running, and the initial page view is recorded, before `init` returns. It then fetches the server-side config (recording rules, privacy settings, excluded resources and frustration ignore selectors) from `GET {ingestBase}/v1/config`, authenticated by the client token, and refreshes it every 5 minutes. The fetch has a 5 second timeout and never throws: on any failure (network error, non-2xx, unexpected response shape) the SDK falls back to safe defaults, meaning no recording rules, no excluded resources, `mask_inputs: true` / `mask_text: false` and `hide_action_text: false`. A failed refresh keeps the last known config.

Until the config arrives, errors and measures are sent as usual, while detail events (resources, actions, long tasks) wait in a buffer of up to 500 events, oldest dropped first. Once the config is applied and rules are evaluated, the buffer is sent (with excluded resources removed and click text hidden if the application says so) when detail capture is on for the session, and discarded otherwise.

## Public methods

Public methods never throw. Invalid input is ignored, and an internal failure is swallowed so it cannot break your page.

### `SiteQwalityRUM.init(options)`

Starts the SDK: creates or restores the session, starts all collectors, then fetches the config and evaluates recording rules. It is fire-and-forget. It returns a Promise that settles once the config is applied or has failed to load; you never need to `await` it, and the other methods work as soon as `init` returns.

With the npm package, calls to any other method made before `init()` are ignored. The [CDN snippet](/observability/rum/quickstart/#2-install-the-sdk) queues them, along with errors the page throws before the SDK loads, and replays them once it loads (`init` first).

### `SiteQwalityRUM.setUser(user)`

| Field | Type | Description |
|---|---|---|
| `id` | string | Your internal user ID. Used by `custom` recording rules (`has_user`). |
| `email` | string | User email. |
| `name` | string | Display name. |

All fields optional. `id` and `email` attach to every event recorded after the call; `name` stays in the browser. Call after `init()`; calls made before it are ignored.

From 1.0.6 that includes page views and vitals, so the session shows its user in **RUM → Sessions** and the session search finds it. Earlier versions attached the user to error and detail events only, so a session with no errors and no detail capture showed no user.

Each call replaces the previous user. Call `setUser({})` on logout.

### `SiteQwalityRUM.setGlobalAttribute(key, value)`

Adds a string attribute to every error and detail event recorded after the call, in `custom_attributes`. Page views and vitals do not carry it. Setting an existing key replaces its value, and per-call `context` wins over a global attribute with the same key.

```javascript
SiteQwalityRUM.setGlobalAttribute('plan', 'pro');
```

| Limit | Value |
|---|---|
| Attributes | 50 |
| Key length | 128 characters |
| Value length | 1,024 characters |

A longer value is cut to 1,024 characters. A blank or overlong key, a non-string, or a new key past the 50th is ignored without an error. Global attributes are stored like `context`; see the warning below. Call after `init()`; calls made before it are ignored. Added in 1.0.6.

### `SiteQwalityRUM.removeGlobalAttribute(key)`

Stops attaching `key` to events recorded after the call. Removing a key that is not set does nothing. Added in 1.0.6.

### `SiteQwalityRUM.addError(error, context?)`

Records a custom error alongside auto-captured ones (recorded with `error_source: "custom"`, message, and stack). It accepts any value: a non-`Error` is recorded with `String(value)` as its message and an empty stack. It goes through the same [error filtering](#error-filtering) as captured errors, and once sent counts toward `error` recording rules. The `context` parameter **is stored**: it is merged into the event's `custom_attributes` and retained for 30 days. See the warning under `addAction` below.

### `SiteQwalityRUM.addAction(name, context?)`

Records a custom action with `action_type: "custom"` and `action_target: name`. Actions always increment the session's action count (used by `custom` rules with `min_actions`); the individual action event is only shipped when detail capture is active for the session. The `context` parameter **is stored**: it is merged into the event's `custom_attributes` and retained for 30 days.

If the application [hides element text in click names](/observability/rum/how-to/remote-config/#hiding-element-text-in-click-names), a `name` ending in bracketed text is stored without it, so `checkout[step 2]` becomes `checkout`. Leave square brackets out of action names.

<Aside type="danger" title="Do not put personal data in context">
The `context` argument of `addError` and `addAction` **is stored**. The SDK merges it into the event's `custom_attributes`, a `Map(String, String)` column on the `rum_events` table, and it is retained for **30 days** on every plan, free and paid alike. Buying a larger RUM Analyze pack raises the number of sessions you can record, not how long their events are kept, so there is no way to make that window longer.

An earlier version of this page said `context` was "accepted for forward compatibility and is not attached to the event today". That was wrong. If you have been passing user objects, email addresses, order contents or anything else that identifies a person, that data is in `rum_events` now and stays there until its 30-day window expires.

One timing difference is worth knowing. `addError` ships unless [error filtering](#error-filtering) drops it, so its `context` is normally stored. An `addAction` event is only shipped when detail capture is active for the session, so its `context` is stored only for filter-matched sessions. The action *count* is always incremented either way.

No dashboard screen or API response renders `custom_attributes` today. Do not treat that as a safeguard. The data is stored, it is readable by anyone with database access, and a future release may surface it in the product.

Global attributes set with `setGlobalAttribute` are stored the same way, on every error and detail event.

Pass low-cardinality, non-personal labels only, such as `{ feature: 'checkout', step: '3' }`.
</Aside>

## Error filtering

Every error, `addError` included, passes these steps in order. Only an error that survives all of them is sent.

1. **Default noise rules.** After trimming the message and removing one leading `Uncaught `, the SDK drops:
   - `ResizeObserver loop completed with undelivered notifications` and `ResizeObserver loop limit exceeded`.
   - `Script error.` (or `Script error`) with no stack frames: a cross-origin script error the browser hides details of.
   - Errors whose stack frames all come from browser extensions (`chrome-extension:`, `moz-extension:`, `safari-extension:`, `safari-web-extension:`, `webkit-masked-url:` or `ms-browser-extension:` URLs). With no frames, the error's file name is checked instead.
2. **`ignoreErrors`.** Strings match as case-sensitive substrings of the normalised message; a RegExp is tested against it.
3. **Burst limit.** Each distinct message (its first 200 characters) may send 10 errors, then one more every 10 seconds. A page load sends at most 500 errors in all.
4. **`beforeSend(event, kind)`.** `event` is a `RumErrorEvent`; `kind` is `'error'` (only errors call it in 1.1). Return `false` or `null` to drop the error, an object to replace it, or nothing to send the event (with any changes you made to it). If the hook throws, the original event is sent unchanged. Afterwards the SDK sanitises the URLs in `url`, `error_message` and `error_stack` again and restores `session_id`, `view_id`, `event_id` and `timestamp`, so the hook cannot reintroduce a sensitive URL or move the error to another session.

```javascript
SiteQwalityRUM.init({
  applicationId: 'abc123',
  clientToken: 'pub_def456',
  ignoreErrors: ['Request aborted', /Loading chunk \d+ failed/],
  beforeSend(event) {
    if (event.error_message.includes('third-party-widget')) return false;
    event.error_message = event.error_message.replace(/order \d+/g, 'order <id>');
  },
});
```

The ingest server applies the same default noise rules for every SDK version, and keeps at most 10 errors per session and message in each batch. A dropped error never marks the session as errored, never triggers an `error` recording rule or an error click, and is never billed.

## Click names

With detail capture active, every click is recorded as an action whose `action_target` names the clicked element. From 1.1.0 the clicked element is the nearest of these at or above the click target: a link, button, `role="button"` or `role="link"` element, form control, `label`, `summary`, or an element with `data-sq-action-name`; otherwise the click target itself. A click on an icon inside a button is therefore named and grouped as the button.

| Element | Name |
|---|---|
| Has `data-sq-action-name`, or sits inside an element that has it | That value, trimmed, up to 100 characters, with square brackets turned into parentheses |
| Has an `id` | `#id` |
| Anything else | Tag, up to two classes, then up to 30 characters of its text (or else its full `aria-label`) in brackets, such as `button.btn.primary[Send message]` |

The bracketed text can contain what your users typed or see, such as names or message previews. Two ways to keep it out:

- Set `data-sq-action-name` on the element to give it a fixed name: `<button data-sq-action-name="Send message">`. Needs SDK 1.0.6.
- Turn on [hiding element text in click names](/observability/rum/how-to/remote-config/#hiding-element-text-in-click-names) for the application. Clicks are then named without the brackets, such as `button.btn.primary`. Ingest applies it for every SDK version, and from 1.0.6 the browser stops sending the text too.

## Frustration signals

From 1.1.0 a click carries at most one frustration signal, in this order of precedence: `error_click`, then `rage_click`, then `dead_click`. Signals ride on click events, so they are recorded only for sessions with detail capture.

| Signal | When |
|---|---|
| `error_click` | An error is sent (after [filtering](#error-filtering)) within 1 second after the click. The latest pending click gets it. |
| `rage_click` | The third click on the same element within 1 second of the first. A burst continues while each click follows the previous one within 1 second, and gets one rage click in all. |
| `dead_click` | A click on a link with `href`, an enabled button, a `role="button"` or `role="link"` element, an `input` of type `button`, `submit` or `reset`, a `summary`, or an element with `onclick`, after which nothing happens for 1 second: no DOM change, no history change, no new resource load, and the page stays visible. Clicks with a modifier key, on `a[download]`, or on a link with a `target` other than `_self` never count. |

To exempt an element from rage and dead clicks, add the `data-sq-no-frustration` attribute to it or an ancestor, or list a matching CSS selector in the application's [frustration ignore selectors](/observability/rum/how-to/remote-config/#ignoring-elements-for-frustration-signals). Error clicks still apply.

A click event is sent when its 1 second window closes, or without a verdict at `pagehide`. The session's action count goes up immediately.

## What is collected when

| Signal | Always-on | Detail (rule-activated) |
|---|---|---|
| Page views (with `loading_type`), load / DOM-ready timing | yes | |
| Web Vitals: `lcp_ms`, `fcp_ms`, `cls`, `inp_ms`, `ttfb_ms` | yes | |
| Error events (message, stack, fingerprinting) | yes | |
| Action count | yes | |
| Individual click / action events | | yes |
| Resource timings (url, duration, transfer size) | | yes |
| Long tasks (browser `longtask` entries, with duration) | | yes |
| Session replay (rrweb) | | with `capture_replay: true` |

Detail capture activates when any enabled [recording rule](/observability/rum/how-to/session-filters/) matches; replay additionally requires `capture_replay: true` on the matching rule.

From 1.0.5 the SDK skips resource timings matching the application's [excluded resources](/observability/rum/how-to/remote-config/#excluded-resources). Ingest drops them for every SDK version.

## Page views and Web Vitals

- A page view is recorded at `init` and whenever the page URL changes through `pushState`, `replaceState`, `popstate` or `hashchange`, but only if the URL differs from the current view's after sanitising. Query strings are removed by default, so a change to only those is not a new view.
- Fragments are removed too, except a hash route (`#/path` or `#!/path`), which is kept like a path so hash-routed apps get one view per route. A hash route that carries parameters (`=` or `&`, such as `#/access_token=...`) is removed like any other fragment.
- Each view carries `loading_type`: `initial_load` for the document's first view, `route_change` for the rest.
- Load timing comes from the browser's navigation timing, for the initial load only: `load_time_ms` is `loadEventEnd` and `dom_ready_ms` is `domContentLoadedEventEnd`, each sent only when above zero. If the page has not finished loading at `init`, the view is sent without them and a separate measure with the two timings follows after the `load` event. Route changes carry no timings.
- Web Vitals belong to the document's initial view: its session, view ID and URL as captured at `init`. A vital reported late, after a route change or a long idle spell, still goes there, and never starts a new session.

## Rule evaluation

[Recording rules](/observability/rum/how-to/session-filters/) are evaluated in the browser against the running session state (errors, LCP, CLS, action count, user presence), immediately:

- when the config loads, and on every refresh,
- after every error sent (filtered errors do not count),
- after every Web Vital,
- after every action,
- after `setUser`.

There is no timer. Activation is one-way: once detail or replay capture turns on for a session, it stays on for that session. The decision and the action count are kept per session and tab in `sessionStorage` (key `sq_rum_rules:<session id>`), so they survive page loads: detail capture resumes at once, and replay resumes once the config arrives if an enabled rule still has `capture_replay: true`. A `min_actions` rule can therefore match across several page loads.

| `filter_type` | Condition keys | Matches when |
|---|---|---|
| `error` | `has_error` | The session has sent at least one error. |
| `slow_performance` | `lcp_gt_ms`, `cls_gt` | LCP or CLS exceeds the threshold. |
| `custom` | `has_user`, `min_actions` | User is identified and/or action count reached. `{}` matches every session. A rule with any other key never matches. |

## Sessions

| Behavior | Value |
|---|---|
| Storage | `sessionStorage` key `sq_rum_session`, so each tab has its own session. |
| Session ID | `crypto.randomUUID()`. |
| Activity | User input (pointer down, key down, scroll, touch start; counted at most once every 5 seconds), the tab becoming visible, and a new page view. Events the SDK sends on its own never count. |
| Expiry | After 15 minutes without activity, or 4 hours total, a new session starts. |
| Rotation | Checked on the next activity or the next event other than a vital. The new session starts with a fresh page view for the current URL (`route_change`, no timings); detail capture and replay start over, the recorder flushes and stops, the pre-config buffer is cleared, and rules are evaluated again. |

## Batching and delivery

The SDK sends three event streams to `ingestBase`, each independently batched:

| Stream | Endpoint | Contents |
|---|---|---|
| Measures | `POST /v1/measure` | Views and vitals. |
| Detail events | `POST /v1/events` | Resources, actions, long tasks. |
| Errors | `POST /v1/errors` | Error events. |

A batch flushes every 10 seconds, immediately at 50 queued events, and on tab hide or page unload. Every batch is a `fetch` with `keepalive`, so the last one outlives the page, authenticated by the `Authorization` header and sent without cookies (`credentials: 'omit'`). A batch over 60 KB goes without `keepalive`, since browsers refuse larger keepalive requests. From SDK 1.0.3 a batch that fails with a 429, 408, 5xx or network error is kept and retried with jittered exponential backoff, waiting at least the server's `Retry-After` and at most 5 minutes between attempts. A 401 or 403 stops sending for the rest of the page, and any other 4xx drops the batch. Each stream holds up to 1,000 events while it waits, dropping the oldest past that. Before SDK 1.0.2 the last batch used `navigator.sendBeacon` and never arrived, so upgrade if you pin an older version.

## Replay recording

- The recorder (rrweb) loads only when a rule with `capture_replay: true` matches, keeping the base bundle small. The CDN build fetches `recorder-<version>.min.js` from next to `sdk.min.js`, or from [`recorderUrl`](#init-options-rumconfig).
- Recording starts when the rule matches. Nothing before that moment is buffered, so an `error` rule's replay starts at the error. On later page loads in the same session and tab, recording resumes once the config arrives.
- Segments flush at 100 rrweb events and at least every 30 seconds, to `POST {replayBase}/v1/segments`.
- Input masking (`mask_inputs`) and text masking (`mask_text`) come from the application's [privacy settings](/observability/replay/reference/#privacy-settings), not from anything you pass to `init()`. A new application is created with input masking on and text masking off, but the value actually stored on your application is what the SDK obeys, and an application created earlier may store `mask_inputs: false`. Check it.
