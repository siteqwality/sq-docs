By the end of this guide you will have:

1. A Site Qwality account.
2. An HTTP check running every 10 minutes against `https://mock.codes/200`.
3. Watched the check fail and recover, with a down and a recovery email landing in your inbox.

Total time: about five minutes.

## 1. Create an account

<Steps>

1. Go to [app.siteqwality.com/auth/signup](https://app.siteqwality.com/auth/signup).

2. Sign up with an email link, Google, GitHub, or email and password. Each creates a fresh account in the free tier. Email sign-up sends a link and a six-digit code: open the link or enter the code on the sign-up screen. No credit card required.

3. You'll land on the empty dashboard. The left sidebar has every product area; the right column has the "Add your first monitor" prompt that walks you through the same flow as this guide.

</Steps>

<Aside type="tip" title="Notifications are already wired up">
On signup, Site Qwality creates a notification group named **Default** with your sign-up email as the destination and a 3-minute delay. It is your account's default group, so new monitors are attached to it unless you choose otherwise, and you can skip notification setup for now. To customize (add Slack, change the email, route different monitors to different groups), see [who gets notified](/incident-management/notifications/default-routing/).
</Aside>

## 2. Create the HTTP check

<Tabs syncKey="interface">
<TabItem label="Dashboard">

<Steps>

1. Go to **Observe → Monitors**, open **Add Monitor** and choose **HTTP Monitor**.

2. Fill in the form:
   - **Name:** `Mock 200 endpoint`
   - **URL or IP:** `https://mock.codes/200`
   - **Check Interval:** `5m`, the free-plan minimum
   - **Method:** `GET` (under **Request**, the default)
   - Leave the notification groups under **Alerting** on their default. Your account's auto-created group is pre-selected.
   - Leave everything else as default.

3. Click **Submit**. The check runs immediately; the first result appears within a few seconds.

</Steps>

</TabItem>
<TabItem label="API">

If you'd rather start from the API, generate a key first under **Settings → API keys**, export it, and POST:

```bash
export SITEQWALITY_API_KEY="<your API key>"

curl -X POST https://api.siteqwality.com/http/job \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "friendly_name": "Mock 200 endpoint",
    "method": "GET",
    "uri": "https://mock.codes/200",
    "timeout_ms": 15000,
    "run_interval_seconds": 600,
    "monitor_tls": false,
    "monitor_dns": false
  }'
```

You'll get back a `201 Created` with the full job object. Save the `id`, since you'll use it to fetch results, update the check, or delete it later.

Omitting `group_notification_ids` attaches the monitor to your account's default notification group (the **Default** group created at signup), so the email lands in your inbox without further setup. To target a specific group, pass its UUID in `group_notification_ids` (`GET /notification_group` lists them). An explicit `[]` creates a monitor that notifies no one.

</TabItem>
</Tabs>

## 3. Confirm it's working

<Steps>

1. Open the monitor's detail page. The status badge should flip to **Success** within one minute.

2. Scroll down to **Recent Checks**. You'll see one row per check result with status code, latency, and the location it ran from.

3. Force a failure: edit the check, change the URL to `https://mock.codes/500`, save.

4. On the next tick the monitor flips to **Failure**. The Default group waits 3 minutes, then emails you if the monitor is still down.

5. Flip the URL back to `/200`. The monitor recovers, and you'll get a recovery email right away.

</Steps>

<Aside type="tip">
If the email never arrives, check your spam folder and confirm the channel email matches your inbox. Site Qwality only retries failed sends a few times. The [Notification channels reference](/incident-management/notifications/channels/) covers the gotchas.
</Aside>

## What just happened

- Your check ran on a schedule from the default check location, `aws-us-east-1` (Virginia, AWS). On a paid uptime plan a new monitor also runs from a second cloud provider by default, and you can add more [check locations](/uptime-monitoring/overview/#check-locations) to the same monitor.
- The result was compared against the assertions on the monitor (status code in the success list, no body keyword search).
- A change in monitor status (success → failure) sent a down alert to the monitor's **notification group**, which fanned out to its channels after the group's 3-minute delay. Each channel renders the alert in its own format.
- When the URL recovered, the group sent a recovery message at once.
- No incident opened: monitor alerts go straight to notification groups. Incidents open when you link a monitor to a service that creates incidents automatically, or when you open one by hand.

You can wire this up much further: link the monitor to a service so a failure opens an incident, then on-call schedules pick *who* gets the page, escalation policies decide what to do if no one acknowledges, and a status page can publish the incident publicly. All of that is in [Incident Management](/incident-management/overview/).
