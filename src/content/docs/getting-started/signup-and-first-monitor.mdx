By the end of this guide you will have:

1. A Site Qwality account.
2. An HTTP check running every 5 minutes against `https://mock.codes/200`.
3. Watched the check fail and recover, with a down and a recovery email in your inbox.

## 1. Create an account

<Steps>

1. Go to [app.siteqwality.com/auth/signup](https://app.siteqwality.com/auth/signup).

2. Sign up with an email link, Google, GitHub, or email and password. Email sign-up sends a link and a six-digit code: open the link or enter the code on the sign-up screen. No credit card is required.

</Steps>

Every new account has a notification group named **Default** that emails your sign-up address after a 3-minute delay. New monitors use it unless you choose otherwise, so you can skip notification setup for now. See [who gets notified](/incident-management/notifications/default-routing/) to change it.

## 2. Create the HTTP check

<Tabs syncKey="interface">
<TabItem label="Dashboard">

<Steps>

1. Go to **Observe → Monitors**, open **Add Monitor** and choose **HTTP Monitor**.

2. Fill in the form:
   - **Name:** `Mock 200 endpoint`
   - **URL or IP:** `https://mock.codes/200`
   - **Check Interval:** `5m`, the free-plan minimum
   - **Method:** `GET` (under **Request**, the default)
   - Leave the notification groups under **Alerting** on their default. Your account's auto-created group is pre-selected.
   - Leave everything else as default.

3. Click **Submit**. The check runs immediately; the first result appears within a few seconds.

</Steps>

</TabItem>
<TabItem label="API">

Generate a key under **Settings → API keys**, export it, and create the monitor:

```bash
export SITEQWALITY_API_KEY="<your API key>"

curl -X POST https://api.siteqwality.com/http/job \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "friendly_name": "Mock 200 endpoint",
    "method": "GET",
    "uri": "https://mock.codes/200",
    "timeout_ms": 15000,
    "run_interval_seconds": 300,
    "monitor_tls": false,
    "monitor_dns": false
  }'
```

The response is the new monitor. Save its `id` to fetch results, update the check or delete it later.

Without `group_notification_ids` the monitor uses the **Default** group. To target other groups, pass their IDs (`GET /notification_group` lists them); an explicit `[]` creates a monitor that notifies no one.

</TabItem>
</Tabs>

## 3. Confirm it's working

<Steps>

1. Open the monitor's detail page. The status badge should flip to **Success** within one minute.

2. Scroll down to **Recent Checks**. You'll see one row per check result with status code, latency, and the location it ran from.

3. Force a failure: edit the check, change the URL to `https://mock.codes/500`, save.

4. On the next tick the monitor flips to **Failure**. The Default group waits 3 minutes, then emails you if the monitor is still down.

5. Flip the URL back to `/200`. The monitor recovers, and you'll get a recovery email right away.

</Steps>

If the email never arrives, check your spam folder and that the group's email channel matches your inbox. See [notification channels](/incident-management/notifications/channels/).

## What just happened

- The check ran from the default [check location](/uptime-monitoring/overview/#check-locations), `aws-us-east-1` (Virginia, AWS), and compared the response with the monitor's assertions (here, the status code).
- The status change sent a down alert to the monitor's **notification group**, which waited its 3-minute delay and then fanned out to its channels. The recovery message went out at once.
- No incident opened: monitor alerts go straight to notification groups. An incident opens when the monitor is linked to a service that creates incidents, or when you open one by hand.

From here, link the monitor to a service so a failure opens an incident, let on-call schedules and escalation policies decide who gets paged, and publish incidents on a status page. See [Incident Management](/incident-management/overview/).
