Site Qwality's observability suite has five pillars. Each has its own explorer in the dashboard. Logs, metrics and RUM can drive threshold alerts that go to your notification groups, and logs, metrics and traces can be shown on [dashboards](/dashboards/overview/).

| Pillar | Stores | Best for |
|---|---|---|
| [Metrics](/observability/metrics/overview/) | Numeric time-series with tags | Counters, gauges, histograms, anything chart-able |
| [Logs](/observability/logs/overview/) | Structured + unstructured events | Error context, audit trails, full-text search |
| [Traces](/observability/traces/overview/) | Span trees following one request | Why a request was slow, what services it touched |
| [RUM](/observability/rum/overview/) | Browser-side telemetry from real users | Web vitals, JS errors, user actions |
| [Replay](/observability/replay/overview/) | Pixel playback of user sessions | "What did the user actually do?" debugging |

## How they relate

```
       (numeric ↑↓)              (events)              (request shape)
        Metrics    ←────→         Logs       ←────→        Traces
         "what?"               "why?"                  "where?"

                                    │
                                    │ correlates via trace_id
                                    │
                                    ▼
                                  RUM            ←────→     Replay
                                "from the user's side"
```

- A **trace** can pull in **logs** for any of its spans, when your log entries carry a `trace_id` (see [correlate traces with logs](/observability/traces/how-to/correlate-logs/)).
- **RUM** can add a `traceparent` header to fetch/XHR requests whose URLs you list in the application's [`trace_urls`](/observability/rum/how-to/remote-config/) setting (SDK 2), so a user's request can open the back-end trace.
- **Metrics** are the numbers you send. Nothing is derived from your logs or traces automatically, so emit a metric for anything you want to chart or alert on as a number.

## When to reach for which

| Question | Tool |
|---|---|
| "How many errors in the last hour?" | **Metrics**, if you emit an error counter. Alertable, fast, cheap. |
| "What was the error message at 14:32?" | **Logs**. The full payload is there. |
| "Why was that one request slow?" | **Traces**. See the call graph. |
| "What was the LCP for users on Safari?" | **RUM**. Filter by browser, OS, device, country or page; see [dimensions](/observability/rum/how-to/dimensions/). |
| "What did the user click before the error?" | **Replay**. Watch them. |

If you find yourself reaching for **logs** to answer "how many", that's a metric. Emit one. If you reach for **metrics** to answer "what was the actual value", that's a log. Cross-emit.

## Ingestion

| Pillar | Endpoint | Auth |
|---|---|---|
| Metrics | `POST https://metrics.siteqwality.com/metrics` | API key |
| Logs | `POST https://logs.siteqwality.com/ingest` | API key |
| Traces | `POST https://traces.siteqwality.com/v1/traces` (OTLP-compatible) | API key |
| RUM | Auto via SDK | Client token (per-app, public) |
| Replay | Auto via SDK | Client token (per-app, public) |

Backends:

- Postgres for transactional data (configs, accounts, dashboards).
- ClickHouse for time-series storage (metrics, logs, traces, RUM events).
- S3 for blobs (HAR files, video, replay segments).

## Pricing

Logs, metrics and traces share one **telemetry** allowance, measured in GB per month and pooled across the three signals: 1 GB with 3-day retention on the free tier, then paid packs of 50 GB (15 days), 200 GB (30 days) and 1 TB (30 days). Telemetry has no per-seat charge. RUM and session replay are priced separately, per session and per replay. See [pricing](https://siteqwality.com/pricing/).

<Aside type="caution" title="What happens at the limit">
You get usage emails at 80% and 100% of your telemetry allowance, as for other products. Usage can then run 10% past the allowance. After that, logs, metrics and traces sent for the rest of the billing period are still accepted with a success response, but they are not stored. The **Usage** tab of your account settings shows where you stand.
</Aside>
