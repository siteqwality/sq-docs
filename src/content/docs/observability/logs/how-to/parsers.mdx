If your logs arrive as plain strings (`Apache combined`, syslog, key/value pairs), parsers extract structured fields server-side at ingest. The result: searchable, filterable fields on every log without the app having to ship JSON.

## Supported parser types

| Type | What it parses |
|---|---|
| `json` | Accepted, but does nothing at ingest: JSON bodies are never run through parsers. Useful only with the test endpoint. |
| `regex` | Custom named-capture regex. |
| `apache_combined` | Apache combined log format. |
| `nginx` | Nginx default log format. |
| `syslog` | RFC 5424 syslog. RFC 3164 lines do not match. |
| `csv` | Delimited values; set `columns` (names) and optionally `delimiter` in `parse_config`. |
| `kv` | `key=value key2=value2` style; `delimiter` and `kv_separator` are configurable. |

Parsers only run on plain-text lines (`Content-Type: text/plain`). A body sent as `application/json` is stored as sent.

## Anatomy of a parser

A parser has:

- `name`: display label.
- `parse_type`: one of the above.
- `parse_config`: type-specific config (`pattern` for regex, `columns` and `delimiter` for CSV, `delimiter` and `kv_separator` for kv).
- `field_mapping`: maps each **extracted field name** to a **destination**: `{"extracted_name": "destination"}`. Destinations are `level`, `message`, `host`, `env`, `source`, `version`, `device`, `trace_id`, `tags.<key>` or `metadata.<key>`. An extracted field that is not mapped keeps its own name, so it is kept only if that name is already a destination (for example `message` or `level`). Everything else is dropped, including a captured `timestamp`: parsed lines are stamped with the ingest time.
- `detect_pattern`: optional regex; only logs matching this run through the parser.
- `source_filter`: optional source name; only logs from this source run through the parser.
- `priority`: when multiple parsers match, lower number runs first. The first parser whose filters match and that parses the line is applied; the rest are skipped.
- `enabled`: toggle on/off without deleting.

Changes to parsers reach the ingest pipeline within about a minute.

## Example: Apache combined

```bash
curl -X POST https://api.siteqwality.com/log_parsers \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Web access logs",
    "parse_type": "apache_combined",
    "source_filter": "web-access",
    "field_mapping": {
      "remote_addr": "host",
      "http_user_agent": "metadata.user_agent",
      "status": "tags.status"
    },
    "enabled": true,
    "priority": 100
  }'
```

After this is enabled, every plain-text line with `source: "web-access"` gets the parser applied. The Apache and nginx parsers extract `remote_addr`, `remote_user`, `time`, `method`, `request_uri`, `protocol`, `status`, `body_bytes_sent`, `http_referer` and `http_user_agent`, and they also set `message` (method, path and protocol) and `level` (`error` for 5xx, `warn` for 4xx, otherwise `info`). The mapping above sends `remote_addr` to `host`, the user agent to metadata and the status to a filterable tag.

## Example: custom regex

```json
{
  "name": "Custom audit log",
  "parse_type": "regex",
  "parse_config": {
    "pattern": "^\\[(?P<timestamp>[^\\]]+)\\]\\s+\\[(?P<level>[A-Z]+)\\]\\s+user=(?P<user_id>\\S+)\\s+(?P<message>.*)$"
  },
  "source_filter": "audit",
  "field_mapping": {
    "user_id": "metadata.user_id"
  },
  "enabled": true,
  "priority": 50
}
```

Named captures (`(?P<name>...)`) become extracted fields. Captures already named after a destination (`level`, `message` here) need no mapping; map the rest via `field_mapping`. The `timestamp` capture has no destination and is dropped.

## Test before saving

Before enabling, send a sample line to the test endpoint:

```bash
curl -X POST https://api.siteqwality.com/log_parsers/test \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "sample": "[2026-05-03T14:32:17Z] [ERROR] user=usr_abc123 Failed to charge card",
    "parse_type": "regex",
    "parse_config": {
      "pattern": "^\\[(?P<timestamp>[^\\]]+)\\]\\s+\\[(?P<level>[A-Z]+)\\]\\s+user=(?P<user_id>\\S+)\\s+(?P<message>.*)$"
    },
    "field_mapping": {
      "user_id": "metadata.user_id"
    }
  }'
```

Response:

```json
{
  "data": {
    "matched": true,
    "extracted_fields": { "timestamp": "...", "level": "ERROR", "user_id": "usr_abc123", "message": "Failed to charge card" },
    "mapped_fields": { "timestamp": "...", "level": "ERROR", "message": "Failed to charge card", "metadata.user_id": "usr_abc123" },
    "parse_type": "regex",
    "error": null
  }
}
```

`mapped_fields` shows each value under its destination name. At ingest, only destination names are kept, so `timestamp` here would be dropped.

The test endpoint and the parser API are on `api.siteqwality.com` and need a full-access API key.

If `matched: false` or `error` is set, fix the pattern and retry.

## Sending plain-text lines

Plain-text lines carry no `source` of their own, so a parser with a `source_filter` only sees them when the request sets one with the `X-Log-Source` header:

```bash
curl -X POST https://logs.siteqwality.com/ingest \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: text/plain" \
  -H "X-Log-Source: web-access" \
  --data-binary '127.0.0.1 - - [03/May/2026:14:32:17 +0000] "GET / HTTP/1.1" 200 1234 "-" "curl/8"'
```

There is no way to pick a parser per request. If you cannot set `X-Log-Source` in your pipeline, leave the parser's `source_filter` empty and use `detect_pattern` to recognise its lines instead.

<Aside type="tip">
For pipelines that ship raw text logs (Vector, Fluent Bit), configure the HTTP output to send `X-Log-Source` once, and every line in each request will match the parser's `source_filter`.
</Aside>
