By the end of this guide you'll have ingested a few logs, queried them via the API, and pinned a saved view in the dashboard.

<Aside type="note" title="Which API key">
Use a **full-access** API key for this guide: step 3 calls `api.siteqwality.com`, which rejects ingest keys with a `403`. In production, give your apps and forwarders an **ingest** key, which can only send telemetry.
</Aside>

## 1. Send a log

```bash
curl -X POST https://logs.siteqwality.com/ingest \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "timestamp": "'$(date -u +%Y-%m-%dT%H:%M:%SZ)'",
    "level": "error",
    "message": "Failed to charge card",
    "source": "billing-api",
    "env": "prod",
    "host": "api-demo-1",
    "tags": { "endpoint": "/api/charge" },
    "metadata": {
      "user_id": "usr_abc123",
      "amount_cents": 9900,
      "stripe_error": "card_declined"
    }
  }'
```

`202 Accepted`. The log becomes searchable about a minute later: ingestion runs in batches that wait up to 60 seconds to fill. If step 3 returns nothing, wait a minute and run it again.

## 2. Send a few more

```bash
for i in {1..20}; do
  LEVEL="info"
  [ $((i % 5)) -eq 0 ] && LEVEL="error"
  curl -X POST https://logs.siteqwality.com/ingest \
    -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
    -H "Content-Type: application/json" \
    -d "{
      \"timestamp\": \"$(date -u +%Y-%m-%dT%H:%M:%SZ)\",
      \"level\": \"$LEVEL\",
      \"message\": \"Order $i processed\",
      \"source\": \"billing-api\",
      \"env\": \"prod\",
      \"tags\": { \"endpoint\": \"/api/orders\" }
    }" > /dev/null
  sleep 2
done
```

That's 20 logs over 40 seconds, with 4 errors mixed in.

## 3. Query

<Tabs syncKey="interface">
<TabItem label="Dashboard">

Open **Logs** and type `source:billing-api level:error` in the search bar. The matching logs render in a table; click one to see its metadata.

</TabItem>
<TabItem label="API">

```bash
# macOS/BSD date first, then GNU date (Linux)
START=$(date -u -v-1H +%Y-%m-%dT%H:%M:%SZ 2>/dev/null || date -u -d '1 hour ago' +%Y-%m-%dT%H:%M:%SZ)
END=$(date -u +%Y-%m-%dT%H:%M:%SZ)

curl -G https://api.siteqwality.com/logs/query \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  --data-urlencode "source=billing-api" \
  --data-urlencode "level=error" \
  --data-urlencode "start_time=$START" \
  --data-urlencode "end_time=$END" \
  --data-urlencode "limit=50"
```

Returns `{"data": {"logs": [...], "total": N}}`.

</TabItem>
</Tabs>

## 4. Save the search

On the **Logs** page, after applying your filters click **Save view** and name it `Billing errors (prod)`. It now appears in your saved views; share it with your team by toggling **Shared**.

Create views from the dashboard rather than the API. A view created with an API key has no owner, so nobody can edit or delete it afterwards. See [saved views](/observability/logs/how-to/saved-views/).

## 5. Wire your real app

Most logging libraries can ship to an HTTP sink. Two common patterns:

**Direct ship from your app** (small services):

```python
import logging, os, requests
from datetime import datetime, timezone

class SqHandler(logging.Handler):
    def emit(self, record):
        requests.post(
            "https://logs.siteqwality.com/ingest",
            headers={"Authorization": f"Bearer {os.environ['SITEQWALITY_INGEST_KEY']}"},
            json={
                # timestamps must be RFC 3339 strings; numbers are ignored
                "timestamp": datetime.fromtimestamp(record.created, timezone.utc).isoformat(),
                "level": record.levelname.lower(),
                "message": record.getMessage(),
                "source": "my-app",
            },
            timeout=2,
        )
```

This sends one request per line and blocks while it does, so in a busy service buffer lines and send them in batches from a background thread.

**Ship via your existing log pipeline** (Vector, Fluent Bit, Filebeat). Point its HTTP output at `https://logs.siteqwality.com/ingest` with the API key in the `Authorization` header, and map its records to our field names first: the line goes in `message` (Fluent Bit and Docker put it in `log`, many JSON loggers in `msg`), and anything you want to keep goes under `metadata`. Fields with other names are dropped.

For high-volume apps, batch via NDJSON: use `Content-Type: application/x-ndjson` and submit one JSON object per line, up to about 1,000 lines per request, each under 100 KB.
