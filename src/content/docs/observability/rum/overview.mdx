**Real User Monitoring** captures performance and interaction data from your real users' browsers. Unlike browser checks (synthetic, runs from one IP), RUM measures the actual experience: every user, every device, every network condition.

## When to use RUM

- Track user-perceived performance (web vitals: LCP, FCP, CLS, INP, TTFB).
- Catch JS errors your test suite missed.
- Understand real user flows (which pages, which buttons, in what order).
- Identify slow regions, slow devices, slow ISPs.

## When NOT to use RUM

- Answering "is the site up?" is a job for a [browser check](/uptime-monitoring/browser-checks/overview/) or an HTTP check.
- Backend performance belongs in [traces](/observability/traces/overview/).
- A single canary value won't come from RUM, which is statistical (millions of points), not deterministic.

## How it works

You install the `@siteqwality/rum` SDK in your front-end. It:

1. Starts a session shared by the visitor's tabs.
2. Records page views and Web Vitals with `PerformanceObserver`.
3. Listens for errors (`error`, `unhandledrejection`).
4. Tracks clicks, requests and other activity.
5. Sends batched events to `https://in.siteqwality.com`.

The SDK has **two layers**:

- **Observe**, sent for every sampled session: page views, Web Vitals, errors (with their stacks), failed requests, frustration signals and custom events.
- **Analyze**, activated only when a [recording rule](/observability/rum/how-to/session-filters/) matches the session: every click and form action, successful requests, resource timings, console entries and long animation frames. Keeps cost down by not capturing every detail for every user.

[Session replay](/observability/replay/overview/) is the third tier: pixel playback, activated only by Replay recording rules. A new application starts with a rule that replays every errored session and an Auto sample within your replay quota. See its own page.

## RUM application

Each install of the SDK targets a **RUM application**, typically one per domain or one per major build. Each app has:

- A unique `application_id` and a public `client_token`.
- A `domain` for the dashboard's "Open in app" links.
- Privacy settings: a [privacy level](/observability/rum/how-to/remote-config/#privacy-levels) and selectors.
- Recording rules that activate detail and replay capture.
- [Excluded resources](/observability/rum/how-to/remote-config/#excluded-resources): resource URLs it never records.

Create one in **RUM → New application**.

## Install

Two install paths:

### NPM

```bash
npm install @siteqwality/rum
```

```javascript
import { SiteQwalityRUM } from '@siteqwality/rum';

SiteQwalityRUM.init({
  applicationId: 'abc123',
  clientToken: 'pub_def456',
  // version: '1.4.2', // your release; enables source-mapped stack traces
});
```

Calls made before `init()` are ignored with the npm package, so call it first.

### CDN

For static sites, paste the [CDN snippet](/sdk/v2/#cdn-snippet) into the page's `<head>`. It loads `https://cdn.siteqwality.com/rum/v2/sdk.min.js` asynchronously, queues calls and captures errors until it arrives, then replays them. It is a classic script and defines a single global, `SiteQwalityRUM`. The replay recorder is a separate file, downloaded only for sessions a Replay recording rule has matched or could still match.

`init()` is fire-and-forget: collection starts synchronously, and the Promise it returns (settled once remote config is applied or fails) never needs an `await`. If your site sets a Content Security Policy, see [CSP and intake endpoints](/observability/rum/how-to/csp/).

## Tracking custom data

```javascript
// Identify a user (call after login); the session then shows it
SiteQwalityRUM.setUser({ id: 'usr_abc', email: 'alice@example.com', name: 'Alice' });

// Label every later batch
SiteQwalityRUM.setGlobalAttribute('plan', 'pro');

// Custom error
SiteQwalityRUM.addError(new Error('Payment dialog refused'), { feature: 'checkout' });

// Custom event
SiteQwalityRUM.addAction('checkout_step_2', { variant: 'A' });
```

## What gets captured

| Observe (every sampled session) | Analyze (rule-activated) | Replay (Replay rule) |
|---|---|---|
| Page views, load timing, time spent and scroll depth | Clicks, taps, field changes and form submits | Full DOM snapshots and mutations |
| Web Vitals (LCP, FCP, CLS, TTFB, INP) with attribution | Successful fetch and XHR requests | Mouse, scroll and input events |
| Errors with message and stack (known browser noise filtered) | Resource timings | Privacy: masking and blocking from the application's privacy level |
| Failed requests and frustration signals | Console entries | |
| Custom events from `addAction` | Long animation frames | |

See [what is collected when](/sdk/v2/#what-is-collected-when) for the details.

## Privacy

The SDK follows the application's privacy settings, delivered with its config:

- A [privacy level](/observability/rum/how-to/remote-config/#privacy-levels), `strict`, `balanced` or `relaxed`, sets how replays mask inputs, text and media, and which personal data patterns are scrubbed.
- `hide_action_text`: drop element text from click names. See [hiding element text in click names](/observability/rum/how-to/remote-config/#hiding-element-text-in-click-names).
- Consent, Global Privacy Control, cookieless sessions and user email capture. See [consent and browser signals](/sdk/v2/#consent-and-browser-signals).

Set these conservatively if you handle PII or financial data, and check what is stored on each application rather than assuming a default: an application created before privacy levels may store `mask_inputs: false`. See [replay privacy](/observability/replay/overview/#privacy) and the [privacy settings reference](/observability/replay/reference/#privacy-settings).

## Session dimensions

Every session carries `browser`, `os`, `device_type` and `country`, so you can segment vitals and errors without instrumenting anything. The first three are parsed from the User-Agent server side. Country is looked up from the client IP address at ingest; the IP itself is never stored or logged. A `country` sent in the payload still wins.

There was **no backfill**: sessions recorded before each dimension shipped keep an empty value. See [segmenting by dimension](/observability/rum/how-to/dimensions/).

## In the dashboard

**Overview** leads with LCP, INP and CLS at the 75th percentile (p75), each coloured by Google's thresholds, with a bar showing the share of page views rated good, needs improvement and poor. FCP and TTFB sit in a second row. Each page view counts once per vital, using its latest valid value ordered by sequence and timestamp. The top row shows sessions, page views, errors and the share of sessions with an error. **Sessions** counts only sessions with at least one page view, and the error numbers come from the error events themselves.

| Vital | Good | Poor |
|---|---|---|
| LCP | ≤ 2,500 ms | > 4,000 ms |
| INP | ≤ 200 ms | > 500 ms |
| CLS | ≤ 0.1 | > 0.25 |
| FCP | ≤ 1,800 ms | > 3,000 ms |
| TTFB | ≤ 800 ms | > 1,800 ms |

Anything between the two is "needs improvement".

**Top pages** lists each URL's page views with p75 LCP, INP, CLS and load time. Load time counts initial page loads only, never route changes. Click a row to see the sessions that visited it.

**Vitals charts** plot p50, p75 and p95 in your local time zone, with dates on ranges over 24 hours. Buckets are 5 minutes for the last 1 or 6 hours, 1 hour for 24 hours, 6 hours for 7 days and 1 day (aligned to your time zone) for 30 days. Empty buckets show as gaps, buckets with fewer than 10 samples are drawn faded, and lines mark the good and poor thresholds.

**Sessions** lists sessions active in the range that have at least one page view. Search matches any user ID or email the session carried, a session ID prefix, any visited URL or any error message in the session, ignoring case. The browser, OS, country and device filters offer only values seen in the range, with session counts. Filters, sort and range live in the URL, so a copied link reopens the same view.

**Errors** groups errors and shows events, sessions and identified users per group for the selected range. Search runs on the server across every group in the range. An error's page lists the affected sessions, and **View all sessions** opens Sessions filtered to that error. **Watch replay** appears only when the session has a replay, and opens it at the error.


Overview also reports visitors, bounce rate and median active time, with comparison to the previous period. Pages separates initial loads from route changes and connects poor Web Vitals to recorded element, script and resource details. Save an investigation privately or share it with your account, and discuss sessions or issues in comments. The same features are available through the API.
