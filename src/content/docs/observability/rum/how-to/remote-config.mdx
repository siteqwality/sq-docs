The RUM SDK does not carry its capture rules in your bundle. It fetches them from SiteQwality at startup and refreshes them periodically, so you can change what gets captured without shipping a new build.

## What is served

```
GET https://rum.siteqwality.com/v1/config
Authorization: Bearer <client_token>
```

The same public client token the SDK already holds authenticates the request, and the application is identified from that token rather than from a parameter.

```json
{
  "data": {
    "application_id": "<uuid>",
    "filters": [
      {
        "id": "<uuid>",
        "name": "Sessions with errors",
        "filter_type": "error",
        "conditions": { "has_error": true },
        "capture_replay": true,
        "enabled": true,
        "priority": 0,
        "created_at": "2026-08-01T10:00:00Z"
      }
    ],
    "settings": {
      "privacy": { "mask_inputs": true, "mask_text": false },
      "retention": { "observe_days": null, "analyze_days": null },
      "resource_exclusions": ["/b", "https://us.i.posthog.com"]
    }
  }
}
```

Only **enabled** filters are sent. Disabling one in the dashboard removes it from the payload entirely rather than shipping it with a flag.

`priority` is stored and returned but is not currently used to order evaluation. Filters are evaluated as a set, and a session activates if **any** of them matches.

## What you can change remotely

Four things, and it is worth being clear about the boundary:

| Change | Effect |
|---|---|
| Add, edit or disable a [session filter](/observability/rum/how-to/session-filters/) | Controls whether detail capture turns on for a session |
| Set `capture_replay` on a filter | Controls whether [session replay](/observability/replay/overview/) starts |
| Change `mask_inputs` / `mask_text` | Controls replay masking |
| Edit [excluded resources](#excluded-resources) | Stops matching resource timings from being recorded |

**What you cannot change remotely:** there are no sample rates in the configuration, and no global kill switch. Flush intervals, batch sizes and session timeouts are fixed in the SDK. Endpoint hosts can only be set locally in `init()`.

If you need to stop collection entirely, disable every filter to stop detail and replay capture, and remove the `init()` call to stop the always-on measurements.

## Where you set it

| What | Where |
|---|---|
| Privacy settings | **RUM → Settings → Privacy**, or `settings.privacy` in a full-settings `PUT /rum/{app_id}` |
| Session filters | **RUM → Filters**, or the `/rum/{app_id}/filters` endpoints |
| Excluded resources | **RUM → Settings → Excluded resources**, or `settings.resource_exclusions` in a full-settings `PUT /rum/{app_id}` |

Defaults for a newly created application: `mask_inputs` is **on**, `mask_text` is **off**, nothing is excluded, and there are no filters, meaning no detail capture and no replay.

<Aside type="caution" title="PUT replaces the whole settings object">
Fetch `GET /rum/{app_id}`, change only the key you need, and send `settings` back with every other key exactly as returned. Any key you leave out is reset to its default, so saving only `privacy` clears your excluded resources and your retention limits.
</Aside>

<Aside type="danger" title="An existing application may not carry those defaults">
Privacy settings are written into the application record when it is created, and nothing rewrites them afterwards. An application created earlier can have `mask_inputs` stored as `false`, in which case its recordings capture input values however this page describes the default.

The config payload above is the authority: `GET {ingestBase}/v1/config` returns exactly what the SDK will obey for your application, and the dashboard's **RUM → Settings → Privacy** toggles show the same stored values. Check them per application. There is no backfill.
</Aside>

## How long changes take to land

<Aside type="note" title="Budget about ten minutes, and understand the latches">
Two delays stack. The SDK refreshes its configuration on a **5 minute** cycle, and the authorisation decision for the config request is cached at the edge for up to a further **5 minutes**.

More importantly, **activation is one-way within a session**. Once detail capture or replay has turned on for a session, it stays on for the rest of that session; a later config refresh cannot turn it back off. Replay masking is applied when recording starts, so changing it does not re-apply to a recorder that is already running.

So a tightening change ("stop capturing this") applies to *new* sessions, not to sessions already in flight. Plan privacy changes accordingly.
</Aside>

## Filter conditions

The condition keys the SDK evaluates:

| `filter_type` | Condition keys | Matches when |
|---|---|---|
| `error` | `has_error` | The session has thrown at least one error. |
| `slow_performance` | `lcp_gt_ms`, `cls_gt` | LCP or CLS exceeds the threshold. |
| `custom` | `has_user`, `min_actions` | A user is identified, and/or the action count is reached. |

Evaluation happens in the browser against the running session, so a session that turns bad partway through activates partway through.

Note that an `error` filter fires on **any** error in the session, regardless of what its conditions say.

## Excluded resources

Some requests are noise as resource events: a polling endpoint, a game loop, an analytics beacon. List them on the application and they stop being recorded. Only that application is affected.

A rule takes one of two forms:

| Form | Example | Excludes |
|---|---|---|
| Path, starting with `/` | `/b` | `/b` and everything under `/b/` on the page's own origin |
| Absolute, starting with `http://` or `https://` | `https://us.i.posthog.com` | Everything on that origin, or under the given path on it |

How a resource URL is matched:

- The origin must match: scheme, host and port. Host case is ignored and default ports are normalized, so `https://API.example:443/v1` matches `https://api.example/v1/x`.
- The path must equal the rule's path or continue it after a `/`. `/b` matches `/b`, `/b?t=1` and `/b/2`, but not `/blocks`. A trailing slash on the rule is ignored, and `/` excludes the whole origin.
- Query strings and fragments are ignored.

Each application takes up to **50** rules of up to 512 characters each. A rule may not contain `?`, `#` or whitespace. Blank lines and duplicates are dropped on save.

Wildcards are not supported, so list each host: `https://us.i.posthog.com` and `https://eu.i.posthog.com`, not `https://*.posthog.com`.

Ingest drops matching resource events within a minute of saving, from every SDK version, before they are stored. From SDK **1.0.5** the browser also skips them, so they are never sent, and it picks up changes on its 5 minute config refresh without a page reload.
