The RUM SDK does not carry its capture rules in your bundle. It fetches them from SiteQwality at startup and refreshes them periodically, so you can change what gets captured without shipping a new build.

## What is served

```
GET https://rum.siteqwality.com/v1/config
Authorization: Bearer <client_token>
```

The same public client token the SDK already holds authenticates the request, and the application is identified from that token rather than from a parameter.

```json
{
  "data": {
    "application_id": "<uuid>",
    "filters": [
      {
        "id": "<uuid>",
        "name": "Sessions with errors",
        "filter_type": "error",
        "conditions": { "has_error": true },
        "capture_replay": true,
        "enabled": true,
        "priority": 0,
        "created_at": "2026-08-01T10:00:00Z"
      }
    ],
    "settings": {
      "privacy": { "mask_inputs": true, "mask_text": false, "hide_action_text": false },
      "retention": { "observe_days": null, "analyze_days": null },
      "resource_exclusions": ["/api/heartbeat", "https://analytics.example.com"],
      "frustration_ignore_selectors": [".carousel-next"]
    }
  }
}
```

`filters` holds your [recording rules](/observability/rum/how-to/session-filters/) (the API's name for them). Only **enabled** rules are sent. Disabling one in the dashboard removes it from the payload entirely rather than shipping it with a flag.

`priority` is accepted and returned but not used. Rules are evaluated as a set, and a session activates if **any** of them matches.

## What you can change remotely

Six things, and it is worth being clear about the boundary:

| Change | Effect |
|---|---|
| Add, edit or disable a [recording rule](/observability/rum/how-to/session-filters/) | Controls whether detail capture turns on for a session |
| Set `capture_replay` on a rule | Controls whether [session replay](/observability/replay/overview/) starts |
| Change `mask_inputs` / `mask_text` | Controls replay masking |
| Turn on [`hide_action_text`](#hiding-element-text-in-click-names) | Drops element text from click names |
| Edit [excluded resources](#excluded-resources) | Stops matching resource timings from being recorded |
| Edit [frustration ignore selectors](#ignoring-elements-for-frustration-signals) | Stops rage and dead clicks on matching elements |

**What you cannot change remotely:** there are no sample rates in the configuration, and no global kill switch. Flush intervals, batch sizes and session timeouts are fixed in the SDK. Endpoint hosts can only be set locally in `init()`.

If you need to stop collection entirely, disable every rule to stop detail and replay capture, and remove the `init()` call to stop the always-on measurements.

## Where you set it

| What | Where |
|---|---|
| Privacy settings | **RUM → Settings → Session Replay Privacy** and **Click Names**, or `settings.privacy` in a full-settings `PUT /rum/{app_id}` |
| Recording rules | **RUM → Recording rules**, or the `/rum/{app_id}/filters` endpoints |
| Excluded resources | **RUM → Settings → Excluded resources**, or `settings.resource_exclusions` in a full-settings `PUT /rum/{app_id}` |
| Frustration ignore selectors | **RUM → Settings → Frustration signals**, or `settings.frustration_ignore_selectors` in a full-settings `PUT /rum/{app_id}` |

Defaults for a newly created application: `mask_inputs` is **on**, `mask_text` and `hide_action_text` are **off**, nothing is excluded or ignored, and there are no rules, meaning no detail capture and no replay.

<Aside type="caution" title="PUT replaces the whole settings object">
Fetch `GET /rum/{app_id}`, change only the key you need, and send `settings` back with every other key exactly as returned. Any key you leave out is reset to its default, so saving only `privacy` clears your excluded resources, your frustration ignore selectors and your retention limits.
</Aside>

<Aside type="danger" title="An existing application may not carry those defaults">
Privacy settings are written into the application record when it is created, and nothing rewrites them afterwards. An application created earlier can have `mask_inputs` stored as `false`, in which case its recordings capture input values however this page describes the default.

The config payload above is the authority: `GET {ingestBase}/v1/config` returns exactly what the SDK will obey for your application, and the dashboard's **RUM → Settings → Privacy** toggles show the same stored values. Check them per application. There is no backfill.
</Aside>

## How long changes take to land

<Aside type="note" title="Budget about ten minutes, and understand the latches">
Two delays stack. The SDK refreshes its configuration on a **5 minute** cycle, and the authorisation decision for the config request is cached at the edge for up to a further **5 minutes**.

More importantly, **activation is one-way within a session**. Once detail capture or replay has turned on for a session, it stays on for the rest of that session, across page loads in the same tab; a later config refresh cannot turn it back off. The one exception is replay on a new page load: it resumes only if an enabled rule still has `capture_replay: true`. Replay masking is applied when recording starts, so changing it does not re-apply to a recorder that is already running.

So a tightening change ("stop capturing this") applies to *new* sessions, not to sessions already in flight. Plan privacy changes accordingly. A loosening change (a new rule) is evaluated on the next refresh and can activate a session in progress.
</Aside>

## Rule conditions

The condition keys the SDK evaluates, and the only ones the API accepts:

| `filter_type` | Condition keys | Matches when |
|---|---|---|
| `error` | `has_error` | The session has sent at least one error. Filtered browser noise never counts. |
| `slow_performance` | `lcp_gt_ms`, `cls_gt` | LCP or CLS exceeds the threshold. |
| `custom` | `has_user`, `min_actions` | A user is identified, and/or the action count is reached. `{}` matches every session. |

Evaluation happens in the browser against the running session, immediately: when the config loads or refreshes, and after every sent error, Web Vital, action and `setUser` call. A session that turns bad partway through activates at that moment. A `custom` rule carrying any other key never matches, and the API rejects it with a `400`; see the [validation table](/observability/rum/reference/#conditions-by-filter-type).

Note that an `error` rule fires on **any** sent error in the session, regardless of what its conditions say.

## Excluded resources

List requests you do not want recorded as resource events, such as polling endpoints or analytics beacons. Only that application is affected.

A rule takes one of two forms:

| Form | Example | Excludes |
|---|---|---|
| Path, starting with `/` | `/api/heartbeat` | That path and everything under it on the page's own origin |
| Absolute, starting with `http://` or `https://` | `https://analytics.example.com` | Everything on that origin, or under the given path on it |

How a resource URL is matched:

- The origin must match: scheme, host and port. Host case is ignored and default ports are normalized, so `https://API.example:443/v1` matches `https://api.example/v1/x`.
- The path must equal the rule's path or continue it after a `/`. `/api/poll` matches `/api/poll`, `/api/poll?t=1` and `/api/poll/2`, but not `/api/polls`. A trailing slash on the rule is ignored, and `/` excludes the whole origin.
- Query strings and fragments are ignored.

Each application takes up to **50** rules of up to 512 characters each. A rule may not contain `?`, `#` or whitespace. Blank lines and duplicates are dropped on save.

Wildcards are not supported, so list each host separately.

Ingest drops matching resource events within a minute of saving, from every SDK version, before they are stored. From SDK **1.0.5** the browser also skips them, so they are never sent, and it picks up changes on its 5 minute config refresh without a page reload.

## Hiding element text in click names

Auto-captured clicks are named from the clicked element, including up to 30 characters of its text, or else its full `aria-label`, such as `button.btn.primary[Send message]`. On pages that render what users wrote, that text can be personal data.

Turn on **Hide element text in click names** under **RUM → Settings → Click Names** (or set `settings.privacy.hide_action_text` to `true`) and clicks are stored without the bracketed text:

| Sent | Stored |
|---|---|
| `button.btn.primary[Send message]` | `button.btn.primary` |
| `a.nav[Home]` | `a.nav` |
| `#save` | `#save` |

Ingest strips the text within a minute of saving, from every SDK version, before it is stored. From SDK **1.0.6** the browser also leaves it out, picking up the change on its 5 minute config refresh. Clicks already stored keep their names.

To give an element a stable, readable name instead, add `data-sq-action-name`. It applies to clicks on the element and anything inside it, whether or not the setting is on:

```html
<button class="btn primary" data-sq-action-name="Send message">Send</button>
```

`data-sq-action-name` needs SDK 1.0.6. The value is trimmed, cut to 100 characters, and its square brackets become parentheses, so the setting never strips it. Keep personal data out of it.

Names passed to `addAction()` are never changed by this setting.

## Ignoring elements for frustration signals

Some controls draw rapid clicks by design (a carousel arrow, a stepper) or legitimately change nothing on screen. To stop their clicks being marked as rage or dead clicks, list CSS selectors under **RUM → Settings → Frustration signals**, one per line, or set `settings.frustration_ignore_selectors`:

```json
"frustration_ignore_selectors": [".carousel-next", "[data-role=stepper] button"]
```

A click on an element matching any selector, or inside one, gets no rage or dead click. A click followed by an error is still an error click. Up to **50** selectors of 1 to 256 printable characters each; anything else returns a `400`. A selector the browser cannot parse is skipped. The SDK picks up changes on its 5 minute config refresh.

To exclude an element in your markup instead, add the `data-sq-no-frustration` attribute to it or an ancestor. See [frustration signals](/sdk/reference/#frustration-signals) for how each signal is defined.
