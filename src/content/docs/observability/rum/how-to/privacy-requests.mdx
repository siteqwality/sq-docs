Account admins can request erasure in **RUM → Settings → Data requests** or through the API. Choose an identifier and application scope, optionally select **Also add to do-not-record**, then review and confirm the request. The history shows status, deleted row and object counts, and timing.

Deletion runs asynchronously. A queued request or saved retention setting does not mean cleanup has finished. Check the request status and counts before treating erasure as complete.

## Request erasure

An account admin, or an API key without scope restrictions, can submit `POST /rum/deletion-requests`. Keep privileged credentials on your server. These endpoints are unavailable through MCP, including `call_api`.

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "application_id": "22222222-2222-4222-8222-222222222222",
  "subject_kind": "user_id",
  "subject_value": "customer-123",
  "do_not_record": true
}
```

Generate a fresh UUID for `id`. Reuse it when retrying the same request; changing its input returns `409`. Supported subjects are `user_id`, `user_email`, `anonymous_id` and `session_id`. Email matching trims surrounding whitespace and lowercases the address. A session ID must be a UUID.

Omit `application_id` to cover every application your account owns, up to 1,000; an account with more must submit one application at a time. The scope does not grow when an application is created later.

The completion target for a queued request is 24 hours, with escalation after seven days. These are targets, not a guaranteed completion time: retries and in-flight uploads can delay cleanup.

## Track the result

- `GET /rum/deletion-requests/{id}` returns `pending`, `running`, `failed` or `done`, progress counts and deadlines.
- `GET /rum/deletion-requests` returns the newest 50 requests. Pass the last returned ID as `?before=<id>` for the next page.
- `failed` retains completed work and retries on subsequent scheduled passes. It is not a successful erasure result.
- `done` means the captured applications finished discovery and cleanup. The submitted value is replaced with a hash in the request record. Request responses and history never return that value.

Counts describe stored rows matched for erasure and acknowledged object removals, not unique events or users. A repeated request can report fewer rows because an earlier request already removed them. Deleting an application is blocked while a privacy request for it remains unfinished.

## What is removed and retained

Erasure removes the matching sessions' measures, events, session summaries, raw and compacted replay recordings with their indexes, session comments and stored identity links. Affected error and network aggregates are rebuilt from surviving events, and error descriptions derived from erased events are cleared while issue workflow state remains.

Audit records, aggregate billing usage, operational statistics and shared stylesheet assets remain. Erasure does not delete an account, erase unrelated telemetry, purge backups or refund usage.

An erased session can never be uploaded or compacted again. With `do_not_record: true`, an application-scoped identity hash also prevents future recording under the matching identifier. Without DNR, a later new session may be recorded again. DNR cannot recognize a person who changes all identifiers or stops sending an identifying field.

## DNR and first-party proxies

Intake checks stored DNR state before writing, including replay requests whose session was previously linked to an identity. If that check is unavailable, intake returns a retryable failure instead of accepting recording data.

For an identity check, SDK clients send the application-scoped SHA-256 hash. The intake supports `POST /v2/identity` with `{"h":"<64 hex characters>"}` and the compatibility `GET /v2/identity?h=<hash>`. Published SDK 2.1 to 2.3 use GET, so proxies must retain it. Keep the bearer client token in `Authorization`; POST also requires `Content-Type: application/json`. The response is `{"record":true}` or `{"record":false}` with `Cache-Control: private, no-store`. Keep GET query strings out of proxy access logs; a hash is still an identifier. An identity check controls future recording; it does not report deletion progress.

See the [CSP and proxy guide](/observability/rum/how-to/csp/#first-party-proxies) for the rest of the proxy requirements. A proxy does not replace consent, masking or allowed-origin checks.

## Shorten retention

In **RUM → Settings → Retention**, account admins can set the Observe, Analyze and Replay retention ceilings. Leave a ceiling empty to use the plan limit. Shortening a ceiling permanently removes older data asynchronously.

The same settings are available through `PATCH /rum/{application_id}`, for admins only:

```json
{
  "settings": {
    "retention": {
      "observe_days": 30,
      "analyze_days": 14,
      "session_replay_days": 7
    }
  }
}
```

Observe and Analyze ceilings are positive day counts. Replay accepts 7, 14 or 30 days. Each value is capped by your plan's window and cannot extend it. `null` removes a customer ceiling and cannot restore data already erased. Shorter retention does not change what you are billed.
