## Access and keys

Keep ingest keys in server secret stores and restrict them by signal. A read-only key queries the selected account and scopes; it does not send telemetry. Member service/environment/signal allowlists apply to explorers, details, saved views, exports and correlation. Owners/admins can manage restrictions in [Telemetry settings](https://app.siteqwality.com/account/telemetry). API keys and machine clients use their own scopes; do not assume they inherit a person's member allowlist.

Saved views and links grant no extra access: a link to a restricted service or trace stays restricted. Permission changes can clear loaded data and invalidate paging. Read audit records hold query hashes and bounded metadata, not raw payloads.

## Exports

Use the explorer Download/Export controls. Inline exports are bounded to **10,000 rows and 4 MiB compressed**; for more, narrow the range or filter, or choose an asynchronous export. Asynchronous exports page through at most 10,000,000 rows, report truncation at the cap and run within a 900-second budget.

`POST /telemetry/exports` creates an export job, `GET /telemetry/exports` lists your jobs and `GET /telemetry/exports/{id}` reports its state. After a timeout, keep the returned ID rather than creating a duplicate. Download once the job is ready and returns a URL; completed artifacts expire after 24 hours. Download URLs are credentials, so do not publish them. An export covers only data its creator may read and does not bypass retention or restrictions. Access is rechecked, and erasure can invalidate a job or artifact.

## Erasure

In [Erase data](https://app.siteqwality.com/account/telemetry/privacy) under Telemetry settings, choose an account, service/environment, attribute or trace scope and an optional time range. Confirm the scope carefully.

```text
POST /telemetry/deletion-requests
GET /telemetry/deletion-requests/{id}
```

The create body contains `id`, `kind`, optional `signals`, `service`, `env`, `attribute_key`, `attribute_value`, `trace_ids`, `from` and `to`, as appropriate for the selected kind. Generate `id` once and reuse it across ambiguous retries. Do not recreate deleted data by replaying an old sender buffer.

A request runs asynchronously. The API returns `status`, `step`, target and due times, `completed_at`, backup retention and a `blocked_reason` when needed. The target is 24 hours with a seven-day due limit. **Only a completed status confirms the deletion finished.** Pending storage deletions or remaining exports can keep a request blocked; escalate overdue work to support with the request ID.

Erasure covers the matching data, its dependent series and points, issue metadata and exports within the selected scope. Aggregates without personal values, audit records and already counted billing totals can remain. Backups follow their separate **35-day retention**; this API does not promise their immediate removal. Copies you downloaded are outside server-side deletion. To reduce future collection, see [retention](/observability/billing/) and [pipeline redaction](/observability/pipelines/).

## Browser correlation and CORS

Trace propagation is opt-in and should target only URL prefixes you control; see the [RUM correlation guide](/observability/traces/how-to/correlate-logs/). A server ingest key never belongs in a browser, public RUM token, query string or cross-origin request header. Limit CORS to intended origins and allow `traceparent`/`tracestate` where propagation needs them. Tracing does not grant replay consent or bypass replay access.
