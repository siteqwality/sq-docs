A **trace** is the path of one logical request through your system. It's made of **spans**. Each span is one unit of work (an HTTP request, a database query, a cache lookup) with a start time, end time, status, and structured attributes.

Use traces to answer "where did this request spend its time?" and "what did it talk to?"

## When to use traces

- Diagnosing tail latency: when a request takes 3 seconds, which service is at fault?
- Debugging cross-service errors: an upstream returns 500; trace shows the downstream call that returned 503.
- Visualizing service dependencies you didn't know you had.

## When NOT to use traces

- Use a [metric](/observability/metrics/overview/) for "how many requests per second".
- Use [logs](/observability/logs/overview/) for full payload bodies (you can correlate them via `trace_id`).

## How it works

Site Qwality is OpenTelemetry-compatible: instrument your apps with the OTel SDK, point the OTLP exporter at Site Qwality's traces endpoint, and traces flow in.

```
POST https://traces.siteqwality.com/v1/traces
Authorization: Bearer <api-key>
Content-Type: application/json | application/x-protobuf
```

The body shape is the standard OTLP `ExportTraceServiceRequest`. Most language SDKs handle this for you, and most default to protobuf, which is supported. See [sending OTLP over HTTP/protobuf](/observability/traces/how-to/otlp-protobuf/) for the exporter settings and the limits worth knowing (gRPC is not supported, and only traces are accepted).

Span attributes are stored as sent, so use the OTel semantic conventions (`http.request.method`, `http.response.status_code`, `db.system`, and so on) for consistent names across services. Custom attributes are accepted on every span.

## Anatomy of a span

| Field | Description |
|---|---|
| `trace_id` | Identifier for the whole trace. Same across every span in one request. |
| `span_id` | Identifier for this span. |
| `parent_span_id` | The span that triggered this one. Empty for the root span. |
| `service_name` | Logical service emitting the span (`web`, `api`, `db-proxy`). |
| `operation_name` | What this span did (`POST /checkout`, `SELECT users`). |
| `span_kind` | `SERVER`, `CLIENT`, `PRODUCER`, `CONSUMER`, `INTERNAL` (or `UNSPECIFIED`). |
| `start_time` / `end_time` | Wall-clock span boundaries. |
| `duration_ms` | Computed span length. |
| `status_code` | `UNSET`, `OK` or `ERROR`. |
| `attributes` | Free-form span metadata. |
| `resource_attributes` | Service-level metadata (host, region, version) shared across spans. |
| `events` | Timestamped log-like events within the span. |
| `links` | Cross-trace references (e.g. async followups). |

## Querying

Trace search reads your stored spans and groups them by trace. Common queries:

| Query | Use |
|---|---|
| `service_name=billing` | Traces with spans in one service. |
| `min_duration_ms=1000` | Traces with a span slower than one second. |
| `status=error` | Traces with failing spans. `error`, `ok` and `unset` are accepted in any case. |
| `tags={"http.route":"/checkout"}` | Exact match on a span attribute. See [tag filters](/observability/traces/reference/#tag-filters). |
| `search=card_declined` | Case-insensitive text search in operation names, status messages, and span and resource attribute values. |

The dashboard's **Traces** page composes these. For programmatic access, use `GET /traces/search` with a full-access API key.

## Service map

`GET /traces/service-map` returns nodes (services) and edges (caller→callee with call counts, error counts and latencies p50/p95/p99). An edge appears where a span in one instrumented service is the parent of a span in another, so databases and third-party APIs without their own spans do not appear as nodes. A node's numbers cover every span the service emitted (database calls and internal spans included), not just its incoming requests. Useful for:

- Finding unexpected dependencies ("we still call legacy-svc?").
- Spotting hot paths (the edge with the most calls).
- Identifying error sources (the edge with the highest error rate).

The dashboard renders this as an interactive graph.

## Correlation

- A log entry can carry a `trace_id` (top level or in `metadata`) and a `span_id` (in `metadata`). The trace view then lists that log, and a log whose `metadata` holds the `trace_id` shows a **View trace** link. See [correlate traces with logs](/observability/traces/how-to/correlate-logs/).
- `GET /traces/{trace_id}/logs` returns all logs tagged with the trace ID.
- The RUM SDK adds a `traceparent` header to fetch/XHR requests whose URLs match the application's [`trace_urls`](/observability/rum/how-to/remote-config/) setting, allowing browser → backend trace stitching.

<Aside type="tip">
For the most useful traces, instrument **at service boundaries** (incoming and outgoing HTTP, database calls, message queue ops). Don't instrument every internal function. The noise drowns the signal.
</Aside>

## Pricing

Traces count toward your telemetry allowance, which is measured in GB per month and pooled with logs and metrics; they are not priced per span. Retention follows the pack (3, 15 or 30 days). Sampling reduces volume, but it also changes what counts and error rates show; see the [sampling how-to](/observability/traces/how-to/sampling/) and the [observability overview](/observability/overview/#pricing).
