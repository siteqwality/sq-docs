## Backend logs and exemplars

Attach the active OpenTelemetry trace ID and span ID to log records through a logger integration. OTLP log records have dedicated trace/span fields; custom JSON accepts supported `trace_id`/`span_id` fields. IDs must be valid and nonzero. Matching a service name or timestamp alone does not prove a log belongs to a trace.

Open a recorded trace and its correlated Logs, Errors, metrics or browser context. Links retain the selected time window and signal permissions. An exemplar refers to a real recorded sample; an expired, unsampled or restricted target is shown as unavailable. Trace and log retention can differ.

## Browser opt-in

The RUM client token is public and separate from a server ingest key. Enable distributed trace propagation only for URLs you control. Set the appropriate trace URL/prefix settings in the RUM and telemetry collection settings. Never propagate server Authorization or a Site Qwality ingest key into a browser request.

For cross-origin requests, allow the intended frontend origin and the `traceparent` and `tracestate` request headers in your backend CORS configuration. Handle OPTIONS correctly. Permit credentials only when your application needs them and avoid a wildcard origin with credentials. Limit URL prefixes so third-party hosts do not receive trace context.

Existing stable CDN examples remain on the published SDK version. The new SDK 2.3.0 correlation work must be published and CDN-verified before changing stable install instructions to 2.3.0. Until that release, do not infer the newer correlation behavior merely because a setting is saved. See the [RUM quickstart](/observability/rum/quickstart/) for the published install path.

Replay links also require a retained replay, consent/sampling eligibility and replay access. Correlation does not enable recording or grant another user's data access. Synthetic checks and browser checks use their own configured propagation behavior.
