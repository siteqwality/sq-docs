Replay is configured through the [RUM application](/observability/rum/reference/), not through its own object. This page collects every replay-relevant setting in one place.

## Activation

Replay records only for sessions matching a [recording rule](/observability/rum/how-to/session-filters/) (an API session filter) with `capture_replay: true`. A new application has none, so replay is off until one exists. The SDK evaluates rules when its config loads or refreshes and after every sent error, Web Vital, action and `setUser` call, with no timer. Recording starts at the match, with no buffer of what came before. Once replay activates for a session it stays on for that session, and it resumes on later page loads in the same tab while an enabled rule still has `capture_replay: true`.

| Setting | Where | Default | Description |
|---|---|---|---|
| `capture_replay` | Recording rule | `false` | Record replay when this rule matches. |
| `enabled` | Recording rule | `true` | Disabled rules are never delivered to the SDK. |
| `priority` | Recording rule | `0` | Accepted by the API but not used. |

## Privacy settings

Set on the RUM application under `settings.privacy` and delivered to the SDK with its config. `PUT /rum/{app_id}` replaces the whole `settings` object, so send it back as `GET /rum/{app_id}` returns it with only `privacy` changed:

| Field | Documented default | Effect |
|---|---|---|
| `mask_inputs` | `true` | Masks all input values in the recording (rrweb `maskAllInputs`). |
| `mask_text` | `false` | Masks all user-visible text in the recording. |

`settings.privacy` also carries [`hide_action_text`](/observability/rum/how-to/remote-config/#hiding-element-text-in-click-names), which is not a replay setting. Send it back unchanged too.

<Aside type="danger" title="Read the stored value, not the documented default">
Applications created earlier can have `mask_inputs` stored as `false`, because the value was written into the application's settings at creation time and nothing rewrites it afterwards. The documented default governs what a new application is created with; **the stored value is what governs what is recorded**.

`GET /rum/{app_id}` returns `settings.privacy` for the application, and the dashboard shows the same two values as toggles under **RUM → Settings → Privacy**. Check them on every application you operate before relying on either one. There is no bulk fix and no backfill.

`mask_text` is off, which is a deliberate default and not a defect: with it off, all user-visible page text is recorded verbatim. Turn it on, or apply `rr-mask` to the elements that matter, if the pages being recorded render anything you would not want in a recording.
</Aside>

## Segment mechanics

The SDK records with [rrweb](https://www.rrweb.io), which is lazy-loaded only when replay activates. Recorded events are shipped as **segments**:

- A segment is flushed when it reaches 100 rrweb events, and at least every 30 seconds.
- `segment_index` starts at 0 and increments per flush within the session.
- A failed upload is retried like an event batch (see [batching and delivery](/sdk/reference/#batching-and-delivery)). Up to 10 segments or 4 MB wait in memory, oldest dropped first.

Ingest request (sent by the SDK):

```
POST https://replay.siteqwality.com/v1/segments?session_id={id}&segment_index={n}
Authorization: Bearer <client_token>
Content-Type: application/json

{ "session_id": "...", "segment_index": 0, "events": [ ... ] }
```

## Stored segment fields

| Field | Type | Description |
|---|---|---|
| `session_id` | string | The RUM session. |
| `segment_index` | int | Position within the session. |
| `timestamp` | string | When the segment was received. |
| `s3_key` | string | Storage location (internal). |
| `content_hash` | string | First 16 hex digits of the payload's SHA-256. |
| `first_event_ts` | string | Time of the earliest event in the segment. |
| `size_bytes` | int | Segment payload size. |

Each distinct payload is stored once. A retried upload with the same content is accepted and not stored again.

## Retrieval

`GET /rum/{app_id}/replay/{session_id}` returns one entry per stored segment, ordered by `first_event_ms`, then `segment_index`:

| Field | Description |
|---|---|
| `segment_index` | Position within the session. Not unique: older SDK versions restart it at 0 on every page load. |
| `url` | Presigned download URL for the segment payload. |
| `size_bytes` | Segment payload size. |
| `first_event_ms` | Time of the earliest event in the segment, in Unix milliseconds. |
| `expires_in_seconds` | URL lifetime: 900 seconds (15 minutes). Re-fetch the list for fresh URLs. |

Play the segments in the order returned. Do not deduplicate or sort them by `segment_index`.

The dashboard player consumes these; you can also fetch them directly for your own tooling.

## Replay links

The dashboard player opens at a given moment from its URL, `https://app.siteqwality.com/rum/{app_id}/replay/{session_id}`:

| Query | Effect |
|---|---|
| `?t=754`, `?t=12:34`, `?t=1:02:03` | Opens at that offset into the recording (seconds, `m:ss` or `h:mm:ss`), clamped to the recording. **Copy link at current time** writes this form. |
| `?at=<epoch ms>&event=<event_id>` | Opens 5 seconds before that absolute time (never before the start) and highlights the event row with that ID. An error's **Watch replay** link uses the error's `error_ts_ms` and `event_id`. |

When both are present, `t` wins.
