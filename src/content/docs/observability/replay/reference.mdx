> **SDK versions:** The recorder behavior and examples below describe SDK 1.x unless stated otherwise. SDK 2.1 has a different endpoint, pre-trigger memory buffer and privacy enforcement. Read [replay 2.1 transport](/sdk/v2/#replay-21-transport) and [buffer and privacy](/sdk/v2/#replay-buffer-and-privacy) before upgrading; replay v2 must be enabled for your application.

Replay is configured through the [RUM application](/observability/rum/reference/), not through its own object. This page collects every replay-relevant setting in one place.

## Activation

Replay records only for sessions matching a Replay [recording rule](/observability/rum/how-to/session-filters/). A new application starts with **Errored sessions** (every errored session) and an Auto sample within the replay quota; an application created before recording rules v2 keeps the rules copied from its session filters. With SDK 1.x, recording starts at the match, with no buffer of what came before, and only rules [SDK 1.x can express](/observability/rum/how-to/session-filters/#sdk-versions) apply. Once replay activates for a session it stays on for that session, and it resumes on later page loads in the same tab while an enabled Replay rule still applies.

| Setting | Where | Default | Description |
|---|---|---|---|
| `capture` | Recording rule | required | `replay` records a replay when the rule matches. |
| `sample_rate`, `auto_sample` | Recording rule | `1`, `false` | Share of matching sessions; Auto follows the replay quota. SDK 2.0. |
| `min_duration_ms`, `require_interaction` | Recording rule | `3000`, `true` for Replay | Gates before upload, bypassed by error conditions. SDK 2.0. |
| `enabled` | Recording rule | `true` | Disabled rules are never applied. |

## Privacy settings

Set on the RUM application under `settings.privacy` and delivered to the SDK with its config. Change them with `PATCH /rum/{app_id}`, sending only the keys you change; it needs an account admin or an API key with no scope restriction. A [privacy level](/observability/rum/how-to/remote-config/#privacy-levels) writes these flags for you:

| Field | Documented default | Effect |
|---|---|---|
| `mask_inputs` | `true` | Masks all input values in the recording (rrweb `maskAllInputs`). |
| `mask_text` | `false` | Masks all user-visible text in the recording. |

`settings.privacy` also carries [`hide_action_text`](/observability/rum/how-to/remote-config/#hiding-element-text-in-click-names), which is not a replay setting.

<Aside type="danger" title="Read the stored value, not the documented default">
Applications created earlier can have `mask_inputs` stored as `false`, because the value was written into the application's settings at creation time and nothing rewrites it afterwards. The documented default governs what a new application is created with; **the stored value is what governs what is recorded**.

`GET /rum/{app_id}` returns `settings.privacy` for the application, and the dashboard shows the same two values as toggles under **RUM → Settings → Privacy**. Check them on every application you operate before relying on either one. There is no bulk fix and no backfill.

`mask_text` is off, which is a deliberate default and not a defect: with it off, all user-visible page text is recorded verbatim. Turn it on, or apply `rr-mask` to the elements that matter, if the pages being recorded render anything you would not want in a recording.
</Aside>

## Segment mechanics

The SDK records with [rrweb](https://www.rrweb.io), which is lazy-loaded only when replay activates. Recorded events are shipped as **segments**:

- A segment is flushed when it reaches 100 rrweb events, and at least every 30 seconds.
- `segment_index` starts at 0 and increments per flush within the session.
- A failed upload is retried like an event batch (see [batching and delivery](/sdk/reference/#batching-and-delivery)). Up to 10 segments or 4 MB wait in memory, oldest dropped first.

Ingest request (sent by the SDK):

```
POST https://replay.siteqwality.com/v1/segments?session_id={id}&segment_index={n}
Authorization: Bearer <client_token>
Content-Type: application/json

{ "session_id": "...", "segment_index": 0, "events": [ ... ] }
```

## Stored segment fields

| Field | Type | Description |
|---|---|---|
| `session_id` | string | The RUM session. |
| `segment_index` | int | Position within the session. |
| `timestamp` | string | When the segment was received. |
| `s3_key` | string | Storage location (internal). |
| `content_hash` | string | First 16 hex digits of the payload's SHA-256. |
| `first_event_ts` | string | Time of the earliest event in the segment. |
| `size_bytes` | int | Segment payload size. |

Each distinct payload is stored once. A retried upload with the same content is accepted and not stored again.

## Who can watch a replay

<Aside type="note" title="Wave 2 rollout candidate">
The manifest, chunk URLs, compaction and replay access controls below describe the Wave 2 candidate. They become available after the corresponding backend and player rollout. SDK 2.1 replay transport still requires enablement for your application; see the [versioned SDK guide](/sdk/v2/#replay-21-transport).
</Aside>

A replay shows what a user saw, so reading one needs more than read access to RUM.

| Caller | Needs |
|---|---|
| Team member | The account's replay access level: **Members** (default) lets any member watch, **Admins** only admins and super admins. **Viewers and auditors never can.** |
| API key or [M2M client](/enterprise/api-clients/) | The `read:rum_replay` scope, plus `read:rum`. A key with no scope list does not get replays: add both scopes. |
| AI assistant | Never. The [MCP server](/integrations/mcp/) does not expose replay content. |

Change the access level with `PUT /rum/settings` (account admins only), sending only the fields you change:

```json
{ "replay_access": "admins", "body_access": "members" }
```

`body_access` sets the same rule for network bodies, headers and console arguments. `GET /rum/settings` returns both.

Callers without access get a `403`. An application outside your account returns `404`.

## Retrieval

The player loads a replay in two steps: a manifest that lists every piece without URLs, then short-lived URLs for the pieces it is about to play.

### Manifest

`GET /rum/{app_id}/sessions/{session_id}/replay`:

| Field | Description |
|---|---|
| `status` | `ready` (all compacted), `live` (a segment arrived in the last 2 minutes on a page still open: poll every 5 seconds), `processing` (some page loads are still raw segments; they play, and are compacted within about 35 minutes) or `none`. |
| `reason` | With `none`, why nothing was recorded, when the SDK reported it: `not_sampled`, `no_rule`, `consent`, `quota`, `privacy_url`, `too_large` or `opted_out`. |
| `start_ms`, `end_ms` | First and last recorded event, Unix milliseconds. |
| `active_ms`, `activity` | Time with user input, and the `[start, end]` ranges it falls in, for skipping inactivity. |
| `windows[]` | One per browser tab: `window_id`, `index` (0 for the tab that recorded first) and its `page_loads[]`. |
| `page_loads[]` | One per document: `page_load_id`, `url` (minimised), `start_ms`, `end_ms` and its `chunks[]` in playback order. |
| `chunks[]` | `id` (opaque), `kind` (`block` or `segment`), `start_ms`, `end_ms`, `bytes`, and `snapshot` (playback can start here). |

SDK 1.x and 2.0 record no tabs or page loads. Until compaction infers their page loads, their segments are listed under the nil `window_id` and `page_load_id`.

### Chunk URLs

`POST /rum/{app_id}/sessions/{session_id}/replay/chunks` with `{"ids": [...]}`, at most 20 ids, returns one entry per id found (unknown ids are left out):

| Field | Description |
|---|---|
| `id`, `kind` | The id asked for, and `block`, `segment` or `stylesheet`. |
| `url` | Presigned GET URL. |
| `range` | For blocks: send it as the `Range` header. |
| `expires_in` | 120 seconds. On a `403` from storage, ask for the URL again. |

Block ids include their compaction version. Keep ids opaque and use the range returned with each URL. If a chunk id is omitted, refresh the manifest before retrying. Existing URLs remain valid through recompaction until their 120-second expiry.

How to play each kind:

- **`block`**: a compacted block, one gzip stream holding a JSON array of rrweb events. Gunzip it yourself; the response has no `Content-Encoding`. Every block starts with Meta and a full snapshot and plays on its own. When you continue from the previous block of the same page load, skip the new block's leading Meta and full snapshot events and every event marked `"sqk": 1`: they only rebuild the state the player already has.
- **`stylesheet`**: plain CSS. A block's `_cssText` attribute or style text that reads `sq-css:<hash>` names one: request `css:<hash>` with the block's other ids and swap in its text before handing events to rrweb.
- **`segment`**: a raw segment as the SDK sent it, either a JSON array of rrweb events (SDK 2.1+) or `{session_id, segment_index, events}` (SDK 1.x and 2.0).

### Compaction

About 30 minutes after a page load goes quiet (2 minutes once the SDK marks it ended), its segments are compacted into blocks. Compaction applies the application's current [privacy settings](#privacy-settings) and selectors again on the server, including recordings from older SDKs. These rules apply at compaction time; changing settings does not automatically recompact existing blocks. It also removes duplicated events, moves stylesheets of 1 KB or more into a shared store, and adds a full snapshot about every megabyte so seeking never replays the whole page load. Raw segments stay until their retention ends.

### Who watched

Every replay view is written to the [audit log](/enterprise/audit-log/) as `rum.replay.viewed`, with `target_kind` `rum_session` and the session as `target_id`, at most once per viewer per 30 minutes. Whenever the manifest, the chunk URLs or the legacy endpoint below return something to play, the view is recorded first; if it cannot be recorded, the request fails with a `500` and returns no content. Within the 30 minutes, further requests by the same viewer add no entries.

`GET /rum/{app_id}/sessions/{session_id}/viewers` lists who watched over the last 90 days, most recent first: `actor_type`, the person or key (`user_id`, `email`, `api_key_id`, `api_key_name`, `m2m_client_id`), `first_viewed_at`, `last_viewed_at` and `views`.

### Legacy segment list

<Aside type="caution" title="Deprecated">
`GET /rum/{app_id}/replay/{session_id}` predates compaction and returns raw segments only. It follows the same access rules and records a view like the manifest. Use the manifest for new tooling.
</Aside>

It returns one entry per stored segment, ordered by `first_event_ms`, then `segment_index`:

| Field | Description |
|---|---|
| `segment_index` | Position within the session. Not unique: older SDK versions restart it at 0 on every page load. |
| `url` | Presigned download URL for the segment payload. |
| `size_bytes` | Segment payload size. |
| `first_event_ms` | Time of the earliest event in the segment, in Unix milliseconds. |
| `expires_in_seconds` | URL lifetime: 900 seconds (15 minutes). Re-fetch the list for fresh URLs. |

Play the segments in the order returned. Do not deduplicate or sort them by `segment_index`.

## Replay links

The dashboard player opens at a given moment from its URL, `https://app.siteqwality.com/rum/{app_id}/replay/{session_id}`:

| Query | Effect |
|---|---|
| `?t=754`, `?t=12:34`, `?t=1:02:03` | Opens at that offset into the recording (seconds, `m:ss` or `h:mm:ss`), clamped to the recording. **Copy link at current time** writes this form. |
| `?at=<epoch ms>&event=<event_id>` | Opens 5 seconds before that absolute time (never before the start) and highlights the event row with that ID. An error's **Watch replay** link uses the error's `error_ts_ms` and `event_id`. |

When both are present, `t` wins.
