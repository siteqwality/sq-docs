Replay is configured through the [RUM application](/observability/rum/reference/), not through its own object. This page collects every replay-relevant setting in one place.

## Activation

Replay records only for sessions matching a Replay [recording rule](/observability/rum/how-to/session-filters/). A new application starts with **Errored sessions** (every errored session) and an Auto sample within the replay quota. While a Replay rule could still match, the SDK buffers the last 60 to 120 seconds in memory, and a match sends that buffer before streaming; see [replay buffer and privacy](/sdk/v2/#replay-buffer-and-privacy). Once replay activates for a session it stays on for the rest of that session, in every tab and across page loads.

| Setting | Where | Default | Description |
|---|---|---|---|
| `capture` | Recording rule | required | `replay` records a replay when the rule matches. |
| `sample_rate`, `auto_sample` | Recording rule | `1`, `false` | Share of matching sessions; Auto follows the replay quota. |
| `min_duration_ms`, `require_interaction` | Recording rule | `3000`, `true` for Replay | Gates before upload, bypassed by error conditions. |
| `enabled` | Recording rule | `true` | Disabled rules are never applied. |

## Privacy settings

Set on the RUM application under `settings.privacy` and delivered to the SDK with its config. Change them with `PATCH /rum/{app_id}`, sending only the keys you change; it needs an account admin or an API key with no scope restriction. A [privacy level](/observability/rum/how-to/remote-config/#privacy-levels) writes these flags for you:

| Field | Documented default | Effect |
|---|---|---|
| `mask_inputs` | `true` | Masks all input values in the recording (rrweb `maskAllInputs`). Any privacy level masks inputs whatever this flag says. |
| `mask_text` | `false` | Masks all user-visible text in the recording. Strict masks text whatever this flag says. |

`settings.privacy` also carries the [privacy level](/observability/rum/how-to/remote-config/#privacy-levels), the personal data patterns, the per-element selectors (`mask_selectors`, `unmask_selectors`, `block_selectors`, `ignore_input_selectors`) and `never_record_urls`; see [replay privacy](/observability/replay/overview/#privacy). It also carries [`hide_action_text`](/observability/rum/how-to/remote-config/#hiding-element-text-in-click-names), which is not a replay setting.

<Aside type="danger" title="Read the stored value, not the documented default">
Applications created earlier can have `mask_inputs` stored as `false`, because the value was written into the application's settings at creation time and nothing rewrites it afterwards. The documented default governs what a new application is created with; **the stored value is what governs what is recorded**.

`GET /rum/{app_id}` returns `settings.privacy` for the application, and the dashboard shows the same two values as toggles under **RUM → Settings → Privacy**. Check them on every application you operate before relying on either one. There is no bulk fix and no backfill.

`mask_text` is off, which is a deliberate default and not a defect: with it off, and below Strict, user-visible page text is recorded (Balanced scrubs emails, card numbers and long digit runs from it). Turn it on, choose Strict, or add `mask_selectors` for the elements that matter, if the pages being recorded render anything you would not want in a recording.
</Aside>

## Segment mechanics

The SDK records with [rrweb](https://www.rrweb.io), in a separate chunk loaded only for sessions a Replay rule has matched or could still match. Every tab records its own window, and each page load is its own stream of **segments**:

- A segment closes at 20 seconds or about 2.5 MB of JSON, and when the tab is hidden. A page's first full snapshot is sent at once.
- Segments are numbered from 0 per page load (`q`) and carry the session, window and page load IDs, the event range and, on the last one, a final marker.
- Each segment is a JSON array of rrweb events, gzipped where the browser can, sent to `POST https://in-replay.siteqwality.com/v2/segments` with the client token in `Authorization` and the index in the `x-sq-replay-index` header.
- A failed upload is retried with backoff, and a `Retry-After` holds every send. See [replay transport](/sdk/v2/#replay-transport) for the full contract.

## Stored segment fields

| Field | Type | Description |
|---|---|---|
| `session_id`, `window_id`, `page_load_id` | uuid | The RUM session, browser tab and document. |
| `seq` | int | Position within the page load, from 0. Gaps mean segments not (yet) received. |
| `timestamp` | string | When the segment was received. |
| `first_event_ts`, `last_event_ts` | string | Time of the earliest and latest event in the segment. |
| `event_count` | int | rrweb events in the segment. |
| `has_full_snapshot`, `is_final` | bool | Playback can start here; the SDK's last segment of the page load. |
| `content_hash` | string | First 16 hex digits of the SHA-256 of the segment's JSON. |
| `size_bytes`, `uncompressed_bytes` | int | Stored (gzip) size and JSON size. |
| `sdk_version`, `rule_id` | string | The SDK release, and the recording rule that started recording. |

Each distinct payload is stored once. A retried upload with the same content is accepted and not stored again.

## Who can watch a replay

A replay shows what a user saw, so reading one needs more than read access to RUM.

| Caller | Needs |
|---|---|
| Team member | The account's replay access level: **Members** (default) lets any member watch, **Admins** only admins and super admins. **Viewers and auditors never can.** |
| API key or [M2M client](/enterprise/api-clients/) | The `read:rum_replay` scope, plus `read:rum`. A key with no scope list does not get replays: add both scopes. |
| AI assistant | Never. The [MCP server](/integrations/mcp/) does not expose replay content. |

Change the access level with `PUT /rum/settings` (account admins only), sending only the fields you change:

```json
{ "replay_access": "admins", "body_access": "members" }
```

`body_access` sets the same rule for network bodies, headers and console arguments. `GET /rum/settings` returns both.

Callers without access get a `403`. An application outside your account returns `404`.

## Retrieval

The player loads a replay in two steps: a manifest that lists every piece without URLs, then short-lived URLs for the pieces it is about to play.

### Manifest

`GET /rum/{app_id}/sessions/{session_id}/replay`:

| Field | Description |
|---|---|
| `status` | `ready` (all compacted), `live` (a segment arrived in the last 2 minutes on a page still open: poll every 5 seconds), `processing` (some page loads are still raw segments; they play, and are compacted within about 35 minutes) or `none`. |
| `reason` | With `none`, why nothing was recorded, when the SDK reported it: `not_sampled`, `no_rule`, `consent`, `quota`, `privacy_url`, `too_large` or `opted_out`. |
| `start_ms`, `end_ms` | First and last recorded event, Unix milliseconds. |
| `active_ms`, `activity` | Time with user input, and the `[start, end]` ranges it falls in, for skipping inactivity. |
| `windows[]` | One per browser tab: `window_id`, `index` (0 for the tab that recorded first) and its `page_loads[]`. |
| `page_loads[]` | One per document: `page_load_id`, `url` (minimised), `start_ms`, `end_ms` and its `chunks[]` in playback order. |
| `chunks[]` | `id` (opaque), `kind` (`block` or `segment`), `start_ms`, `end_ms`, `bytes`, and `snapshot` (playback can start here). |

### Chunk URLs

`POST /rum/{app_id}/sessions/{session_id}/replay/chunks` with `{"ids": [...]}`, at most 20 ids, returns one entry per id found (unknown ids are left out):

| Field | Description |
|---|---|
| `id`, `kind` | The id asked for, and `block`, `segment` or `stylesheet`. |
| `url` | Presigned GET URL. |
| `range` | For blocks: send it as the `Range` header. |
| `expires_in` | 120 seconds. On a `403` from storage, ask for the URL again. |

Block ids include their compaction version. Keep ids opaque and use the range returned with each URL. If a chunk id is omitted, refresh the manifest before retrying. Existing URLs remain valid through recompaction until their 120-second expiry.

How to play each kind:

- **`block`**: a compacted block, one gzip stream holding a JSON array of rrweb events. Gunzip it yourself; the response has no `Content-Encoding`. Every block starts with Meta and a full snapshot and plays on its own. When you continue from the previous block of the same page load, skip the new block's leading Meta and full snapshot events and every event marked `"sqk": 1`: they only rebuild the state the player already has.
- **`stylesheet`**: plain CSS. A block's `_cssText` attribute or style text that reads `sq-css:<hash>` names one: request `css:<hash>` with the block's other ids and swap in its text before handing events to rrweb.
- **`segment`**: a raw segment, a JSON array of rrweb events as the SDK sent it: gzip, or plain JSON for an uncompressed tail sent at page close. Check for the gzip header before unpacking.

### Compaction

About 30 minutes after a page load goes quiet (2 minutes once the SDK marks it ended), its segments are compacted into blocks. Compaction applies the application's current [privacy settings](#privacy-settings) and selectors again on the server. These rules apply at compaction time; changing settings does not automatically recompact existing blocks. It also removes duplicated events, moves stylesheets of 1 KB or more into a shared store, and adds a full snapshot about every megabyte so seeking never replays the whole page load. Raw segments stay until their retention ends.

### Who watched

Every replay view is written to the [audit log](/enterprise/audit-log/) as `rum.replay.viewed`, with `target_kind` `rum_session` and the session as `target_id`, at most once per viewer per 30 minutes. Whenever the manifest or the chunk URLs return something to play, the view is recorded first; if it cannot be recorded, the request fails with a `500` and returns no content. Within the 30 minutes, further requests by the same viewer add no entries.

`GET /rum/{app_id}/sessions/{session_id}/viewers` lists who watched over the last 90 days, most recent first: `actor_type`, the person or key (`user_id`, `email`, `api_key_id`, `api_key_name`, `m2m_client_id`), `first_viewed_at`, `last_viewed_at` and `views`.

## Replay links

The dashboard player opens at a given moment from its URL, `https://app.siteqwality.com/rum/{app_id}/replay/{session_id}`:

| Query | Effect |
|---|---|
| `?t=754`, `?t=12:34`, `?t=1:02:03` | Opens at that offset into the recording (seconds, `m:ss` or `h:mm:ss`), clamped to the recording. **Copy link at current time** writes this form. |
| `?at=<epoch ms>&event=<event_id>` | Opens 5 seconds before that absolute time (never before the start) and highlights the event row with that ID. An error's **Watch replay** link uses the error's `error_ts_ms` and `event_id`. |

When both are present, `t` wins.
