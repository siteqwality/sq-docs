This guide configures logs. You need a Site Qwality account with early access to telemetry (email [hello@siteqwality.com](mailto:hello@siteqwality.com) to request it) and an ingest key from [API keys](https://app.siteqwality.com/account?tab=api-keys). Replace YOUR_INGEST_KEY on your server. Never use a real key in a public example.

## 1. Install Fly Log Shipper in your organization

Keep the shipper private. Preserve the supplied NATS source and transforms. Select the application/region SUBJECT you intend to collect. Review and pin the shipper revision before deployment.

```bash
git clone https://github.com/superfly/fly-log-shipper.git
cd fly-log-shipper
fly launch --no-deploy
```

## 2. Append an HTTP sink to vector.toml

The official shipper configuration uses the log_json transform. Preserve it and its NATS source when adding this sink. Store the key as a Fly secret and use Vector environment substitution in production. Keep a single NATS consumer queue for replicas to avoid duplicate logs.

```toml
[sinks.siteqwality]
type = "http"
inputs = ["log_json"]
uri = "https://otlp.siteqwality.com/ingest"
method = "post"
encoding.codec = "json"
framing.method = "newline_delimited"
batch.max_bytes = 1000000
[sinks.siteqwality.request.headers]
Authorization = "Bearer YOUR_INGEST_KEY"
"Content-Type" = "application/x-ndjson"
"X-Service" = "my-service"
"X-Env" = "production"
```

## 3. Deploy the shipper configuration

Inspect fly logs for sink errors and open Logs in Site Qwality. Add the private Vector health check from Fly documentation so a stalled shipper is visible.

```bash
fly deploy --file-local="/etc/vector/vector.toml=./vector.toml"
```

## Confirm readable data

Open [Add data](https://app.siteqwality.com/add-data?platform=fly), select the signal and choose **Check again**. This reads retained data permitted for your account and member. A permission error is not proof that collection failed. Open the explorer, select your service/environment and a recent window.

- Create an ingest key for this account and only the signals you send. Read-only keys cannot ingest; ingest keys cannot query. Use a separate read-only API key or your signed-in session for exploration.
- A successful OTLP HTTP response is 200 with an ExportResponse. Inspect partialSuccess for rejected records. JSON /ingest and /metrics return 200 with accepted, rejected and errors. Remote-write returns 204 on full acceptance; platform adapters use their own acknowledgement formats.
- Accepted data has been written to storage or durable spill. It can appear later during replay. Acceptance does not mean every record passed validation or that it is already searchable. Retry transient 429/5xx failures with backoff and honor Retry-After; do not blindly resend an entire partially accepted batch.
- Requests allow 4,000,000 wire bytes, up to 40,000,000 inflated bytes for logs/traces or 16,000,000 for metrics, and at most 100:1 inflation. Use gzip or supported deflate on HTTP; Prometheus uses Snappy. Split oversized requests instead of retrying unchanged.
- 401/403: check key, account, signal scope and collection access. 413: reduce batch bytes. 415: check protocol and content type. 429: check quota/cardinality/rate and wait for Retry-After. Persistent 5xx: retain your local buffer and contact support with request time, never the key.

## Production checklist

Store the key in your platform secret mechanism, rotate it when exposed and remove test keys. Set a stable service.name and deployment.environment.name; avoid user IDs or unbounded values in metric labels. Prefer a persistent queue, bounded retries and exporter failure monitoring. Review redaction and processors before increasing traffic.
