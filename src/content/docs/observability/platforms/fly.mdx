This guide covers logs. Replace `YOUR_INGEST_KEY` with your key.

<BeforeYouStart />

## 1. Install Fly Log Shipper in your organization

Keep the shipper private. Preserve the supplied NATS source and transforms. Select the application/region SUBJECT you intend to collect. Review and pin the shipper revision before deployment.

```bash
git clone https://github.com/superfly/fly-log-shipper.git
cd fly-log-shipper
fly launch --no-deploy
```

## 2. Append an HTTP sink to vector.toml

The sink reads from the shipper's `log_json` transform. In production, store the key as a Fly secret and use Vector environment substitution. Keep a single NATS consumer queue across replicas to avoid duplicate logs.

```toml
[sinks.siteqwality]
type = "http"
inputs = ["log_json"]
uri = "https://otlp.siteqwality.com/ingest"
method = "post"
encoding.codec = "json"
framing.method = "newline_delimited"
batch.max_bytes = 1000000
[sinks.siteqwality.request.headers]
Authorization = "Bearer YOUR_INGEST_KEY"
"Content-Type" = "application/x-ndjson"
"X-Service" = "my-service"
"X-Env" = "production"
```

## 3. Deploy the shipper configuration

Check `fly logs` for sink errors, then open Logs in Site Qwality. Add the private Vector health check from the Fly documentation so a stalled shipper is visible.

```bash
fly deploy --file-local="/etc/vector/vector.toml=./vector.toml"
```

## See your data

Open [Logs](https://app.siteqwality.com/logs). New data usually shows up within a minute. Nothing arriving? See [failure handling](/observability/ingest/#failure-handling).

## Production checklist

Store the key in your platform secret mechanism, rotate it when exposed and remove test keys. Keep service and environment names stable. Prefer a persistent queue, bounded retries and delivery failure monitoring. Review [redaction and processors](/observability/pipelines/) before increasing traffic.
