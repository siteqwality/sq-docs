<Aside type="caution" title="Log drains not available yet">
Vercel log drains (`/v1/vercel`) are not available during early access, so step 1 does not work today. A Vercel traces drain (step 2) sends to the standard OTLP traces endpoint.
</Aside>

This guide configures traces, and logs once log drains are available. You need a Site Qwality account with early access to telemetry (email [hello@siteqwality.com](mailto:hello@siteqwality.com) to request it) and an ingest key from [API keys](https://app.siteqwality.com/account?tab=api-keys). Replace YOUR_INGEST_KEY on your server. Never use a real key in a public example.

## 1. Create a signed Logs drain (not available yet)

Once log drains are available, add a Logs drain in Vercel Team Settings, Drains, and select projects/environments. Copy its signature verification secret into Usage and settings, Collection, Vercel signing secret. Site Qwality requires x-vercel-signature using HMAC-SHA1 over the exact request bytes, even though Vercel calls signing optional. Save the secret before testing the drain.

```text
Destination: https://otlp.siteqwality.com/v1/vercel
Encoding: JSON or NDJSON
Authorization: Bearer YOUR_INGEST_KEY
X-Service: my-service
X-Env: production
```

## 2. Create a separate OTLP Traces drain

Choose Traces as the drain data type. The log-drain signing requirement applies to /v1/vercel; traces use the normal OTLP authorization contract. Drain availability depends on your Vercel plan.

```text
Destination: https://otlp.siteqwality.com/v1/traces
Encoding: OTLP HTTP Protobuf or JSON
Authorization: Bearer YOUR_INGEST_KEY
```

## 3. Generate and verify

Do not send Speed Insights, Web Analytics or Audit Log envelopes to the log adapter. Never put the ingest key in NEXT_PUBLIC_* variables.

```text
Redeploy the project, make a request, and emit a server log. Check the Vercel drain test result and the Site Qwality explorer.
```

## Confirm readable data

Open [Add data](https://app.siteqwality.com/add-data?platform=vercel), select the signal and choose **Check again**. This reads retained data permitted for your account and member. A permission error is not proof that collection failed. Open the explorer, select your service/environment and a recent window.

- Create an ingest key for this account and only the signals you send. Read-only keys cannot ingest; ingest keys cannot query. Use a separate read-only API key or your signed-in session for exploration.
- A successful OTLP HTTP response is 200 with an ExportResponse. Inspect partialSuccess for rejected records. JSON /ingest and /metrics return 200 with accepted, rejected and errors. Remote-write returns 204 on full acceptance; platform adapters use their own acknowledgement formats.
- Accepted data has been written to storage or durable spill. It can appear later during replay. Acceptance does not mean every record passed validation or that it is already searchable. Retry transient 429/5xx failures with backoff and honor Retry-After; do not blindly resend an entire partially accepted batch.
- Requests allow 4,000,000 wire bytes, up to 40,000,000 inflated bytes for logs/traces or 16,000,000 for metrics, and at most 100:1 inflation. Use gzip or supported deflate on HTTP; Prometheus uses Snappy. Split oversized requests instead of retrying unchanged.
- 401/403: check key, account, signal scope and collection access. 413: reduce batch bytes. 415: check protocol and content type. 429: check quota/cardinality/rate and wait for Retry-After. Persistent 5xx: retain your local buffer and contact support with request time, never the key.

## Production checklist

Store the key in your platform secret mechanism, rotate it when exposed and remove test keys. Set a stable service.name and deployment.environment.name; avoid user IDs or unbounded values in metric labels. Prefer a persistent queue, bounded retries and exporter failure monitoring. Review redaction and processors before increasing traffic.
