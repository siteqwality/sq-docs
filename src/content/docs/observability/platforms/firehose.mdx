This guide covers logs and metrics. Replace `YOUR_INGEST_KEY` with your key.

## 1. Configure an HTTP destination

Firehose sends the access key in `X-Amz-Firehose-Access-Key`, without Bearer; do not add Authorization or `api_key` as well. Choose small buffers so the encoded envelope stays below 4,000,000 bytes, since base64 adds roughly one third.

```text
Endpoint URL: https://otlp.siteqwality.com/v1/firehose
Access key: YOUR_INGEST_KEY
Content encoding: GZIP
Retry duration: choose for your delivery requirements
S3 backup: enable failed-data backup
```

## 2. Select the source payload

The adapter decodes CloudWatch log events and length-delimited OTLP metric messages, so configure the source output to match. Any rejected record fails the batch, so Firehose can retry or back it up.

```text
CloudWatch Logs: preserve the supported gzip/base64 CloudWatch log envelope.
CloudWatch Metric Streams: choose OpenTelemetry 1.0.0, not JSON or OpenTelemetry 0.7.
```

## 3. Test delivery

Firehose buffers can add latency, and its retries may duplicate records. Keep failed-data backup enabled.

```text
Use the Firehose destination test, then generate a real CloudWatch event or metric. Inspect DeliveryToHttpEndpoint failures and the S3 error output, and confirm the relevant explorer.
```

## See your data

Open [Logs](https://app.siteqwality.com/logs) or [Metrics](https://app.siteqwality.com/metrics). Data shows up once Firehose flushes its buffer. Nothing arriving? See [failure handling](/observability/ingest/#failure-handling).

## Production checklist

Store the key in your platform secret mechanism, rotate it when exposed and remove test keys. Keep service and environment names stable, avoid user IDs or unbounded values in metric labels and monitor delivery errors. Review [redaction and processors](/observability/pipelines/) before increasing traffic.
