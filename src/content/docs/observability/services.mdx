Open **Services**, then the **From telemetry** tab, to explore services observed in telemetry. The **Service map** and **Deployments** tabs sit beside it. Use stable `service.name`, environment and version resource fields. A service name groups telemetry; a linked incident service supplies ownership, tier, on-call and runbook context.

Service and endpoint RED shows received request rate, errors and duration with sampling and quality indicators. RED is derived from received spans, before your trace exclusion or sampling rules where supported. It does not reconstruct traffic the SDK never sent, and weighted counts can be estimates. A dependency map needs actual matching client/server trace relationships; missing spans and short retention can leave edges incomplete.

Deployment markers come from observed service versions and deployment information. They help compare error, rate and duration changes, but they show reported versions, not proof that a whole fleet deployed. Open related logs, metrics, trace samples and Errors with the same time range. An admin links a telemetry service to its incident service with **Catalog links**.

| Read endpoint | Purpose |
|---|---|
| `GET /services/telemetry` | List observed services. |
| `GET /services/telemetry/{name}` | Service overview. |
| `GET /services/telemetry/{name}/endpoints` | Endpoint RED. |
| `GET /services/telemetry/{name}/versions` | Observed versions. |
| `GET /services/telemetry/{name}/dependencies` | Service dependencies. |
| `GET /services/map` | Scoped map. |
| `GET /services/deployments` | Deployment markers. |
| `PUT /services/{id}/telemetry-links` | Link an incident service to telemetry identities. |

These are API-relative paths at `https://api.siteqwality.com`. URL-encode names. Derived results can be pending or partial; wait or narrow the query rather than treating an empty result as zero traffic.
