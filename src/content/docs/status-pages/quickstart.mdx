By the end of this guide you'll have a public status page at `https://statuspage.siteqwality.com/<account-id>/<page-id>` showing the status of an HTTP check, with a custom logo and brand color, and you'll have published one incident update to it.

## Prerequisites

- An existing HTTP check (or [follow the first-monitor quickstart](/getting-started/signup-and-first-monitor/)).
- A logo as PNG or SVG, ≤2MB.

## 1. Create the page

<Tabs syncKey="interface">
<TabItem label="Dashboard">

<Steps>

1. **Status pages → New status page.**

2. Set the **friendly name**. This is the public page title, so use your product name, e.g. `Acme Cloud`.

3. Click **Create**. You're dropped onto the page settings, with the page's public URL (`https://statuspage.siteqwality.com/<account-id>/<page-id>`) shown at the top.

</Steps>

</TabItem>
<TabItem label="API">

```bash
curl -X POST https://api.siteqwality.com/status_page \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "friendly_name": "Acme Cloud" }'
```

Returns the new page's `id`. The public URL is `https://statuspage.siteqwality.com/<account-id>/<page-id>`.

</TabItem>
</Tabs>

## 2. Add components

A *component* is a public-facing label for one of your monitors. Attach any HTTP check or browser check. Heartbeats and components whose status you set yourself are added on the **Layout** tab; see [Group and order status page components](/status-pages/how-to/organize-components/).

<Tabs syncKey="interface">
<TabItem label="Dashboard">

<Steps>

1. On the page, open the **Monitors** tab and click **Add Monitor**. For a browser check, use the **Browser Checks** tab and **Add Browser Check**.

2. Pick the check under **HTTP Site** and give it a public **Name** if the internal one is too technical (`prod-api-eu-west-1` → `API`). Click **Add**.

3. Optionally click the pencil on its row and set an **SLA target** (e.g. `99.9`). The page compares the uptime over the range the visitor picked (7, 30, 60 or 90 days) with this target.

</Steps>

Repeat for each monitor you want public. A typical SaaS publishes 3–6 components: API, Web app, Auth, Webhooks, Background workers.

</TabItem>
<TabItem label="API">

```bash
# Attach an HTTP check
curl -X POST https://api.siteqwality.com/status_page/$STATUS_PAGE_ID/http_job/$HTTP_JOB_ID \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "friendly_name": "API" }'

# Attach a browser check
curl -X POST https://api.siteqwality.com/status_page/$STATUS_PAGE_ID/browser_check/$BROWSER_CHECK_ID \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "friendly_name": "Checkout flow" }'
```

</TabItem>
</Tabs>

## 3. Brand the page

<Tabs syncKey="interface">
<TabItem label="Dashboard">

<Steps>

1. On the page, open **Branding**.

2. **Upload a logo** in PNG, JPEG, SVG or WebP, up to 2MB, and a **dark theme logo** if your logo needs one. Site Qwality stores them on S3 and serves them via CDN.

3. Set the **primary color** (`#RRGGBB`) for the page title and the **accent color** for links and the Subscribe button. The page shifts either one to a readable shade in a theme where it would be hard to read; the preview shows both themes.

4. Set a **page title** (browser tab) and optional **header/footer text**.

5. Pick a **default theme** (`light`, `dark`, or `system` to follow visitor's preference).

6. Save.

</Steps>

</TabItem>
<TabItem label="API">

Branding is a two-step flow because logos go to S3 first.

```bash
# 1. Get a presigned upload URL for the logo
UPLOAD=$(curl -s -X POST https://api.siteqwality.com/status_page/$STATUS_PAGE_ID/branding/upload \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "file_type": "logo",
    "content_type": "image/png",
    "file_size_bytes": 24576
  }')

UPLOAD_URL=$(echo "$UPLOAD" | jq -r .upload_url)
S3_KEY=$(echo "$UPLOAD" | jq -r .s3_key)

# 2. PUT the bytes directly to S3
curl -X PUT "$UPLOAD_URL" \
  -H "Content-Type: image/png" \
  --data-binary @logo.png

# 3. Save the s3_key + branding fields
curl -X PUT https://api.siteqwality.com/status_page/$STATUS_PAGE_ID/branding \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d "{
    \"page_title\": \"Acme Cloud Status\",
    \"default_theme\": \"system\",
    \"logo_s3_key\": \"$S3_KEY\",
    \"primary_color\": \"#0066ff\",
    \"accent_color\": \"#00ccaa\"
  }"
```

</TabItem>
</Tabs>

## 4. Publish your first incident

An incident reaches a status page when you create it on the page, or when a [service](/incident-management/services/overview/) publishes an incident it opened automatically. Let's create one by hand to confirm the page shows it.

<Tabs syncKey="interface">
<TabItem label="Dashboard">

<Steps>

1. On the status page, open **Incidents → New incident**.

2. Title: `Investigating elevated API latency`. Severity: `minor`. Status: `investigating`.

3. Paste an initial update message: `Our monitoring detected increased latency on the API. We're looking into it now.`

4. Save. The incident appears immediately on the public page.

5. To resolve, post a closing update with status `resolved`, then mark the incident resolved. The update alone adds a line to the timeline but leaves the incident open on the page.

</Steps>

</TabItem>
<TabItem label="API">

```bash
# Create the incident on the status page
curl -X POST https://api.siteqwality.com/status_page/$STATUS_PAGE_ID/incident \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Investigating elevated API latency",
    "severity": "minor",
    "message": "Our monitoring detected increased latency on the API. We are looking into it now.",
    "affected_http_job_ids": ["<http-job-id>"]
  }'

# Post the closing update (emails confirmed subscribers)
curl -X POST https://api.siteqwality.com/status_page/$STATUS_PAGE_ID/incident/$INCIDENT_ID/update \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "status": "resolved",
    "message": "Latency has returned to baseline."
  }'

# Mark the incident resolved so the page shows it as closed
curl -X PUT https://api.siteqwality.com/status_page/$STATUS_PAGE_ID/incident/$INCIDENT_ID \
  -H "Authorization: Bearer $SITEQWALITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Investigating elevated API latency",
    "severity": "minor",
    "status": "resolved"
  }'
```

</TabItem>
</Tabs>

## 5. Confirm visitors can see it

Open `https://statuspage.siteqwality.com/<account-id>/<page-id>` in an incognito window. You should see:

- Your logo and brand colors.
- Each component with its current status (green check if healthy, red if failing).
- The published incident at the top with its updates in chronological order.
- For each HTTP check, a 90-day uptime bar chart and response-time percentiles. Browser checks show their current status and SLA label only.

<Aside type="tip">
The status page is rendered on request and is not cached at the edge. Its data is at most about 30 seconds old, and an open page refreshes its live status every 60 seconds, so visitors during an active incident see fresh data.
</Aside>
