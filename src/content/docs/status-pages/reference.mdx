The full request schemas live in the auto-generated [API Reference](/api-reference/). This page is the human-readable cheat sheet for the `/status_page` endpoint family.

## Status page

| Field | Type | Description |
|---|---|---|
| `friendly_name` | string | The page name. The only writable field on the page object itself. |
| `id` | uuid | Read-only. Page ID, also the default subdomain slug. |
| `account_id` | uuid | Read-only. Owning account. |
| `created_at` | rfc3339 | Read-only. |

Branding, components, incidents, maintenance, and the custom domain are all nested resources (below).

## Components (attached monitors)

Attach an HTTP check with `POST /status_page/{status_page_id}/http_job/{http_job_id}` or a browser check with `POST /status_page/{status_page_id}/browser_check/{browser_check_id}`.

| Field | Type | On | Description |
|---|---|---|---|
| `friendly_name` | string | create + update | Public-facing name shown on the page (independent of the monitor's internal name). |
| `sla_target_percentage` | number \| null | update only | SLA target shown next to the component, e.g. `99.9`. Send `null` to clear. |

The component's live status is the underlying monitor's status; there is no separate status field to set.

Group, order, describe and hide components in the dashboard's **Layout** tab or with `PUT /status_page/{id}/layout`, which saves the whole layout at once. See [Group and order status page components](/status-pages/how-to/organize-components/).

A page shows at most 100 monitors, HTTP and browser checks together. Attaching a 101st returns `400` with `A status page can show at most 100 monitors`. Sending the attach again for a monitor already on the page still works and just updates its `friendly_name`.

## Branding

`PUT /status_page/{status_page_id}/branding`. All fields optional; omitted fields keep their value.

| Field | Type | Constraint | Description |
|---|---|---|---|
| `page_title` | string | max 100 chars | Browser-tab and page title. |
| `default_theme` | enum | `light` \| `dark` \| `system` | Theme for first-time visitors. |
| `primary_color` | string | `#rrggbb` | Primary brand color. |
| `accent_color` | string | `#rrggbb` | Accent color. |
| `header_text` | string | max 500 chars | Text above the component list. |
| `footer_text` | string | max 500 chars | Text below the component list. |
| `meta_description` | string | max 160 chars | SEO / OG description. |
| `custom_css` | string | max 50 KB | Injected stylesheet. |
| `white_label` | bool | paid plans | Removes Site Qwality attribution. |
| `logo_s3_key` / `favicon_s3_key` / `og_image_s3_key` | string | from upload flow | Set after uploading the asset (below). |

### Asset upload flow

1. `POST /status_page/{id}/branding/upload` with `{ "file_type": "logo" | "favicon" | "og_image", "content_type": "...", "file_size_bytes": n }`.
2. The response contains a presigned `upload_url`, the resulting `s3_key`, and `expires_in_seconds`.
3. `PUT` the file to `upload_url`, then `PUT /branding` with the returned key in the matching `*_s3_key` field.
4. Remove an asset with `DELETE /status_page/{id}/branding/asset/{asset_type}`.

Public responses expose CDN URLs (`logo_url`, `favicon_url`, `og_image_url`), never S3 keys.

## Custom domain

`POST /status_page/{status_page_id}/custom_domain` with `{ "domain": "status.example.com" }`. Creating one requires a verified email address; reads and deletes do not.

| Field | Type | Description |
|---|---|---|
| `domain` | string | Your domain, lowercased. No scheme prefix, no spaces. |
| `status` | enum | `pending_validation`, `provisioning`, `active`, `failed`, `deleting`. |
| `cname_target` | string | The intermediate CNAME to point your domain at: `<status_page_id>.custom.siteqwality.com`. |
| `acm_validation.name` / `.value` | string | The DNS validation CNAME record to create while `status` is `pending_validation`. |
| `failure_reason` | string \| null | Populated when `status` is `failed`. |
| `created_at` / `updated_at` | rfc3339 | Timestamps. |

See the [custom domain guide](/status-pages/how-to/custom-domain/) for the DNS walkthrough.

## Scheduled maintenance

Customer-facing planned-downtime entries under `/status_page/{status_page_id}/maintenance`. These render on the page; to silence internal paging use [maintenance windows](/incident-management/maintenance/reference/).

| Field | Type | On | Description |
|---|---|---|---|
| `title` | string | create + update | Maintenance title. |
| `body` | string \| null | create + update | Longer description. |
| `scheduled_start_at` | rfc3339 | create + update | Planned start. |
| `scheduled_end_at` | rfc3339 | create + update | Planned end. |
| `affected_http_job_ids` | uuid[] | create + update | Which components the maintenance covers. |
| `status` | enum | update only | `scheduled`, `in_progress`, or `completed`. New entries start as `scheduled`. |

The page shows a `scheduled` entry as in progress once `scheduled_start_at` passes, and drops it after `scheduled_end_at`, so you do not have to move it by hand. Setting `in_progress` starts it early, and `completed` ends it early. Leave `affected_http_job_ids` empty to cover the whole page. Creating a maintenance emails the page's confirmed subscribers, and so do its start and end. See [Publish a status page maintenance](/status-pages/how-to/publish-maintenance/).

## Incidents on a page

Incidents published to a page (via `status_page_id` at creation, or `POST /incident/{id}/publish`) render with their updates. Field-by-field: [Incident reference](/incident-management/incidents/reference/).

## Subscribers

The people who signed up for email about a page. A page holds at most 1000 (confirmed and pending together); beyond that the public form and `POST` below answer `409`.

| Field | Type | Description |
|---|---|---|
| `id` | uuid | Subscriber id, used to remove one. |
| `email` | string | Lower-cased address. |
| `state` | enum | `confirmed` gets notices. `pending` has not clicked the link yet. `expired` never did and the link lapsed; a daily job removes it a week later. |
| `subscribed_at` | rfc3339 | When the address was first submitted. |
| `confirmed_at` | rfc3339 | Absent until confirmed. |

`GET /status_page/{id}/subscriber` returns one page, newest first, as `{"data": [...], "total": N, "counts": {"confirmed", "pending", "expired"}, "capacity": 1000}`. `total` is the number matching your filters; `counts` always covers the whole list. Filters: `state`, `q` (part of an address, ignoring case), `limit` (default 50, at most 200) and `offset`.

`POST /status_page/{id}/subscriber` with `{"email": "you@example.com"}` sends that address a confirmation link. It joins the list as `pending` and receives nothing until the person clicks. The answer is `{"email": "...", "result": "confirmation_sent"}`, or `"nothing_to_send"` when the address already subscribed or a link went out in the last hour. It returns `400` for anything but a plain address, `409` for a full page and `429` after 30 confirmation emails to the page in an hour.

`GET /status_page/{id}/subscriber/export` downloads the whole list as CSV (`email,state,subscribed_at,confirmed_at`), or JSON with `?format=json`. It takes the same `state` and `q` filters.

`DELETE /status_page/{id}/subscriber/{subscriber_id}` removes one address, for an erasure request or a mistake. Nothing more is mailed to it, and `404` means no such subscriber on that page.

## Public status page API

The status page front-end reads a public, unauthenticated JSON API. You can use it to show your status inside your own app. Base URL: `https://statuspageapi.siteqwality.com`. CORS allows any origin for `GET` and `POST`.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/status-page/{account_id}/{status_page_id}` | The whole page: headline, components, incidents, maintenance, branding. Optional `?limit=` sets how many days of `performance_data` come back for each HTTP check (default 45, at most 100); the status page asks for 90. |
| `GET` | `/status-page/{account_id}/{status_page_id}/live` | A fresh status for each HTTP check, for polling. The page calls it every 60 seconds. |
| `POST` | `/status-page/{account_id}/{status_page_id}/subscribe` | Starts an email subscription with `{"email": "you@example.com"}`. The address gets a confirmation link and receives nothing until it confirms. Returns 400 for an invalid address, 404 for an unknown page, 409 when the page already holds 1000 subscribers and 429 when rate limited. |

Both ids are in the page's address: `https://statuspage.siteqwality.com/<account-id>/<page-id>`. An unknown page returns 404.

The page response has these fields:

| Field | Type | Description |
|---|---|---|
| `global_status` | enum | The headline: `operational`, `unknown`, `degraded_performance`, `partial_outage`, `major_outage` or `under_maintenance`. `unknown` means no monitor has a current reading. |
| `groups[]` | array | Section headings in page order: `id`, `name`, `description`. A group with nothing to show is left out. |
| `http_jobs[]` | array | One entry per HTTP check: `http_job_id`, `friendly_name`, `sla_target_percentage` (or `null`), `current_status`, `group_id` (`null` for ungrouped), `description`, `show_uptime`, `order` (rank among the page's components, compare within one group), and `performance_data[]` (empty when `show_uptime` is `false`) with one row per day (`day`, `uptime_percentage`, `avg_response_time_ms`, `p50_response_time_ms`, `p95_response_time_ms`, `p99_response_time_ms`). |
| `browser_checks[]` | array | One entry per browser check: `browser_check_id`, `friendly_name`, `sla_target_percentage`, `current_status`, and the same `group_id`, `description`, `show_uptime` and `order`. No daily data. |
| `active_incidents[]` | array | Open incidents with their `updates[]`. |
| `upcoming_maintenances[]` | array | Maintenance that is scheduled or in progress: `id`, `title`, `body`, `status`, `scheduled_start_at`, `scheduled_end_at`, `affected_http_job_ids`. |
| `incident_history[]` | array | The latest 30 incidents, same shape as `active_incidents`, with `resolved_at` once closed. |
| `branding` | object \| null | Title, theme, logo, colors, header and footer text, and so on. `null` when none is saved. |
| `page_url` | string | The page's public address: `https://<your-domain>` when a custom domain is live, otherwise `https://statuspage.siteqwality.com/<account-id>/<page-id>`. Incidents are at `<page_url>/incidents/<incident-id>`. |

`current_status` is one of `operational`, `degraded` (failing, not yet confirmed down), `down`, `paused`, `maintenance` or `unknown`. The `/live` response is a list with `http_job_id`, `status` (the same values), `success`, `response_time_ms` and `checked_at` for each HTTP check.

## Published files

The same page is also published as static files that update within a minute of a change: the page JSON above at `https://statuspagecdn.siteqwality.com/v1/pages/<account-id>/<page-id>.json`, and beside it `summary.json`, `incidents.rss`, `incidents.atom` and `badge.svg`, plus an embed script at `https://statuspagecdn.siteqwality.com/v1/embed.js`. See [Feeds, badge and embed](/status-pages/how-to/feeds-badge-embed/).
